# Networking

Server authoritative, Source/GMod style. Start a server with `luajit glw --server` (physics is on, `host` runs automatically, `GOLUWA_PORT` overrides the port for `host` and `connect`), and a client with `luajit glw --3d` then `connect 127.0.0.1`, or headless with `luajit glw --cli --physics`.

- Transport: `goluwa/network/connection.lua` (handshake, reliable ordered per channel, fragmentation, sequenced/unreliable, pings, timeouts) on `transport_layer.lua` (UDP). `GOLUWA_NET_LATENCY`, `GOLUWA_NET_JITTER` (ms) and `GOLUWA_NET_LOSS` (%) simulate bad connections.
- To replicate an entity, give it the `network` component (`shapes.Box{Network = true, ...}` or `Entity.New{network = {}, ...}`). Every component declares what replicates in a `META.Network = {Key = {type, rate, flags, interp}}` table (transform, model, rigid_body, lights, ...). The spawn packet carries the component list and their values, and the client builds the entity through `Entity.New`. Models are paths the client already knows (`model` component: `ModelPath`, `ModelOptions`, `MaterialConfig`, procedural `models/*.lua` work). Rigid bodies obey transform scale. Non owned bodies are kinematic on clients.
- Players: input is a `usercmd` (`goluwa/network/usercmd.lua`) produced once per physics tick by `player_controller` (from `player_input` locally, from the network on the server, or from a `CreateMove` hook for bots). `player_movement` only consumes the command, so the same code predicts on the client and simulates on the server. The client reconciles against `player_ack`, the server relays commands to the other players, and the physgun runs on the server from the command buttons.
- The NETWORK tab of the PERF window (`perf network`, `net_stats` prints the rows) shows the network stats. Tests: `luajit glw test network/` (includes two process e2e tests that spawn a server, a bot and an observer from `test/network_e2e/`).

# Players

A player is one entity (the nick, `player_camera_rig` for the local one) with `transform`, `rigid_body`, `player_controller`, `player_movement`, `weapon_holder`, `player_avatar` and for the local one `camera` and `player_input`. Its rotation is the yaw of the view (`player_movement:SetBodyYaw` sets the body and the transform every tick from the command, so the server and the prediction agree, the capsule stays upright and its pitch is only in the head). Its origin is where it stands, the feet, in both modes (fly mode keeps the capsule but turns collision off). `rigid_body.CenterOffset` is where the center of the body is relative to the entity origin (`Position = origin + CenterOffset`, the transform is written back as `Position - CenterOffset`, `GetOriginPosition`, `GetInterpolatedOrigin`), `player_movement` keeps it at half the capsule height, and everything physics does (solver, sweeps, prediction, `processed.position` of the acks) stays in center space. `player_movement:GetViewOffset()` is the eye above the origin (`SetEyePosition` places the player by its eye), `spawn:GetPlacement(0)` puts the feet on the spawn point.

- `armature` (`goluwa/entities/components/armature.lua`, client side) holds a rig made from a registered skeleton (`Armature.RegisterSkeleton(name, {{bone, parent}, ...})`, the player's is `root, body, head, hand_r, hand_l` in `network_players.lua`) and nothing is skinned. Whatever animates it calls `SetBone(name, matrix, space)` with `"local"` (relative to the parent bone) or `"model"` (relative to the entity) matrices (`render3d/skeleton.lua` and `rig.lua` are the same classes a skinned model uses, a clip or procedural code can drive it later), `GetBoneMatrix(name)` reads them back.
- `transform.Attachment` (storable, `root` by default, every transform has it) attaches a transform to a bone of the armature of its nearest ancestor that has one: `world = local * bone * parent_world`. `root`, or a name that armature does not have, is the origin of the parent. The property editor lists `root` and the bones of that armature. An attached transform is always dynamic (`IsFrameDynamic`), and `visual.lua` treats everything under an armature as dynamic.
- The look of a player is its outfit (`addons/game/lua/outfit.lua`, a prefab, the root is an identity container). The default one has a `body` capsule node with a script that squashes it from `player_avatar.crouch_alpha` (the crouch look lives in the outfit, `outfit.CrouchScript`) and a `visor` attached to the `head` bone, an `Attachment` finds the armature of the nearest ancestor. `player_avatar` builds the armature on clients, adds the outfit instance as a child of the player and animates the bones each frame (the player entity itself turns with the view in yaw, so the bones are set relative to it: `head` only adds the pitch and sits at the eye, `hand_r` and `hand_l` follow the pitched view), the weapon models sit on `hand_r` (`weapon.lua` `UpdateModel` creates an instance of the weapon's `ModelPrefab`, one of the built in prefabs of `addons/game/lua/weapon_models.lua`, and sets its visibility, `weapon:GetMuzzle()` is the node of that prefab named `muzzle`, the weapon values stay on the weapon components so a pushed model prefab only changes how it looks). The whole outfit is hidden in first person (`outfit.visibility:AddHider("first_person")`, see Visibility below). A player whose outfit has not arrived is not drawn. The parts follow the player entity, `transform` renders a physics body interpolated. Nothing is replicated except `Crouching`, `Holding` and `ViewRotation` and the outfit definitions. There is no physgun beam yet. A weapon is a built in prefab named like its component (`addons/game/lua/weapons.lua`, `weapons.Register(name, values)`: the `weapon` values Slot, DisplayName, ModelPrefab, FireRate, HiddenInFirstPerson plus the `weapon_*` component that does the firing), `weapon_holder:Give(name)` instantiates it, `GiveLoadout()` gives `weapons.Loadout`. The player entity is not a prefab: remote clients only get `transform`, `rigid_body`, `network` and `player_avatar` from the spawn packet, and a prefab with `player_movement` and `player_controller` would build those on every proxy too.
- The `player` skeleton is Source like: `root, body (pelvis), spine, chest, neck, head`, `clavicle/upperarm/forearm/hand` and `thigh/calf/foot` for `_r` and `_l`. The procedural animation only moves `head` and the hands. `player_outfit_source` (`addons/game/lua/outfit_source.lua`, built in, pick it with the pvar `cl_outfit`, default `player_outfit`, the outfit pushed to the server is whatever it names) is a gmod player model (`models/player/kleiner.mdl`, needs the gmod mount) with an `animator` and a `script` that does everything inline: velocity from the render position of the player (smoothed), `move_x`/`move_y`/`vertical_velocity` pose parameters, sequences `idle/walk/run/cidle/cwalk/jump` with the suffix of the active weapon's model prefab (`all` without one), and each frame it copies the rig bones into the player's armature (`SetBone(name, matrix, "model")`, the head and neck take part of the view pitch, the hands keep the animated position but point where the player looks so weapon models sit in them). It calls `player_avatar:SetBonesDriven(true)` so the procedural animation stops, `player_avatar.pitch` is the view relative to the player. `transform:GetRenderVelocity()` is the velocity it reads, measured from the world position (smoothed, once per frame, zero when not asked for 0.25 s, do not modify the vector) because `rigid_body` velocity is only real for the body the client predicts and is not replicated. Scripts in a pushed outfit are dropped by a server without `sv_client_scripts`, so other players only see it animated when that is on. Test: `luajit glw test render3d/outfit_source.lua`.
- The editor window owns an editor camera `View` (priority 10 above the player's). While it is open the player is shown even in first person (`player_avatar` only hides it when the player's camera is the rendered one). Ctrl+E (`editor_window:SetPlaying`, Escape also ends it) hides the editor window, frees its mouse request and fires `EditorControlsChanged`, `player_input` then takes input although its camera is not rendered (`controls_override`), the editor camera stays where it is and the gizmo is off until the editor comes back.
- Anything placing a player by eye uses `SetEyePosition`. LuaJIT miscompiled `ffi.copy` (`Vec3:CopyFrom`) into a vector followed by reads of the same vector in one trace (stale values, a body that flew away on about one run in twenty), write the fields one by one when the next lines read what was copied, see `RigidBody:SynchronizeFromTransform`.

# Visibility

The `visibility` component (`goluwa/entities/components/visibility.lua`) works like hiding a part in pac3: an entity is hidden when it hides itself or any entity above it does, and what is below keeps its own state for when the root shows again. `Visible` is the stored flag (default true), `AddHider(name)` / `RemoveHider(name)` are named reasons that stack (first person, an editor, a script), `IsSelfHidden()`, `IsHidden()` (own or inherited) and `GetReasonsHidden()` read it. Entities without the component only inherit: `entity.visibility_hidden` exists on every entity and is kept up to date when the component changes and when an entity is built, parented or unparented (`Visibility.Refresh(entity)`, unchanged state stops the walk). `OnHide` and `OnShow` are local events of every entity whose state changes, so components and scripts (`function Entity:OnHide()`) receive them; they are not sent while an entity is being built, a component that needs the state then implements `OnEntityConstructed`. `visual` follows them: `Visible` is what is drawn, the own flag of `SetVisible` unless the entity is hidden. `light` and `water_volume` keep their own stored `Visible` and are in the scene while it is on and their entity is not hidden. Tests: `luajit glw test entities/visibility.lua`.

# Ownership and permissions

Every entity has an owner, `entity:GetOwnedBy()`: a client or a world (`Entity.World`, `Panel.World`). It is not `component.Owner`, which is the entity a component sits on. `SetOwnedBy(owner)` sets it explicitly (an `OnEntityHierarchyChanged` `owned` event follows), an entity without one belongs to its parent's owner and at the top to its world, so code that creates entities needs no ownership code and only player content sets an owner. `BaseEntity.GetOwnerKey/GetOwnerLabel` give a key and the editor's label (`you`, a nick, `none` for a world).

- The `network` component sets the owner from `NetworkOwner`, `player_avatar` owns the player entity and the head, body and beam it builds (the outfit and weapons inherit), a client's pushed scene entities are owned by that client (the server sets it from the sender, never from the payload, and tells the other clients in the blob header, the snapshot for late joiners has an `owners` blob that is applied once it is spawned).
- `Transient` now only means derived or runtime, never saved or synced. `entity:IsRuntime()` is `GetTransient()` that a world owns, what a client owns is not hidden by the editor (tree filter, picker). `scene.Serialize` (what Save writes) leaves out what other clients own, a snapshot to a joiner includes everything.
- The entity tree groups the children of a root under their owner when `GroupByOwner` is set (you first, other players by nick, none last, `OwnerGroup` nodes, expanded unless collapsed explicitly). The editor sets it, groups are views, the hierarchy below them is the real one.
- `goluwa/entities/permissions.lua`: `permissions.Can(client, "create" | "modify" | "remove", entity)` and `CanPushPrefab(client, name)`, the server's `scene_sync` handlers (push, remove, prefab) ask. A listener of the `EntityPermission` event (`client, action, entity or prefab name`) answers first with true or false. The pvar `sv_entity_permissions` is `all` (default, everything is allowed) or `owner` (clients only change what they own, add to the world or to their own entities, and replace no shared prefab except what a listener allows, `network_players` allows the player's own outfit). Tests: `luajit glw test entities/ownership.lua entities/permissions.lua panel/entity_tree_owner.lua` (ownership and permissions pass as of 2026-10-11). Don't revert `Transient` to ownership-only, and new player content should rely on parent inheritance of the owner.

## Session-scoped edits, pac3 model

*server never persists pushed scenes/prefabs; clients resubmit on join; player outfit = local player_outfit.prefab*

Client-pushed scene entities and prefabs live in server memory for the session only. The server does not save scenes or prefabs by default; a server script may persist them. Players keep their own copies locally and resubmit on join. This follows pac3 (the user authored both pac3 and goluwa; goluwa is what they wanted pac3 to be).

**Why:** the user corrected earlier assumptions (from other sessions) that the server stores scenes/prefabs.
**How to apply:** don't add server-side saving to scene_sync handlers; per-player content (outfit) is a local file sent on connect. See [Prefab, script and use systems](prefabs-and-scripts.md#prefab-script-and-use-systems).
