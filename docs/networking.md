# Networking

Server authoritative, Source/GMod style. Server: `luajit glw --server` (physics on, `host` runs automatically; `GOLUWA_PORT` overrides the port). Client: `luajit glw --3d` then `connect 127.0.0.1`, or headless `luajit glw --cli --physics`. Tests: `luajit glw test network/` (includes two-process e2e tests using `test/network_e2e/`).

- `--server-client` (with `--3d`): the client runs the server in a second lua state of the same process (`goluwa/network/server_process.lua`, started from `run_game`, listens on 127.0.0.1, `GOLUWA_PORT` or 1234) and connects once it reports ready (after its startup command). The command after the flags (`map gm_construct`) runs on the server, not the client. Chat `!commands` then run on the server through a `server_command` message authorized by a per-run token and the output comes back as console lines. The worker state has `_WORKER_THREAD`, so it skips the repl, the pid file and signal handlers; `os.exit` there ends the whole process.
- Transport: `goluwa/network/connection.lua` (handshake, reliable ordered channels, fragmentation, sequenced/unreliable, pings, timeouts) over `transport_layer.lua` (UDP). `GOLUWA_NET_LATENCY`, `GOLUWA_NET_JITTER` (ms) and `GOLUWA_NET_LOSS` (%) simulate bad connections.
- Replication: give an entity the `network` component (`shapes.Box{Network = true}` or `Entity.New{network = {}}`). Each component declares what replicates in `META.Network = {Key = {type, rate, flags, interp}}`; a component only joins the spawn packet if it has a `Network` table at all, so a component that has to exist on clients but replicates nothing declares `META.Network = {}`. The spawn packet carries the component list and values and the client builds the entity through `Entity.New`. Models replicate as paths the client already knows. Non-owned bodies are kinematic on clients. `rigid_body:GetServerDynamic()` tells a client whether the server body is dynamic (the physgun prediction needs it to pick what it can grab).
- Players: input is a `usercmd` (`network/usercmd.lua`) produced once per physics tick by `player_controller` (from `player_input` locally, the network on the server, or a `CreateMove` hook for bots). `character_movement` only consumes the command, so the same code predicts on the client and simulates on the server. The client reconciles against `player_ack`; the server relays commands to other players; the physgun runs on the server from the command buttons.
- `net_prediction_debug` (addons/debug) toggles a view of the owner's prediction: green box = predicted body now, blue = the client's own predicted state at the last acked command, red = the server's state at that command, a yellow line for the error, and a label with ack age, commands ahead, position/velocity/distance error and how many of the last 64 acks needed a correction (`player_controller.last_ack`, `GetAckStats`). Reconcile corrects at 2 mm position error or 0.3 velocity error; a smaller velocity-only difference is ignored (it is usually the carry velocity of a body the client does not simulate, like a dynamic prop under the player) because a velocity error that matters shows up as a position error within a few ticks, and injecting it every ack made the player wobble. It also draws the real colliders of networked bodies within 8 m (green: the client's collider edges; red: the server's collider bounds, fetched with `net_debug_request`/`net_debug_response` from `prediction_debug_server.lua`) with a label that turns yellow when the shape type or vertex count differs, the player's own collider at the predicted and the acked position, and the last physgun and toolgun traces of both sides (`lua/trace_debug.lua`, recorded only while the view or a debug request has enabled it) with how far apart their hits are. Identical client and server shapes that still look wrong mean the model's physics data is wrong.
- The NETWORK tab of PERF (`perf network`, `net_stats`) shows stats.
- Sandbox spawning (`addons/sandbox/lua/spawn_requests.lua`): the spawn menu asks the server with `sandbox_spawn(kind, name, position, yaw)` (kinds `weapon`, `interactive`, `npc`, `prop`, `vehicle`) and the server validates the name, `permissions.CanSpawn` and that the position is within reach of the player's eye before spawning, owned by the sender. With no server it spawns locally. Entity ownership of spawned entities is server side only.
- Sandbox undo (`addons/sandbox/lua/game_history.lua`): on a server every client has its own `History` (`game_history.GetHistory(client)`), filled by spawns and toolgun `context:Record`. A connected client sends `sandbox_history("undo"|"redo")`, the server applies it and answers `sandbox_history_applied` for the notice. Restoring an entry re-adds the `network` component (transient, so not in the snapshot) to what was networked.
- Sessions: client-pushed scene entities and prefabs live in server memory for the session only (like pac3). Do not add server-side saving to `scene_sync` handlers; per-player content (outfit) is a local file sent on connect.

# Players

A player is one entity with `transform`, `rigid_body`, `player_controller`, `character_movement`, `character_pose`, `attachment_points`, `procedural_pose`, `weapon_holder`, `player_avatar` and, for the local one, `camera` and `player_input`. The player entity is deliberately not a prefab: remote clients only get `transform`, `rigid_body`, `network` and `player_avatar` from the spawn packet.

- The owner's rig is the same entity as the server's player: `player_start` carries the server player's network id and the client links its predicted rig to it (`network.Link`), so the owner never receives the player root itself (it is predicted) but receives everything else the server makes under it. Entities whose `network` has `SendToOwner` (weapons) are replicated to their owner too, so weapon state, effects and entity references work the same for the owner as for everyone else. A client therefore must not create networked children itself while linked (local loadout is removed on link and given again on `Disconnected`).
- The player root is not sent to its owner, but a var with `to_owner = true` in its `Network` info is (`health`, `rpg`, `status_effects`, `ragdoll` Limp, and the pose vars only the server can know: hits, reacts, actions, blocking). Everything else on the root is owner-authored or predicted (movement, view, crouch, `Shots`). The server resends all `to_owner` vars when it links the owner (`ResendOwnerVars`).
- Effects are predicted by the owner and sent by the server to everyone else. A weapon implements `OnWeaponPredictThink/Primary/Secondary` (same gating as `OnWeaponThink/Primary/Secondary`, called by `weapon:Predict` from the owner's linked rig only, and only for effects, never for state) and the server's effect events (`replicated_event` with a `get_predicted_client`) skip the owner. A component with `NetworkOwnerExcluded` (`tool_beam`) is left out of its owner's spawn and updates the same way, so the owner's predicted state is not overwritten. To see exactly what other players get, start with `GOLUWA_PVARS="net_prediction=false"` (pvar `net_prediction`, read when the owner is linked and when the server sends, so set it at startup on both sides; `--server-client` shares the environment): the client skips `weapon:Predict` and the server stops excluding the owner. It also turns off movement prediction: the player root (`network.Predicted`) is replicated to its owner like anyone else, the linked rig becomes a kinematic body driven by that transform, `character_movement` does not simulate the owner's commands (they are still built and sent) and `player_ack` is not reconciled. `character_pose` then treats the rig as a remote avatar (speeds from the replicated transform, view, crouch, lean and distance from replicated vars), which is what other players animate from.
- Rotation is the view yaw (`character_movement:SetBodyYaw` every tick from the command, so server and prediction agree; pitch is only in the head). Origin is the feet in both modes. `rigid_body.CenterOffset` is the body center relative to the entity origin: everything physics does (solver, sweeps, prediction, `processed.position` of acks) stays in center space. Place players by eye with `character_movement:SetEyePosition`, and by feet with `spawn:GetPlacement(0)`.
- `armature` (client side) holds a rig made from a registered skeleton (`Armature.RegisterSkeleton`); whatever animates it calls `SetBone(name, matrix, "local"|"model")`. `transform.Attachment` attaches a transform to a bone of the nearest ancestor armature (`world = local * bone * parent_world`); an attached transform is always dynamic.
- The look of a player is its outfit (`addons/game/lua/outfit.lua`, a prefab; default has a crouch-squashed body and a visor on the `head` bone). `player_avatar` builds the biped armature on clients and adds the outfit as a child; bones are driven by `procedural_pose` or the outfit's `source_pose` (see characters.md). The outfit is hidden in first person via `outfit.visibility:AddHider("first_person")`. Weapons are built-in data-only prefabs (`addons/game/lua/weapons.lua`, definitions in `weapons/*.lua`: model nodes plus a `script` component whose source holds the behaviour and `OnWeapon*` hooks); `weapon_holder:Give(name)` instantiates one. A weapon without a `weapon_holder` parent is in the world: the authority gives it a dynamic `rigid_body` sized by `WorldSize`/`WorldCenter` (`weapon:RefreshWorldState`, on `OnParent`/`OnUnParent`), `OnCollisionEnter` with a holder calls `weapon_holder:Pickup`, `weapon_holder:Drop` puts it back; `weapons.Spawn` creates one. `player_outfit_source` (`outfit_source.lua`, pvar `cl_outfit`) uses a gmod player model animated by `source_pose` (`gmod_player` profile) from `character_pose` speeds (`rigid_body` velocity where the body is simulated, otherwise `transform:GetRenderVelocity()`; `rigid_body` velocity is only real on the predicting client and is not replicated). Scripts in a pushed outfit are dropped by a server without `sv_client_scripts`.
- The editor window owns an editor camera `View` above the player's; Ctrl+E (`editor_window:SetPlaying`) hands input back to the player while the editor camera stays.
- Do not use `ffi.copy` (`Vec3:CopyFrom`) into a vector that is read in the same trace (miscompile, see `RigidBody:SynchronizeFromTransform`).

# Visibility

The `visibility` component (`goluwa/entities/components/visibility.lua`) works like hiding a part in pac3: an entity is hidden when it or any ancestor is, and descendants keep their own state. `Visible` is the stored flag, `AddHider(name)`/`RemoveHider(name)` are stacking named reasons (first person, editor, script). Every entity has `entity.visibility_hidden` kept current (`Visibility.Refresh`) and receives `OnHide`/`OnShow` local events (not while being built: use `OnEntityConstructed`). `visual` follows them; `light` and `water_volume` keep their own `Visible`. Tests: `luajit glw test entities/visibility.lua`.

# Ownership and permissions

Every entity has an owner, `entity:GetOwnedBy()`: a client or a world (`Entity.World`, `Panel.World`). It is not `component.Owner` (the entity a component sits on). An entity without an explicit owner inherits its parent's, so code creating entities needs no ownership code; only player content sets one (`SetOwnedBy`). The server sets a pushed entity's owner from the sender, never from the payload.

- `Transient` means derived/runtime, never saved or synced. `entity:IsRuntime()` is transient and world-owned. `scene.Serialize` leaves out what other clients own; a joiner snapshot includes everything. Do not revert `Transient` to ownership-only.
- `goluwa/entities/permissions.lua`: `permissions.Can(client, "create"|"modify"|"remove", entity)` and `CanPushPrefab(client, name)`, asked by `scene_sync` handlers. An `EntityPermission` event listener answers first. Pvar `sv_entity_permissions` is `all` (default) or `owner`.
- The entity tree groups children of a root under their owner when `GroupByOwner` is set (the editor does).
- Tests: `luajit glw test entities/ownership.lua entities/permissions.lua panel/entity_tree_owner.lua`.
