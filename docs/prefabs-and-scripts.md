# Prefabs

A prefab (`goluwa/entities/prefab.lua`) is a tree of scene records plus declared inputs. An instance is an entity with the `prefab` component (`Path`, `Inputs`, `goluwa/entities/components/prefab.lua`); its generated nodes are never saved with the scene, only the path and input values are. Editing any instance writes back to the definition and every other instance follows. The definition is a saved tree only: behaviour comes from the `script` component ("like pac3").

- The root record becomes the instance's own entity. The instance keeps entity properties, `transform`, `rigid_body`, `network` and `prefab` (`INSTANCE_COMPONENTS`); the definition owns every other root component and all child nodes. `shapes.Box/Sphere/Cone/Capsule` are thin wrappers over built-in prefabs in `goluwa/entities/prefabs/shapes.lua`.
- Definitions: `prefab.Register(name, {inputs = {...}, entities = {...}})` or `.prefab` files in `storage/prefabs/` (`prefab.Save`, `prefab.Get`; any mounted `prefabs/` folder is searched). `entities` use the scene record format, parents before children, root first with guid `root`. Instantiate with `Entity.New{prefab = {Path = name, Inputs = {...}}}`. Prefabs are assets of category `prefabs`; a registered one is virtual until saved. Prefabs can contain instances of other prefabs.
- An input is `{Name, Type, Default, Targets = {{Node, Component, Property, Key}}}`: a push binding (not `objects.AddPropertyLink`). Setting it (`instance.prefab:SetInput`, property editor, `Inputs` property) pushes into every target; `Component = "entity"` targets entity properties; `Key` addresses a field of a table valued property (`ModelOptions.size`, script `Values`). Editing a bound property changes the input of that instance instead. `Inputs` must be declared before `Path` in the component so apply order builds once with the inputs.
- Write-back is explicit, never automatic: `prefab.MarkDirty(object, property_name)` writes only that property of that node (`CommitProperties`); `prefab.MarkStructureDirty(entity)` re-captures nodes, components and hierarchy (`Commit`, keeping values of existing nodes). Both flush once per frame in `prefab.Flush`. Code that drives nodes (scripts) must not be written back: wrap in `prefab.Suppress/Unsuppress` (script calls already are). The editor does write-back for the selected entity (`addons/editor/lua/prefab_tools.lua`). Whole-instance capture would bake script-driven values into the definition.
- Events: `PrefabChanged` fires for every definition change, `PrefabInputsChanged` only when inputs/links change; the editor rebuilds its property panel only on the latter (rebuilding on value edits destroys the control being dragged).
- `prefab.CreateFromEntity(entity, name)` turns a subtree into a prefab; `prefab.Unpack(entity)` turns an instance into plain entities. `BaseEntity:GetPrefab()` returns the nearest instance root, `GetNode(id)` a node of it.
- Patches and prefab mode: in a scene an instance is one tree node; a child added under it is a patch (never written to the definition). The editor's Edit prefab enters prefab mode (`prefab.SetEditing(component)`); children added then become nodes. `prefab_tools.lua` implements the editor integration (context actions to expose properties as inputs, badges, tabs).
- Records are shared by all instances: always `copy_value` before applying (aliasing a Vec3 corrupts the definition). Sync re-applies must skip equal values (`apply_properties(..., skip_equal)` in `scene.lua`), otherwise table valued properties like `ModelOptions` look changed and rebuild every instance's models.
- `rigid_body` is never serialized without `ShapeModelPath`, so prefab data cannot carry colliders: scripts add them in `OnCreate` (`EnsureComponent`), and bodies only work on root-level entities (`SynchronizeFromTransform` uses the local transform), never on prefab child nodes.
- Replication: definitions replicate through `scene_sync` (server sends every non-builtin definition before the scene snapshot and after each edit; a client editor sends edits via `sv_scene_push`). Child nodes are built on every side from the definition. A player's outfit is the prefab named by `cl_outfit`: the local file `storage/prefabs/player_outfit.prefab` (custom), the builtin `player_outfit_default`, or `player_outfit_source` with a `Model` input from `cl_outfit_model`. It is sent as `outfit_<uniqueid>` with the input values baked into its defaults (`addons/game/lua/outfit.lua`). The Outfit desktop program picks one; `prefab.CreatePreview(name, inputs)` previews a prefab with temporary inputs.
- Examples: `addons/examples/lua/examples/render3d/prefab_inputs.lua`, `prefab_scripts.lua`. Tests: `luajit glw test entities/prefab.lua`.

# Scripts and use

The `script` component (`goluwa/entities/components/script.lua`) has one real property, `Source`, a Lua string that is a normal component file (`local META = objects.CreateTemplate("x") ... return META:Register()`, see `addons/game/lua/components/`), loaded with the whole engine as environment; `import` works with root-relative paths. The component it defines is instantiated on the script's owner (`self.Owner`).

- Hooks: `Initialize` (not `OnCreate`: `self.Owner` is not set during `OnCreate`), `OnUpdate(dt)` (after `self:AddGlobalEvent("Update")`), `OnRemove`, and any `On*` local event such as `OnUse(user, hit)`. Creation is deferred (`prefab.WhenBuilt`) until the outermost prefab build finished so every node exists. A script that errors is logged, stays off and shows the error until `Source` changes. Hooks run under `xpcall`.
- Classes created by the chunk get a private `RegistryKey` (`scriptN:<Type>`) so they never clobber real components of the same Type. Classes are cached by source text with a refcount, so scripts with the same source SHARE upvalues: per-instance state must live on `self`.
- The instance is `entity:CreateSubObject(meta, {ScriptComponent = script})`, aliased as `entity[Type]`, not in the component list (the scene would serialize it). Storable props of the class persist in the hidden storable `Values` (non-default only); editor rows come from `GetDynamicProperties`. Prefab inputs link to them as keyed targets `{Component = "script", Property = "Values", Key = <prop>}`.
- Scripts run in every process. Shared state belongs in prefab inputs changed only where `network.HasAuthority()` is true (server or standalone game); NOT `SERVER` (false in a standalone `--3d` game).
- `sv_client_scripts` (off by default) controls whether the server keeps script components clients send, as entities or inside a prefab definition.
- Use: pressing E (not while the physgun holds something) sets `usercmd.BUTTON.USE`; the authority (`weapon_holder:OnPhysicsUpdate`) calls `use.Press` (`goluwa/entities/use.lua`), which finds the closest collider or visible mesh within `use.MaxDistance` and fires `OnUse(user, hit)` on that entity and up its parents until a handler returns true. `network/use_sync.lua` tells clients (message addressed by network id or guid plus prefab node path). A dedicated server only sees colliders, so usable things need a `rigid_body`. When the direct hit has no enabled `usable` in its parent chain, the `FindUseFallback` hook (`usable` component) picks the enabled `usable` closest to the view direction (within 1.5x `MaxDistance`, inside a 60 degree cone), so third person does not need exact aim. `use.Find` is `Trace` plus that fallback; the HUD prompt and `use.Press` both go through it. A `usable` counts only while it is `Enabled` and no component of its entity returns false from the local `OnCanUse` event (a held weapon does, so a weapon in someone's hands is never offered or taken, and the HUD never measures one that has no body).
- Example pitfalls: usable example scripts add a static `rigid_body` in `OnCreate`; a light inside a mesh needs `OcclusionMap = false` or the mesh shadows it.
- Examples: `prefab_scripts.lua` (lamp, door, dispenser, beacon). Tests: `luajit glw test entities/script.lua`. The Lua source editor is `render2d/ui/widgets/code_editor.lua` with `properties/code.lua`.
