# Debugging

Temporary print logging and code edits are fine for finding causes; remove them afterwards.

- `table.print(tbl)`, `print_once(...)`, `debug.trace()` (traceback of the caller), `print(x) os.realexit(0)` (print and force exit).
- `--exit-on-error` turns Lua errors (and Vulkan validation messages, when the layers are on) into an exit instead of a hang. `--vulkan-validate` enables the validation layers; without `--exit-on-error` it reports messages and keeps running. `GOLUWA_VALIDATE=1 VK_LAYER_VALIDATE_SYNC=1` runs the layers and the sync checks.

## Device lost

`VK_ERROR_DEVICE_LOST` carries no message, the kernel says why: `journalctl -k | grep Xid` (nvidia; `dmesg` is usually unreadable). Xid 13 is a bad compute launch descriptor, Xid 109 `CTX SWITCH TIMEOUT` is a context the gpu could not preempt (a hang). A run can hang without printing device_lost; garbage or black screenshots with no error are a hint.

- `Fence:Wait` asserts on a lost device, so the first error is the real one; later validation messages (`vkResetCommandBuffer ... is in use`) are consequences.
- `GOLUWA_CHECKPOINTS=1` (`VK_NV_device_diagnostic_checkpoints`, `goluwa/render/vulkan/internal/checkpoints.lua`) puts markers before every named gpu scope, dispatch, ray launch, acceleration structure build and instrumented command buffer methods. On loss the engine prints the markers the queue reached: the last `stage 0x2000` marker is the command that had not finished.
- On loss the engine always prints the `VK_EXT_device_fault` description and on Linux the recent `NVRM: Xid` kernel log lines (`checkpoints.Report`).
- `GOLUWA_NO_RAY_TRACING=1` disables ray tracing, useful to bisect.
- Intermittent Xid losses in the biggest `vkCmdTraceRaysKHR` launch of a frame (ddgi_shade, reflections_trace) were timing dependent and traced to the driver, not to engine objects or synchronization; do not spend long hunting it in engine code.

# Profiling

`PROF` (`goluwa/global_environment.lua`) wraps LuaJIT's statistical profiler. `PROF.Start(id, opts)`: `frames` (default 300; stops and shuts down after that many frames), `shutdown = false` (no auto shutdown), `trace_recorder = false` (do not observe trace recording), `skip_frames`, `sampling_rate`. Prefer `PROF.Start(id, {trace_recorder = false, shutdown = false})` and stop it yourself with `PROF.Stop()` then `PROF.Summary(path, {top_n = 20})`: trace recording distorts the numbers and has segfaulted on shutdown. It only sees Lua CPU time, see performance.md for what it misses.

- Profile N update frames then exit: `luajit glw --2d --background lua "PROF.Start('id', {frames = 1000}) import('tmp/script.lua')"`.
- Profile a one-off action: `luajit glw --2d --background lua "PROF.Start('id', {shutdown = false}) work() PROF.Stop() system.ShutDown(0)"`.
- Captures are saved to `storage/logs/jit_profile_<id>.glwp`. `PROF.Summary(path, opts)` takes that capture path, prints to stdout, and with the trace recorder on ends with "top aborts by source" (reason, line, count): look there for the files you changed. "error thrown or hook called during recording" entries with a count of 1 come from the profiler itself.
- Headless physics runs: `--cli` and `--server` sleep 33 ms every Update (`--fps=N` changes it), so wall frame time there is meaningless. Use `--headless --fps=60`, call `physics.Initialize()` yourself, and time `physics.instance.UpdateFixed`; without a limiter a frame takes microseconds and the fixed step never accumulates a tick. Headless profiles are much steadier than ones with the renderer.

# jit.log (streaming trace and profile log)

A LuaJIT fork in `local_stuff/LuaJIT-Profiler` (pinned to the flake's rev) adds `require("jit.log")`, which writes trace start/stop/abort/flush and profiler samples as binary records straight from C, with no Lua callbacks. Run the engine with `local_stuff/LuaJIT-Profiler/src/luajit glw ...` to use it.

- Build: `nix-shell -p gcc gnumake --run 'make amalg XCFLAGS="-DLUAJIT_ENABLE_LUA52COMPAT" BUILDMODE=static'` in the fork. Run `make clean` first when switching between amalg and non-amalg builds.
- API: `log.start(path, {traces, profile, interval, mode, depth, alloc})`, `log.stop()`, `log.flush()`, `log.status()`, `log.string(s)`, `log.section_ptr()` (address of the uint32 section id every sample snapshots; set it through ffi, a C call inside traced code would abort the trace), `log.heap(limit)`.
- `alloc = bytes` samples allocations: every that many bytes allocated by the logged VM, one record with the Lua stack and the running trace, weighted by the bytes. It only runs together with `profile = true` (a long `interval` keeps the time samples, which abort trace recording, rare). This is what finds allocation sources; the `gc_total` of time samples only correlates with them.
- `log.gc()` returns the time spent in each collector state (`propagate`, `atomic`, `sweep`, `finalize`, ...) while logging, cumulative with call counts and the longest call; diff it per frame to see what a long frame spent in the collector.
- `log.heap(limit)` runs a full collection and returns the live heap by object type, by cdata ctype (anonymous structs list their fields), by table metatable, and `edges`: what holds tables, closures and cdata (child, key, parent class). It works without a running log.
- Starting or stopping a profile in line or function mode (`mode = "l"`/`"f"`) flushes every trace, so the log begins with a full recompile: `R` (compiler) samples and trace starts in a short window are inflated by it, and the two `trace_flush` records the summary reports are the profiler's own. Log a long window (hundreds of steps) or compare against a `jit.attach(cb, "trace")` flush count from a stock run before blaming the engine for flushes.
- Samples are taken on the main thread's CPU clock and only interrupt that thread. Stock `jit.profile` (`PROF`) uses a process-wide `SIGPROF` that also lands on busy worker threads: the handler then races the main thread on the dispatch table and can leave the profile hook stuck on (the VM slows to a crawl), and the sample rate follows the CPU time of all threads.
- Read it outside the engine with `tools/log_reader.lua` in the fork: `local_stuff/LuaJIT-Profiler/src/luajit local_stuff/LuaJIT-Profiler/tools/log_reader.lua file.gljl` prints a summary, or `dofile` it for `Reader.New(path)`, `:Poll()` (incremental, works while the log is still being written), `:GetLiveTraces()`, `:Summary()`, `.events`. Aborts carry the C source site and a description of the live values; side trace head register failures name the Lua locals.
- The log is process-wide but only follows the Lua state that started it. Worker threads have their own VM and JIT and are ignored.
- Format: `u8 type, 3 byte padded varint length, payload`, payload starts with a varint ns delta. Strings, protos and stacks are defined once before first use; unknown record types can be skipped.

# Desktop and the PERF window

- `goluwa/render2d/ui/desktop.lua` is the desktop (keys bound in `goluwa/main.lua`): hold `c` for program buttons and a free cursor, Escape toggles it dimmed and sticky. Add programs with `desktop.RegisterProgram{...}`, menus with `desktop.RegisterMenu`, backdrops with `desktop.RegisterBackdrop`; read the register functions for the fields. A pinned window stays on screen in HUD mode when the desktop hides.
- PERF (`h` toggles, `addons/debug/.../perf_window.lua`) is a `Tabs` window; features add tabs with `perf.RegisterTab(name, order, view)` (`addons/debug/lua/perf.lua`, `view` is a react component, see ui.md). Only the open tab of a shown window is mounted, so what a tab does on mount/unmount is its data collection (the PHYSICS tab enables `physics/stats` in an effect). Polled tabs pass `Rows = react.UsePoll(build_rows, perf.POLL_INTERVAL)` to a `StatTable` (`widgets/stat_table.lua`), keeping `build_rows` a plain function so the console dump commands (`vram_dump`, `physics_stats`, `net_stats`, `terrain_stats`, ...) print the same rows. `perf <tab>` opens the window on a tab. `render.stats` counting is only on while the PERF window is open.
- RENDER VIEWS (`addons/debug/lua/autorun/render_3d/render_views.lua`, `gbuffer_view <field|sheet|targets|off>`) shows gbuffer fields, pass debug textures and lighting term switches; the GBUFFER LAYOUT tab shows how fields are packed.
- `GOLUWA_DUMP_SHADERS=1` writes every stitched GLSL stage to `storage/shader_source/<pass name>.<stage ext>` (`.vert .frag .comp .rgen` ...). Each file compiles standalone: `glslang -V --target-env vulkan1.3 file`. Pipelines without `name` fall back to the creating Lua file; same-name variants get a crc suffix.
- `GOLUWA_SHADER_DEBUG=1` compiles every shader with `NonSemantic.Shader.DebugInfo` (source and function info), which Nsight Graphics needs for source-level shader hotspots and nested calls in the flame graph. Shaders are compiled with the SPIR-V optimizer off either way; the cache key includes the flag. Do not combine it with `--vulkan-validate`: spirv-val rejects the debug info of some shaders (a `DebugTypeMember` column past its source line's length).
- `luajit glw ngfx [trace]` reports a Nsight Graphics `.ngfx-gputrace` (by default the newest in `storage/ngfx_traces/`, where `--capture` writes, or `~/Documents/NVIDIA Nsight Graphics`): gpu time of every recorded frame, the traced frame call group by call group with hardware counters, warp samples per pipeline with stall reasons, and the hottest glsl lines of the top pipelines. `--capture="--3d map IA/Quarry"` takes the trace itself: the Nsight `ngfx` command line tool (found next to `ngfx-ui` or set `NGFX_CLI`) launches the game with `--start-with-ngfx-sdk`, and the game starts the trace through the Nsight Graphics SDK (`goluwa/bindings/ngfx.lua`, `StartTrace` on the engine's queue) when `GOLUWA_NGFX_CAPTURE` fires: `--capture-after=<seconds>` (default 15) after the renderer is ready, or `--capture-after=event:<name>` 60 frames after that event. The `ngfx_capture` console command starts one by hand in any game launched that way. A capture takes about 3 minutes. The real-time shader profiler, which produces the warp samples, and the metric set are per architecture options that the tool silently ignores without `--architecture`; it is detected from `nvidia-smi` (`NGFX_ARCHITECTURE` overrides). `--screenshot=out.png` writes the frame. It is built on `goluwa/codecs/ngfx_gputrace.lua` and `goluwa/codecs/ngfx_perfworks.lua`.
- The file is `WRPV` (versions 10 and 11) then sections `{magic 0x1234, is report, is counters, chunk count, size}` of chunks `{magic 0x4321, stored or lz4, sizes}`. The report section is a protobuf; the counter section is a PerfWorks periodic sampler image (`LOPDATA`), evaluated through Nsight's own `libnvperf_grfx_host.so` (`NGFX_NVPERF` overrides), never parsed by hand.
- Gpu time comes from the timestamps in every submitted call list (`{ptimer, next call index}`): two adjacent timestamps time the calls between them, so a row can hold several calls or barriers. Warp samples, counter ranges and timestamps share one ns clock. Warp samples explain why a pipeline is slow, they are not its time.
- Pipelines are named from `storage/shader_source/pipelines/<pid>.tsv`, which the engine writes with `GOLUWA_DUMP_SHADERS=1`. Source lines need `GOLUWA_SHADER_DEBUG=1` in the traced run: the report's shader blobs (spir-v, cubins with a dwarf line table, sass) are lz4 compressed and xored with a keystream that is the same for every trace and Nsight version (2026.4 xors the compressed data, 2026.3 and older compress the xored data). The keystream lives in `storage/ngfx_keystream.bin`; every report extends it from blobs that are spir-v modules in the shader cache (an exact `LZ4_compress_default` port recompresses them), and `luajit glw ngfx --calibrate` captures an 8 MB incompressible shader to cover every blob. A cubin line n is spir-v instruction n - 6, and the module's `DebugLine` maps it to the glsl line, which matches `storage/shader_source/<name>.<stage>`. Ray tracing stages are not code regions of the report: their cubins list functions at absolute addresses (symbol table, `.rela.debug_line`), are matched to the spir-v module of the same stage that fits the line table best, and the driver's traversal code is reported as `ray tracing internal`.
- A warp sample's stall reason n is `STALL_REASONS[n]` in `ngfx_gputrace.lua`, the order of the PCSampler stall metrics in Nsight's Ada GPU Trace config, checked with compute shaders built to stall on barrier, membar, global and shared memory, sin chains and ray queries. Other architectures may order them differently.

# Game speed

- The `time_scale` pvar (`system.SetTimeScale`, `GOLUWA_PVARS="time_scale=0.1"`) scales the game clock: the `dt` of `Update` events, `system.GetFrameTime()` and `system.GetElapsedTime()` all follow it, so physics, animation, timers, particles and effects slow down together. 0 freezes them (`dt` is 0, so code dividing by `dt` is a bug).
- `system.GetUnscaledFrameTime()` and `system.GetUnscaledElapsedTime()` ignore the scale. Anything that is not simulating the world uses them: UI animation, tooltips, debounces, stats and profiling, file watching, HUD fades, camera-independent debug tools. A new feature picks game time for what the world does and real time for what the person at the keyboard sees.
- `system.SetElapsedTime` (tests, blocking waits) moves both clocks.
