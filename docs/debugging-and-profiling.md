# Debugging

When debugging and thinking about why something happens, feel free to do print logging and changing code around temporarily to verify.

- print a table and its contents: `table.print(tbl)`
- print something once per session: `print_once(...)`
- print a traceback to see where something is called from: `debug.trace()`
- print something and force exit: `print(something) os.realexit(0)`

# Device lost

`VK_ERROR_DEVICE_LOST` has no message of its own, the kernel says why. On this nvidia machine `journalctl -k | grep Xid` (`dmesg` is not readable, the journal is): Xid 13 `SKEDCHECK06_REGISTER_COUNT` + `SKEDCHECK16_CTA_THREAD_DIMENSION_ZERO` is a compute launch whose launch descriptor is all zeros, Xid 109 `CTX SWITCH TIMEOUT` is a context the gpu could not preempt, both name the process (`.luajit-wrapped`). `Fence:Wait` used to ignore its result, so the loss showed up at some later call (the validation layer's `vkResetCommandBuffer ... is in use` in `shadow_map.lua` was the first message everyone saw); it asserts now and prints `failed to wait for fence : error_device_lost`.

`GOLUWA_CHECKPOINTS=1` (nvidia, `VK_NV_device_diagnostic_checkpoints`) puts a marker in the command buffers before every named gpu scope, compute dispatch, ray launch, acceleration structure build and before the instrumented command buffer methods (`PipelineBarrier`, `Dispatch`, the copies, `BeginRendering`, with the lua call site, `checkpoints.lua`). When the device is lost the engine prints the markers the queue had reached: the last `stage 0x1` marker is how far the front end got, the last `stage 0x2000` one is the command that had not finished. `test/harnesses/perf/device_lost_loop.sh` loads a scene over and over until a run dies and keeps its log.

What was found (2026-10-20, driver 615.78.08 closed module, RTX 4090, alpine terrain, one run in ten lost it 8-16 s in as Xid 13, Quarry once as Xid 109):

- The command that had not finished is always a `vkCmdTraceRaysKHR`, the biggest ray tracing pipeline launch of the frame: `ddgi_shade` (13824x1600, a ray generation shader of a ray tracing pipeline) and, with `ddgi_shade_ray_generation` off, `reflections_trace` (960x540) instead. Hundreds of identical launches before it were fine.
- At the loss the first dword of that pipeline's shader binding table read `0x6000c002` where it was made as `0x10`, for the one pipeline that failed and nothing else. It follows the table when it is moved in the pool (a canary buffer took its place), a cpu write is ruled out (the page was `mprotect`ed read only, nothing faulted), the driver's handles asked again were unchanged, and it also loses the device with the table in device local memory, so it looks like a consequence of the fault and not its cause.
- It is a matter of timing: 0 losses with 3 ms of cpu wait before every frame (60 runs), with a `vkDeviceWaitIdle` before every frame (30 runs), or with a 64 KiB tail (129 runs) on `ddgi_ray_hits` that was read from the cpu every frame (BAR reads are slow); a full barrier at the start of the shadow or the main command buffer did not help.
- Not it: the scatter ray tracing range (`r_scatter_rt` off), the Lua garbage collector (stopped), the pipeline cache (no cache, no saving), out of bounds writes of the trace pass (explicit bounds check), a host visible shader binding table or hit buffer, double frees in the buffer pool, synchronization validation (`GOLUWA_VALIDATE=1 VK_LAYER_VALIDATE_SYNC=1` runs the layers and the sync checks without exiting on the first message, the one hazard it found was a `load` load op without read access in `Framebuffer:Begin`, fixed). The same Xid 13 / 109 events are in the journal from earlier sessions, before any of this.
- What is left points at the driver or the gpu firmware, none of the above is the cause. Things to try: another driver version, cutting the ray launches of the frame into smaller ones so none of them is the long running one (every cure above leaves the gpu idle between frames, which would fit a context switch in the middle of a launch), and `VK_EXT_device_fault`, which is on now (see below).
- When the device is lost the engine always prints (no env needed, every part guarded by `pcall`, `checkpoints.Report`) the `VK_EXT_device_fault` description, its address infos, and on Linux the `NVRM: Xid` lines of the kernel log of the last two minutes. On the alpine losses the description is empty and there is one address info of type 6 (`instruction_pointer_fault`), precision 0x10: `0xdefefaabb0` for `ddgi_shade` in two different processes, `0xdeff023570` for `reflections_trace` with `ddgi_shade_ray_generation` off. So the gpu stops at the same instruction of the shader of the launch every time, a hang (Xid 109) and not a bad memory access. Also not it: releasing the BLAS pool ranges 30 frames late instead of 4 (still lost in run 2). Cutting the `ddgi_shade` launch into 8 launches of 1728 columns (a launch offset in a push constant, no barrier between them) lost the device in run 4 at the same address `0xdefefaabb0`, so the launch size is not it either; that experiment was dropped. With the Lua garbage collector stopped (`NOGC=1`, the heap grew to 1.5 GiB), with every object an acceleration structure launch uses kept alive on the command buffer (the pipeline and shader binding table, and everything written into a descriptor), and with every deferred release held 60 submissions longer, the device was still lost (runs 14 and 13 of two instances each, 27 and 25 clean runs before). So neither a collected object nor an early `Device:DeferRelease` explains it. What lives at that address could not be found out here: `VK_KHR_pipeline_executable_properties` (`pipelineExecutableInfo` is true) lists no executables for the ray tracing pipelines, and for compute pipelines only statistics (registers, binary size), no machine code, and there is no `nvdisasm`. The address (`0xdefe...`) is far from every buffer the engine makes (their device addresses are `0xc4...`), so it is in the driver's own shader memory. The shader group handles are not code pointers: 32 bytes, the first dword a driver wide shader index (`0x10`, `0x11`, `0x12` for the `ddgi_shade` raygen, hit and miss records, `0x13` for `reflections_trace`), the stack size in the next bytes, and the dword that reads `0x6000c002` at the loss is that index. That fits a launch whose shader lookup, and not a buffer, went wrong.

# Profiling

The profiler uses luajit's statistical profiler and jit.attach to observe trace recording. Options of `PROF.Start(id, opts)`: `frames` (default 300), `shutdown = false` (do not auto shut down after `frames`), `trace_recorder = false` (do not observe trace recording), `skip_frames`. Prefer `PROF.Start(id, {trace_recorder = false, shutdown = false})` and stop it yourself with `PROF.Stop()` then `PROF.Summary(path)`: trace recording distorts the numbers and has segfaulted on shutdown. The profiler only sees Lua CPU time, see `performance.md` for what it misses.

- `_G.PROF.Start("myprofilesession")` is a high level global helper that starts the JIT profiler with sane default arguments. It runs for 300 update frames, stops and prints a text summary, then calls system.ShutDown(0)

- Profile the update loop for 1000 frames, then implicitly shutdown: `luajit glw --2d --background lua "PROF.Start('profilesession1', {frames = 1000}) import('tmp/benchmark_test.lua')"`

- Profile a one-off action and shutdown manually: `luajit glw --2d --background lua "PROF.Start('profilesession2') something_expensive_and_blocking() PROF.Stop() system.ShutDown(0)"`

- The profile capture is saved to `storage/logs/jit_profile_someid.glwp` which can be read in detail, ie `PROF.Summary("storage/logs/jit_profile_someid.glwp", {top_n = 20})`

# Desktop and the PERF window

`goluwa/render2d/ui/desktop.lua` is a small desktop (the keys are bound in `goluwa/main.lua`): hold `c` for one button per program and a free cursor (it hides on release unless keyboard focus is inside a program window), Escape toggles it with a dimmed backdrop and it stays. `desktop.RegisterProgram{Name, Icon, Pinned, Positioned, Create, OnOpen, OnShown, OnHidden}` adds a program, `Create` returns a `Window`. `OnShown` and `OnHidden` get the window when the desktop shows or hides while the program is open. The defaults: a pinned window (`Window{Pinnable = true}` adds a pin button to its header, `Pinned` is the state, `OnPinChanged` the callback; a program's `Pinned` is the starting state) stays on screen in HUD mode when the desktop hides (`Window:SetHud(true)`: no header, ignores the mouse, fits its content), an unpinned one hides and comes back when the desktop shows. A minimized program stays minimized across the desktop hiding and showing: the dock (`widgets/dock.lua`, the taskbar) lists it and is pinned up while the desktop is shown (`Dock:SetPinned`), clicking its item or opening the program from the desktop restores it. The desktop has a menu bar on top (ENGINE > exit, OPTIONS > theme, the theme switcher the editor used to have, and OPTIONS > layout debugger, which flashes an outline on every panel whose layout was recomputed (`ui_debug` component of `Panel.World`)) over the row of program buttons. Programs are Pvars and Perf (`addons/debug`), the UI Gallery (`addons/ui_gallery/lua/autorun/render_2d/gallery_program.lua`), the asset browser (`addons/editor/lua/autorun/render_3d/asset_browser_program.lua`) and the Editor (`addons/editor/lua/autorun/render_3d/editor_program.lua`, an Interactive program: opening it hides the desktop, it keeps the mouse itself, Escape closes it (or leaves play mode)). With `--hot-reload` the desktop opens on the editor.

PERF (`h` toggles it, `render_2d/perf_window.lua`) is a `Tabs` window, each feature adds a tab with `perf.RegisterTab(name, order, view)` (`addons/debug/lua/perf.lua`, `view` is a react component, see ui.md "React style UI"). Only the open tab of a shown window is mounted (closing the window only hides it), so what a tab does on mount and unmount is its collection: the PHYSICS tab enables `physics/stats` in an effect and disables it in the cleanup. A tab that shows polled rows passes `Rows = react.UsePoll(build_rows, perf.POLL_INTERVAL)` to a `StatTable`, `build_rows` stays a plain function so the dump commands print the same rows. `StatTable` (`goluwa/render2d/ui/widgets/stat_table.lua`) is a fixed size panel of rows drawn with the active theme (frame, body font, palette tokens `text`, `text_disabled`, `neutral`, `negative`, `track`, `primary`) (`Rows` is a list of `{label, value, detail, fraction, color}`, a new list is drawn from the next frame on). Tabs: FRAME (frametime graph and the `render` stats group), GPU (the pie of `gpu_timing`), MEMORY (vram by label), RENDER (the other `render_stats` groups), PHYSICS, CULLING, NETWORK, TERRAIN, STARTUP (where the time from opening the engine to a ready scene went, see performance.md "Startup time", `startup_stats` prints it). `perf <tab>` opens the window on a tab (the `PerfTab` event the window listens to). It takes `Columns` for long lists. The tabs' dump commands (`vram_dump`, `physics_stats`, `net_stats`, `terrain_stats`, `dump_*_gpu_culling_stats`) print the same rows or snapshot. `render.stats` counting is on only while the PERF window is open, the `render_stats` fields are registered with `RegisterField` and shown by `render_stats.GetRows()`. The old shader glyph overlay (`f4`) and the vram HUD (`f2`) are gone.

RENDER VIEWS (`addons/debug/lua/autorun/render_3d/render_views.lua`, a desktop program, `gbuffer_view <field|sheet|targets|off>` shows a gbuffer view full screen) inspects what the passes produce, it replaces the old `g` tile overlay. The VIEWS tab is laid out like the asset browser: a search box above a tree (it filters the nodes by name, a match keeps its children and the tree opens up while searching) with three roots, `sheets` (the gbuffer decoded, albedo, alpha, normal, metallic, roughness, ao, specular, transmission, clearcoat, sheen, emissive, depth, velocity, the ones with several fields are folders) `passes` (the debug textures of ambient occlusion, reflections and ssgi) and `lighting` (switches of the lighting that show one term: direct light only, gi only, the screen space shadows, the ddgi probes and the scene they trace, a tile is a switch, Toggle flips it and Fullscreen applies it with the desktop hidden, Escape turns it off again), the views or the fields of the open folder as tiles with a breadcrumb above them (double click a folder to open it), and the selected one on the right: a preview, Fullscreen (and Sheet fullscreen for sheets) buttons, the controls of the sheet (normal has the source, combined, vertex or map, with a reference sphere in the corner, albedo the terrain base color only) and what is known about it (a field's kind, where it is stored, range and readers, a pass's size). All the sheet tiles and the preview are one `gbuffer_inspect` sheet render, the window only asks for it while the tab is drawn, a pass view is drawn from its own texture. Fullscreen hides the desktop and shows the view on screen, Escape leaves it. The window has a pin button (off by default): pinned, it stays on screen in HUD mode when the desktop hides, without its header and tab bar, and keeps rendering its previews. The GBUFFER LAYOUT tab draws how the fields are packed (target, format, channel per cell, free channels, bytes per pixel, clicking a field cell opens it in VIEWS) and below it the raw packed targets as they are stored, click one for it full screen. Menus are added to the desktop with `desktop.RegisterMenu{Text, Items = function returning MenuItems}`.

# Optimizations

- Trace abort reasons like `blacklisted` are caused by other trace abort reasons, it means that it was attempted too many times

- LuaJIT's trace compiler is non deterministic, sometimes you may get unlucky or lucky. Beware of this.

- `error thrown or hook called during recording` may happen because of the profiler itself. jit.attach and jprofile.start. There is no debug.sethook in this engine.

- Sometimes caching is prefered, but sometimes it is not. The luajit does very well with pure numeric arithmetic, so caching may sometimes interfere with that. Sometimes you may think a function needs caching, but the underlying issue might be a trace abort causing the function not to compile properly, this case might benefit from caching, but if the underlying problem was solved, the function might even be faster than the cached variant.
