# Data driven effects

An effect is a plain Lua table in a file that `return`s it: numbers, strings, booleans, lists and tables, never functions or cdata, so `table.to_source` can write it back and an editor can edit it. Behaviour an editor cannot express is a named script in code that the data refers to.

- Colors are `{r, g, b, a}` arrays. Keys that contain `Color`, `EmissiveMultiplier` and `ShapeSize` are turned into `Color`/`Vec3` by `data_files.Realize` (`goluwa/data_files.lua`) when the definition is registered; the registry keeps the pure copy in `Source[name]` (`data_files.New(dir)`: `Read`, `Remember`, `Save`).
- A registry (`damage_types`, `status_effects`, `effects.UpdateClip`, `movesets`) has `Register`/`Update(name, data)` (live, the game plays the edit at once), `Reload(name)` (from file) and `Save(name)` (`table.to_source`, the formatter reflows it). Consumers read the runtime definition, never `Source`.
- Data forms that stand in for functions are compiled in `Register`: damage type `Apply`; status effect `Think` (`Damage = {Base, PerAmount}`, `Type`, `Attributes`, `Spread = {Above, Radius}`, `Gate`, `Force`, `DrainMana`), `Solid` + `SlowSlope` + `AnimationSlope` (speed, animation speed and attacks stop at `Solid`), `AttackFail`, `Wobble = {{frequency, amplitude}, ...}`. A definition may still hold a function for any of these (an edge case); the editor then shows it as non editable.
- Clips (`goluwa/render3d/clips.lua`, jrpg ones in `lua/jrpg/clips/*.lua`): `Loop = true` is an endless clip. A value is a number, a name (a track, or a param `p.name`) or an expression string (`"p.spin + v.time * 0.8"`; `p` params, `v` track values and `time`, `f` in a track, math functions); the expression keys are `EXPRESSION_KEYS` in `clips.lua`, a track may be an expression of `f` and a key's ease an easing name or an expression. Events: `{t, Burst/Debris = ..}`, `{t, Emitter = "name" or {inline properties}, Count, Direction, Inputs, When}`, `{t, Flash = true, Lumen = , Time = , Offset = {x, y, z}, NormalOffset = }`, `{t, Call = "script"}`. `Follow = "script"`, a layer's `Script = "script"` and `Call` name `clips.RegisterScript(name, {Follow, Event, Init, Push, Setup, Update, Remove})`. `clips.Source[name]` is the data as given.
- Other data files: surface overlay `defaults` (`lua/surface_overlays/defaults/<kind>.lua`, `surface_overlays.SetDefaults`; the `glsl` stays in the kind file), emitters (`lua/emitters/<name>.lua`, see Emitters below) and grenade puff styles (`lua/effect_data/grenade_puffs.lua`, `grenade_effects.UpdatePuffs`), the jrpg clips `flash` and `low_health` (their per frame work is a named script).
- Not data yet: the shaders of surface overlays, the procedural parts of `grenade_effects.lua` (streaks, streamers, traces) and `weapon_effects.lua` (the force burst), and `jrpg_status` (built from the status list).

## Effects editor

The `Effects editor` desktop program (`lua/jrpg/effects_editor.lua`, `ctrl+z`/`ctrl+y`, `space` plays) edits damage types, status effects, clips, overlay defaults, gpu emitters and grenade puffs, and lists the clip scripts read only (with the clips that use each). It plays the selected effect on the stage (`lua/jrpg/effects_stage.lua`, "preview on": the local `player` (default), a spawned `npc` of your choice, or a `gizmo` point whose position and up axis are the hit position and normal for bursts, impacts and explosions; entity effects such as statuses, overlays and flashes still land on the player in gizmo mode). The target is made unkillable for the session and its statuses are cleared when the stage changes. The view is free flying (camera preset, exposure day/dusk/night, loop) and applies every edit to the live registry at once; `FILE > save` writes the file back.

The `PREVIEW` panel docked at the bottom of the view (the clip timeline sits above it) holds everything about watching the effect: `Play` (stops what the last play started and plays again from the start, also `space`), `Stop`, `Loop`, `Auto restart`, the stage (`preview on`, npc or gizmo mode), camera, exposure, `Save view`, and for gpu emitters the test inputs (count and the declared inputs, session only). A category's `Play` may return a function that stops what it started (`effects_editor.Stop` calls it and stops the stage drive); one shot particles cannot be taken back. With `Auto restart` on (the default) an applied edit, an undo or a change of a test input queues a restart that runs 0.25 s after the last one (`effects_editor.QueueRestart`, `Tick`), so dragging a slider does not restart every frame; an edit that fails to apply does not restart. The left panel only edits the file: category, name, undo, redo and the properties.

An effect file can carry a `Preview` block that the editor applies when the effect is opened (damage types, status effects, clips and gpu emitters; the runtime ignores it): `Stage` (`player`, `npc` with `Npc`, `gizmo`), `View = {Offset, Pitch, Yaw}` (the camera relative to the stage subject, set with `FILE > save view as preview`) or `Camera`, `Exposure`, `Loop`, `Duration` (play head length), `Params` (what a clip is played with: numbers, strings, colors under keys named color, and the stage tokens `$target`, `$target.health`, `$target.position`, `$chest`, `$ground`, `$normal`, resolved by `effects_stage.ResolveParams`) and `Drive = {Type, Time, ...}` (`effects_drive.lua`: `sweep` moves a point, `blade` swings a base and tip through an arc, feeding the `position`, `base` and `tip` params of a clip or an emitter) with `Release` (seconds a clip fades out after the drive ends). Anything absent leaves the editor's current setting. Only the keys that apply to the category are offered (clips: `Params`, `Drive`, `Release`; gpu emitters: `Drive`; particle shaders: `Emitter`, `Offset`, `ShaderParams`), and `Npc` alone previews on that npc without a `Stage`. Clips played without `Params` get a default set of look params.

- The view flies with `addons/editor/lua/view_camera.lua` (shared with the move editor): drag with the left mouse over the world to look, `wasd` to move, `e`/`q` up and down, shift faster, ctrl slower. The camera dropdown only sets a starting position.
- Rows are built from the data (`lua/data_items.lua`), refined by a schema per category (`lua/jrpg/effects_schema.lua`, shape in `lua/data_schema.lua`): `Fields` by key name or `Parent.Key` (`Parent[]` for list items) give ranges, enums, `Ref` dropdowns (status, damage type, overlay, texture, flipbook, script, easing), descriptions and `Template`/`Keys`/`NewKey` for adding items and keys; `Labels` name list items; `Root.Keys` are the optional top level keys. A `Ref` row gets an arrow button next to its dropdown (`RowButtons`) when the target is another category; opening pushes the current definition on `session.Trail` and a breadcrumb under the toolbar (`Open`, `Back`, `GetTrailLabels`) goes back to any earlier one, while picking from the category or name dropdowns resets the trail. And `data_schema.Check` reports dangling references under the toolbar.
- Lists are `list` property nodes (see [ui.md](ui.md)): arrays of scalars are rows, or chips with `Display = "chips"` in the schema (Names, Adjectives), arrays of tables are group items with a `Labels` summary, and `Display = "table"` with `Columns = {{Text, Key, Min, Max, Options}}` gives a spreadsheet like list (Wobble, track keys through the `Tracks.*` field). A field spec `Sound = true` makes the field a `sound` property (text, play and browse buttons; the editor's `PlaySound` option plays it at the preview stage). Table and group items keep a stable identity across moves. Any structural change rebuilds the rows; a value edit never does (a drag would be cut off).
- History is `lua/data_history.lua` (snapshots, edits within 0.6 s coalesce).
- Clips get a timeline (`lua/jrpg/clip_edit.lua`: rows for each keyed track and the events, add by clicking, drag, delete); the selected key's fields show at the top of the rows. Expression tracks have no keys. Expression strings are plain text fields: a syntax error shows in the status line and leaves the registered clip as it was.
- Reload of the code behind a `Script` goes through `--hot-reload`, which re-runs the module that registers it.

## Emitters

An emitter file (`lua/emitters/<name>.lua`, loaded by `lua/emitters.lua`) is a plain table of `particle_emitter_gpu` properties (colors as arrays, see `data_files.Realize`). Code asks for it by name: `emitters.Get(name, inputs)` returns a realized copy to hand to `vfx.CreateEmitter`, `emitters.Burst(name, position, direction, count, inputs)` defines and fires it as a burst, and `emitters.DefineBurst(name, inputs)` defines it (and returns the burst key). The loading, inputs and burst keys are `goluwa/render3d/emitter_data.lua` (a registry by name, so a clip layer or event can name an emitter file, or give the properties inline, which is registered under the clip's name). Values a caller varies are declared as `Inputs = {Strength = {Default = 3, Min = 0.1, Max = 12, Targets = {{"Speed", "set_max"}}}}` in the file (a color input has `DefaultColor` instead and only sets the rgb of its target, keeping the target's alpha): each target is a property and a mode (`set`, `scale`, `add`, and `set_min`, `set_max` for a property that is a range; a color property takes `set`, `set_first` and `set_last`, which tint a whole `Color` curve, its first key or its last), a value the caller does not pass falls back to `Default`, and a passed name that is not declared is an error. Do not keep a numeric target in the file, the default replaces it; a color target stays in the file for its alpha. A burst is fixed when it is defined, so every distinct input set is its own gpu emitter (`emitter_data.MAX_VARIANTS` logs a warning): round the values you pass. The editor's `test inputs` group (count and one control per input, session only) feeds the play button. `emitters.Update` redefines a burst that is already defined, so editor changes show on the next burst. The editor's `gpu emitters` category derives its ranges and enums from the property list in `particle_emitter.lua`; a property that accepts a range (see particles.md) shows a wand button that turns the number into a min and a max, and a reset button back; play bursts a one shot emitter and sweeps a `RatePerMeter` emitter along a line. A status effect or damage type `Particles` block can name a base emitter, `Particles = {Emitter = "frozen_snow"}`: `effects.GetParticles(definition)` returns the values, with the damage type's default particle values underneath, the emitter file over those, and the block's own keys on top (nested tables such as `ShaderParams` merge by key); read particle values through it, never from `definition.Particles` directly. In the editor `Emitter` is a dropdown with a button that opens the file. Emitter data is checked against the emitter property lists whenever it is built (`particle_emitter.CheckProperties`: unknown names, a non integer or out of range `MaxParticles`, a wrong enum, boolean, number or range), so a bad edit shows in the editor's status line and the registry keeps the last good data instead of failing later in entity creation. Emitter files are sparse: a property that equals the component default (`particle_emitter.GetDefault`) is not stored, and a missing property means that default (`emitter_data` falls back to it for input targets too). The editor shows every property of the category, grouped like `Material` does it (`StartCategory`, the fourth entry of the property lists: Emission, Shape, Motion, Look, Collision), with the effective value; a row that is not in the file is at its default, a changed row has the primary color bar and Reset in its right click menu (a range or curve row, whose default is not a single value, gets a Reset to the default context action that removes the key)., and `data_items.StripDefaults` drops values that equal their default on load and on every apply. A schema opts in with `Root.Defaults` (key to default value) and `Root.Groups` (`{Name, Keys}` in display order); keys whose presence means something (`Inputs`, `Preview`, `Think`, a shader's `Spawn`) are optional: every group that has `Keys` or a `NewKey` in the schema ends with a `+` row (a `type = "add"` node, `make_add_node`) whose context menu lists the keys that are not there yet, and a present optional key is removed from its own right click menu (`Remove`, a group's header menu for tables and lists). Add a new look as a file, not as a table inside the code that uses it. These are gpu emitters (translucent, optionally with a particle shader); cpu emitters (solid meshes) have no shaders and are only edited inline, as a damage type's `Debris` block.

## Particle shaders

- A status effect or damage type `Particles` block can pick a `Shader` (`snow`, `glow`, your own): the emitter keeps the common properties (rate, shape, lifetime, gravity, size, `Lit`, colors) and the shader adds its own `ShaderParams` (shown as rows built from the shader's declaration, with Min/Max and descriptions; choosing a shader fills `ShaderParams` with its defaults). A `texture` param is a dropdown of the vfx flipbooks and procedural textures (`vfx.RegisterTexture` adds one, for example `snowflake`); a flipbook plays its frames at the emitter's `FlipbookFps` (the `sprite` shader draws one).
- The `particle shaders` category edits the shader files in `addons/game/lua/particle_shaders/`: `Sprite`, the `Params` list (a color param needs a name ending in Color to get a picker) and `Source`, the glsl with the `spawn`, `update`, `visibility` and `shade` functions (see particles.md), as a code property. Every change that touches the glsl or the param layout recompiles the particle compute shader (a second or two); an error is shown in the status line and in the code editor, the previous version keeps running, and Apply on a bad edit does not register it. File > duplicate copies a shader as `name_2`; built in files are ordinary files, so duplicate before experimenting. Play runs the gpu emitter named by the shader file's `Preview.Emitter` (`glow_preview`, `puff_preview`, `sprite_preview`, and `shader_preview`, a slow falling box of flakes, which is also the fallback when a shader has no preview block) with `Shader` forced to the shader being edited and `ShaderParams` set to the shader's defaults plus `Preview.ShaderParams`, placed `Preview.Offset` metres from the stage chest for `Preview.Duration` seconds (`effects.PlayParticleShader`); edit the motion in that emitter file. A status effect with a shader shows on the target when played.
- Shaders are not limited by properties: anything a particle can do in glsl works, but a shader is still one pool shared by every gpu emitter (`MAX_EMITTERS`, a pool of 65536) and its params are limited to 16 floats.
