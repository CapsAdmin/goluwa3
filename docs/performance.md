# Performance measurement and optimization

Re-measure before trusting any number; run-to-run variance is large (see below).

## Measuring correctly

- Never benchmark with `--vulkan-validate` (validation roughly triples CPU frame time). Always pass `--background`. A stray engine process doubles GPU numbers: check `pgrep -af "[l]uajit glw"` first.
- The JIT profiler (`PROF`, see debugging-and-profiling.md) only samples Lua CPU time. Time blocked in fence waits does not show up, so "slow frame but idle profile" means a GPU sync. It also pins C/FFI time on the wrong line, so confirm a hotspot with direct timing before optimizing. Never start `PROF` twice in one run.
- Time with `system.GetTime()`, never `os.clock()` (CPU time over all threads).
- Swapchain acquire / frame fence wait > 0 means GPU bound. About 0 with a bimodal frame-time histogram means a mid-frame CPU-GPU drain. The first `render.SubmitAndWait` of a frame blocks until the GPU finishes earlier frames, so its duration is about the GPU frame time.
- `render.BeginFrame` records render3d inside it (`target:BeginFrame` fires `PreRenderPass`); to time the GPU wait wrap `Wait` on the metatable `__index` of a live fence, not the imported template.
- `goluwa/render/gpu_timing.lua` records GPU timestamps per EasyPipeline pass plus `gpu_frame`. `SetInfo(scope, key, value)` lets a pass attach what it worked on (pixels, rays, ...); `BeginCapture`/`EndCapture` average scopes over the frames between. Shadow maps use their own command buffers and are not in these scopes. `GetMilliseconds(name)` adds the scope from every command buffer recorded in the newest frame that has it (several point shadow maps share one name), never from older frames still in flight; `gpu_frame` is instead the time the GPU was busy with the frame: the union of its graphics parts and its compute segment (with async compute the frame is several submissions; gaps where the GPU waited for the CPU to submit the next part are not counted, overlapping graphics and compute count once); `gpu_compute` is the compute queue's segment, which overlaps `gpu_frame`, and passes on it run slower than alone because they share the SMs; `GetRawMilliseconds` is the last value read back; `gpu_total` is `gpu_frame` plus the shadow scopes. `BeginCapture` averages `GetMilliseconds` per frame. Compare async compute with `GOLUWA_ASYNC_COMPUTE=0` by `gpu_frame` or wall time per frame on a GPU-bound view, never by the pass scopes.
- Process-to-process variance is 10-20% for identical code (ray query passes come in a fast and a slow state; big scenes land in "heavy" or "light" states by translucent draw count). Compare variants alternating inside one process (put a throwaway first run before the real ones) or take medians over several processes, and check draws per frame to tell which state a run is in. Numbers before `BVHSceneReady` are junk.
- Env vars set to `""` are truthy in Lua. Build-time pvars (`r_rt_hit_*`, `reflection_reorder`) must be set through `GOLUWA_PVARS` (`goluwa/cli/pvars.lua`), see AGENTS.md.
- A change to shared GLSL makes the driver recompile every pipeline using it on the next run (see Caches), run twice.

## Screenshot A/B

Screenshot A/B: freeze time-driven things (`system.SetElapsedTime` from a high priority Update listener), lock exposure with `ExposureLock`, compare with ImageMagick `compare -metric PSNR`. Identical runs in one process give ~43 dB, across processes ~38 dB; below ~35 dB look at an amplified difference. Banding in smooth gradients is often a viewer artifact, crop at full resolution before chasing it.

## Benchmarks

- `luajit glw bench` lists `test/benchmarks/*.lua`; `luajit glw bench <name part|all>` runs those whose first line is `-- glw: <flags>`, one process each (`goluwa/cli/bench.lua`). A benchmark must end its own process (`--cli` scripts need `os.exit(0)`).
- `goluwa/render3d/frame_benchmark.lua` `Run{...}` is the scene benchmark harness: waits for `BVHSceneReady`, nothing loading and a stable bvh version, then measures phases (static, spin, move) and prints frame stats, allocation rate, gpu_frame and top gpu scopes. New scene benchmarks should use it. Each phase records draws per frame (needs `render.stats = true`); a different count than the baseline prints "scene in a different state".
- `goluwa/benchmark_results.lua`: results with a noise value are written to `storage/logs/bench/<name>/latest.json`; `--baseline` also saves `baseline.json`; later runs print `[COMPARE]` lines for moves beyond twice the combined noise. `--no-compare` skips it. Noise floors are `RUN_TO_RUN_NOISE` in frame_benchmark.lua.
- Micro benchmarks: `goluwa/benchmark.lua` (`Run`, `Compare` interleaved with paired ratio, `Finish`).

## LuaJIT

- Trace aborts and what to do about them: jit-trace-aborts.md.
- Fewer live locals, no alias locals, direct field access in hot code. Judge by trace abort counts (`-jv`, `jit.attach` logger), not one timing: you need 6+ alternating runs to see anything under 15%.
- Objects of one class must share one hash layout. A compiled field read (`body.Position`) guards on the hash node the key was found in (`HREFK`), and instances whose keys were inserted in another order or set (config applied through `pairs()`, lazily created cache fields) fail the guard and get a side trace each, at every read site: the physics bodies produced tens of thousands of live traces, the trace table overflowed (65535) and the whole JIT cache was flushed and recompiled every few seconds (20-45% of step time in the compiler, `R` in jit.log, `[JITINFO]` of the stress benchmark counts live traces). `META.FieldLayout = {...}` on an `objects` template lists every field an instance may ever get beyond its `GetSet` properties; `CreateObject` inserts them all in one order before anything else (fields without a default are inserted and cleared again, which keeps their node). A field assigned later that is not in the list rehashes that instance into its own layout, so add new instance fields to the list.
- "NYI: register coalescing too complex" only aborts side traces. At a side exit ALL locals in scope (including params and inlined caller frames, even dead ones) are snapshot values. Fixes: wrap temporaries in `do ... end`, `param = nil` after last use, tail calls, keep long-lived scalars in a plain scratch table (not Vec3, which is float32), split fused loops, hoist loop-invariant calls, guarantee number fields so `or 0` branches vanish. Check it is the real bottleneck first.
- No nested row loops in hot solver code: LuaJIT unrolls short inner loops into the outer trace until "too many spill slots" and blacklists the loop (bimodal step times). Use one flat task list.
- `loopunroll` is set in `goluwa/jit/options.lua` (`SetOptimized`); re-sweep it on a steady-state workload if physics code changes a lot (too large makes traces huge).
- Type punning through cdata is not safe under the JIT: its alias analysis treats accesses of different types as independent, so writing bytes through a `uint8_t *` and reading the same memory back as `int16_t` or `float` in one trace returns stale values (the interpreter gets it right, so it only shows once compiled). Assemble numbers with arithmetic, or read through a typed pointer from memory nothing writes in that trace.
- Trace aborts reported as `blacklisted` are caused by earlier abort reasons. Trace compilation is non deterministic. Caching is not always a win: a function that looks slow may just be a trace abort, fix that instead. `error thrown or hook called during recording` can come from the profiler itself.

## Lua heap and GC

- `objects.CheckRemovedObjects` drains `objects.remove_these` on the next Update: a leak census in the same frame as `Remove()` reports everything removed. Wait ~10 frames and run `collectgarbage` several times. Compare heaps after full GCs only.
- `assets.GetModel(path)` caches the model forever; only use it for procedural `.lua` models (`model_loader.model_loads:Forget(path)` drops one). `Texture.New{path = ...}` pins the decoded texture in `texture_cache` by config key: give previews a unique `cache_key` and `Remove()` them, and never remove a texture whose `image` is `Texture.GetFallback().image`.
- Frame hitches of 90+ ms inside arbitrary passes are usually the collector. Fewer allocations make cycles rarer; large cpu-side copies of uploaded data (vertex tables, hulls) make them costlier. The engine sets no GC pause during play (`collectgarbage("setpause", ...)` trades memory for hitches); during scene load `r_loading_gc_pause` (`goluwa/render3d/startup_ready.lua`) is raised and restored when the scene is ready. A new pause only applies when a cycle ends, so restoring it must be followed by `collectgarbage("restart")`, otherwise the heap keeps growing to the old threshold (10x the heap at the last collection).
- Collector time is bursty, not smooth: with millions of live objects it idles for about half of each cycle and sweeps for the other half at up to 20% of the frame, 100+ ms inside single frames, and its cost follows the number of dead objects (small tables, Vec3s, hit records), not their bytes. Read `log.gc()` per frame (diff the `ns` of every state around an Update) to tell a collector hitch from a slow frame; a large `ffi.new` (an animated model's per instance vertex copy is ~1.7 MB) adds debt the collector pays in the same frame.
- `Remove()` what you create. Objects dropped without it are found by the collector and finalized in bulk (a GC step of hundreds of ms after a load), and Vulkan buffers keep their memory until then. Removing many objects of one type is quadratic (`Instances` is searched and shifted per removal).
- `Polygon3D:GetVertices()` unpacks a packed (threaded decoder) mesh into one table plus three cdata per vertex for good; code that only needs positions reads `GetVertexCount`/`GetVertexPosition`, which work on packed and unpacked meshes.
- GC cost grows with the number of live objects, not their bytes: millions of small tables and cdata (per-vertex tables, Vec3 fields) make every cycle and its atomic step slow even when big ffi arrays dominate the bytes. `log.heap()` of the jit.log fork shows both and who holds them.
- Vulkan memory: mesh buffers up to 4 MiB are sub-allocated from 64 MiB blocks (`goluwa/render/vulkan/internal/buffer_pool.lua`) because one `vkAllocateMemory` per buffer dominates model loading. Meshes nothing else shares take `Polygon3D:UploadVertexArray(..., mode)` `"owned"` (no dedupe key string) or `"host"` (cpu-only, no gpu buffers).

## Where GPU/CPU time goes (general rules)

- GPU: DDGI, lighting, translucent/glass and ray traced reflections dominate; they are covered in render3d-lighting.md. Per-light and per-ray early-outs matter more than anything else in shaders: reject cheap cases (brightness, facing away, occlusion map) before the expensive ones (shadow map, screen-space march, ray queries), and march/trace last.
- Ray generation shaders with thread reordering (`ray_reorder`, `ray_generation` in `easy_pipeline_compute.lua`, see vulkan-raytrace.md) beat the same code as ray queries in compute for divergent hit shading.
- CPU draw submission: bind a pipeline once and rebind only descriptors per batch; read culling/soup data from FFI arrays, not scattered Lua tables; write batch records only when their source changed (`BatchTable` tracks material versions via `property_version`, wind via `animation_version`); cache per-material keys by `property_version`; never build strings per draw.
- Versioned properties (Material, `objects.lua`) stamp their object with a new `property_version`; call `Material:Touch()` after changing a vector or color in place.
- Big-scene CPU: key caches on a version counter that only moves when the data does (e.g. `emitter_version` (`render3d/scene/emitters.lua`)), not on a broad version like `soup_version`.
- `r_feature_culling` (gpu_culling.lua) switches off visibility culling to get the worst case: every visible-flagged visual drawn every frame. LOD selection is separate (`lod_level 0` for the most detailed case).
- Terrain/scatter streaming: bvh proxies are rays-only host copies at a coarser stride; bake height once per chunk into a field texture; share one index buffer per tile shape.

## Texture memory

Texture VRAM is usually most of a big map's footprint (the fixed render targets, GI and buffers are about 3 GiB). Measure with `vulkan_memory.Instances` grouped by `debug_name` (`vram_dump`), and compare `nvidia-smi` of the process, not the tracked total alone.

- `r_max_texture_size` drops the mips of compressed texture files above that size at upload (0 is no limit). It applies to `path` textures only, never to `decoded` ones, so conversions (`texture_convert`) always see the full image.
- Streaming (`Texture.New{stream = true}`, `r_texture_streaming`, source 2 materials and their converted textures ask for it): the texture keeps only the mips up to `r_texture_stream_base_size` resident and sets `texture.stream`. `render3d/texture_streaming.lua` decides what each needs and `Texture:RequestStreamLevel` / `UploadStreamLevel` swap the image (the view changes through `TextureViewChanged`, so bindless descriptors follow; the sampler `MaxLod` is open because the mip count changes).
- Demand is the texels needed per pixel, not visibility (culling is on the GPU): every pass over `Visual.Instances` (a slice per frame) takes the nearest distance to a visual's bounds, `pixels per meter = height / (2 d tan(fov / 2))`, divided by the uv density of its polygon (sampled from the packed vertices) and the material's uv scale. Direction is ignored on purpose, so turning never pops. `r_texture_stream_budget` (MiB) caps what stays resident: upgrades that do not fit make the textures needing the least cut back, nothing is cut below the budget.
- Never block on a stream: decode runs on workers (`codec.DecodeFileAsync` reads the byte range itself, also from an archive entry, `vfs.GetReadLocation`), the main thread only creates the image, copies into a staging buffer and submits without waiting. The upload's final barrier makes the data visible to everything submitted later, so the swap happens at once; `Texture.PollStreamUploads` retires the fences. Main thread work per request or upload must stay around a millisecond: reading a 20 MB archive file on the main thread cost 50 ms and showed as hitches on every teleport.
- Test it with a harness that teleports a `View` to random visuals and prints frame times and `texture.stream` states, with the streamer on and off (`r_texture_streaming=0`) so hitches that are not the streamer's can be told apart.

## Caches and the slow first start

1. `storage/cache/shaders/<crc32>_<length>.spv` (`shader_module.lua`): header, SPIR-V, then the GLSL it came from; a hit needs identical GLSL. Misses log `[shader] glslang compiled ...` (GLSL to SPIR-V only; the driver step logs `[pipeline] the driver compiled ...`). glslang is fast, this is not the slow part.
2. `storage/cache/vulkan_pipeline_cache.bin`: saved when a pipeline job finishes (at most every 2 s while others are still compiling, and at once when none are), so a `--one-frame` run keeps what finished during its frame. The driver never evicts entries, so the file grows with every shader edit; the whole file is read and handed to the driver at startup and rewritten on every save. Deleting it costs one cold start. Tests use their own `vulkan_pipeline_cache_test.bin` (`render.Initialize{pipeline_cache_name = ...}` in `test/test_render.lua`).
3. The NVIDIA driver cache (`~/.cache/nvidia/GLCache`, `~/.nv/ComputeCache`) is what makes a cold start take minutes: the driver compiles the huge lighting fragment shaders serially. Any edit of shared GLSL (gbuffer layout, lighting, surface features) costs a slow start once. `[pipeline] the driver compiled ...` is logged for pipelines taking 50 ms or more. Graphics, compute and ray tracing pipelines are created on `thread_pool` workers (`PipelineCache:RunCreate`) and waited for at first bind or dispatch (`Wait`; the ray tracing one also builds its shader binding table there), but the driver does not scale across threads; splitting big shaders is the remaining lever. The driver inlines every GLSL function at every call site, so a big function called from several places multiplies the compile time (the terrain layer sample was inlined four times and cost ~45 s of the gbuffer compile): compute it once into a global in `main` and let the getters read the global. The `ms` in `[pipeline]` lines is the wall time of the create call on its worker.

Cold start: `rm -rf ~/.cache/nvidia/GLCache ~/.nv/ComputeCache storage/cache/shaders storage/cache/vulkan_pipeline_cache.bin`. If something renders wrong only with one machine's cache state, clear the driver cache first: it is the one cache the engine cannot validate.

## Startup time

- `goluwa/startup.lua` is imported first in `main.lua`. `startup.Begin(name)`/`End(name)` record wall-clock spans; `local t = startup.Start() ... startup.Add(name, t)` accumulates totals for repeated work (`group: item` names group in the tab). `Add` is a no-op once the scene is ready. Name tasks (`task:SetName`) or they appear as `task: unknown`.
- "Ready" is decided by `goluwa/render3d/startup_ready.lua`: bvh built, nothing loading or spawning, `instances.version` unchanged for 1.5 s (not counted in the reported time). The version counts added, removed and changed instances, not moving ones: an animated object (the player's held gear) would otherwise keep the scene from ever being ready. It does not see GI/exposure convergence. `GOLUWA_STARTUP_REPORT=1` prints the report; the STARTUP tab of PERF draws it.
- Measure by loading a map from a script, exiting when `startup.IsReady()` and printing `startup.GetReport()`. Noise is 0.3-0.5 s, compare 2-4 runs. The main thread is busy for the whole load, so only less work or more threads help; throttling frames while loading does not.
- Load levers in place: raised GC pause while loading; zip entries inflated on the worker pool (`vfs.Prefetch`, zip context only); terrain builds more tiles per frame and enters the bvh immediately while it holds the scene load; model decoders running on workers (below).
- Threaded model decoders: `model_loader.AddThreadedDecoder(id, {Gather, job, Finish})` (mdl and cgf use it). `Gather` runs on the main thread (workers have no vfs mounts) and returns the job input and size; `job` is the worker source returning a meta table plus a blob of packed vertices/indices (`packed_mesh.PackPolygon`); `Finish` runs on the main thread, makes materials/meshes and unpacks (`packed_mesh.Unpack`). A polygon made this way has empty `Vertices` until `GetVertices()`: code that reads a visual's polygon tables must unpack first. With tasks disabled (map loads) `Await` blocks, so models load one after another unless their jobs already run: `model_loader.Preload(paths)` starts the jobs of the next 48 paths (vfs readable, `Gather(path, path)`) ahead of the loads that consume them. Source 2 models (`vmdl_c`, `vmesh_c`) decode their vertex buffers on workers (`source2/mesh_pack.lua`, no vfs and no loader imports, the loader imports it as the job).
- `goluwa/thread_pool.lua`: see animation-and-source.md "Threaded codecs".
