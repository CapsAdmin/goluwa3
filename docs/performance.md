# Performance measurement and optimization

Lessons from past profiling sessions. Timings in here are rough snapshots; re-measure before relying on them. Use `luajit glw bench` (below) rather than ad hoc scripts when a benchmark exists for the scene.

## Measuring correctly

- Vulkan validation is only on with `--validate` (and in tests). Never benchmark with it, it roughly triples CPU frame time. Always pass `--background`.
- The JIT profiler (`PROF`) only samples Lua CPU time. Time blocked in `vkWaitForFences` does not show up, so "slow frame but the profile looks idle" means a GPU sync. Time `render.SubmitAndWait` and swapchain acquire with `system.GetTime()`. It also pins C/FFI time on the trace's anchor line (a map-load profile blamed one line for 67% that was really 0.6 s), so confirm a hotspot with direct timing before optimizing. Never start `PROF` twice in one run. See debugging-and-profiling.md for how to start it.
- Acquire/frame-fence wait > 0 means GPU bound. About 0 with a bimodal frame-time histogram means a mid-frame CPU-GPU drain.
- `render.BeginFrame` is not just the fence wait: render3d records everything inside it (`target:BeginFrame` fires `PreRenderPass`). To measure the GPU wait, wrap `Wait` on `getmetatable(render.target.in_flight_fences[1]).__index` and GetNextImage/Present on the swapchain; patching the imported Fence template does nothing to live instances.
- `gpu_timing.SetInfo(scope, key, value)` lets a pass say what it worked on (compute passes record `pixels` themselves, ddgi_trace/ddgi_shade `rays`, `dispatched`, `updating`, `mask`, the translucent passes `store_slots`, `cpu_draws`, `components`), `BeginCapture` / `EndCapture` average scopes and the registered groups over the frames in between and hand back the info. `test/harnesses/ddgi/esther_gpu_run.sh label "pvar=value ..."` is that for the esther cave view (about 30 s a run, the measurement itself 6 s after the scene is ready).
- `goluwa/render/gpu_timing.lua` records GPU timestamps per EasyPipeline pass plus `gpu_frame`; per-frame values are in the `last_ms` upvalue of `GetRawMilliseconds` (use `debug.getupvalue`). Shadow maps record into their own command buffers and are not in these scopes. The first `render.SubmitAndWait` of a frame blocks until the GPU finishes earlier frames, so its duration is about the GPU frame time (terrain bakes "looking slow" were really this).
- Use `system.GetTime()` for timers, never `os.clock()` (CPU time over all threads).
- Process-to-process variance is large (the ray query passes ocean/reflections/ddgi_shade come in a fast and a slow state for identical code, 5-12 ms for ddgi_shade) and about half the runs on a big scene land in a "heavy" state (more translucent draws). Compare modes inside one process (the first mode runs slower, put a throwaway `base` first), or take medians of several processes, and check draws per frame to tell which state a run is in. Before BVHSceneReady the numbers are junk (rt_build and soup_expand are huge).
- A stray engine run in the background doubles GPU numbers: check `pgrep -af "[l]uajit glw"` before measuring.
- Env vars set to "" are truthy in Lua.

## Benchmarks

`luajit glw bench` lists `test/benchmarks/*.lua`; `luajit glw bench <name part|all>` runs the ones whose first line is `-- glw: <flags>` (e.g. `--3d`, `--cli`, `--2d --physics`), one process each, and prints a pass/fail summary. A benchmark must end the process itself (`--cli` scripts need `os.exit(0)`).

- `goluwa/render3d/frame_benchmark.lua`: `frame_benchmark.Run{name, load, view, fov, phases, warmup, lead_in, measure, done}` waits for BVHSceneReady, nothing loading and 3 s of stable bvh version, then per phase (static, spin deg/s, move m/s out and back) prints avg/p50/p95/p99/max, allocation MB/s, gpu_frame, shadows and the top gpu scopes. Phases may have `enter(phase)` and `ready()`. New scene benchmarks should use it.
- Every benchmark ends with `benchmark_results` (`goluwa/benchmark_results.lua`): numbers with a noise value go to `storage/logs/bench/<name>/latest.json`, `glw bench <name> --baseline` also saves `baseline.json`, and each run prints `[COMPARE]` lines against the baseline (else the previous run) for numbers that moved by more than twice the combined noise (min 2%). `--no-compare` skips it. The noise floors are `RUN_TO_RUN_NOISE` in frame_benchmark.lua (frame 4%, p95 8%, gpu 5%, one gpu pass 12%): identical code in two processes really differs that much.
- State fingerprint: each phase records draw calls per frame (needs `render.stats = true`, the PERF window sets it while it is open). A different draws/frame than the baseline prints "scene in a different state, timings not comparable".
- Micro benchmarks: `benchmark.Run(name, func, {time, warmup, max_time})`, `benchmark.Compare(name, {{name, func}, ...})` (interleaved, paired ratio), `benchmark.Finish(name)`. Test: test/tests/benchmark.lua.
- Existing: gm_construct_frames, gm_construct_shadows, gm_construct_animation, gm_construct_m3_frames (the heavy map, phases with `r_feature_culling` on and off, see below), lights_stress (synthetic rooms), crysis_beach, physics_stress, physics_map_stack, physics_synthetic_map. gm_construct_frames shows a ~42 ms frame at +3.3 s in its first phase (probably the pipeline cache save, unchecked).

## Screenshot A/B

`test/harnesses/go/run.lua` is the protocol: time-driven things (water) must be frozen with `system.SetElapsedTime(1000 + frame/60)` from a priority-1000 Update listener, restarted per mode so screenshots line up; lock exposure with `ExposureLock` on the View (EV from `r_exposure_info`); compare with ImageMagick `compare -metric PSNR`. The noise floor is about 43 dB between identical runs in one process and 38-39 dB across processes; below ~35 dB look at an amplified diff (`magick a b -compose difference -composite -evaluate Multiply 8`).

- Temporary shader experiments: add an int mode to the pass uniform block set from a global and branch on it, bisect, then remove it before finishing. Early-exit shader variants measured across separate runs were unreliable (the first run after a shader edit gave wrong numbers).
- Do not rewrite a file with `open(p,'w').write(open(p).read())` in a python edit script, it truncates first.
- Banding in smooth gradients (mirror reflections of sky) can be a viewer artifact: crop at full resolution (`magick in.png -crop WxH+X+Y`) before chasing it. The png encoder round-trips exactly and the blit dithers, don't re-audit them. Hard-edged geometric patterns are real.

## LuaJIT

- Fewer live locals, no alias locals (`local x = phys.obj`), direct field access in hot code. Judge by the abort count (`jit.attach` logger, `-jv`), not one timing: a single run can be a lucky or unlucky JIT state, run-to-run variance is +-15-20%, and you need 6+ alternating runs to see anything under 15%.
- "NYI: register coalescing too complex" only aborts side traces. At a side exit ALL locals active in scope (params and inlined caller frames too) are snapshot values, even dead ones. Free fixes: wrap temporaries in `do ... end`, `param = nil` for dead params right after the last use, tail calls (`return f(...)`), keep long-lived scalars in a plain scratch table (not Vec3, which is float32), split one fused loop in two, hoist loop-invariant calls out of nested loops, guarantee fields are numbers so `or 0` branches go away. Hoisting scalars into locals made it worse. Cutting coalescing aborts ~96% in the physics solver did not make the step faster, so check it is the actual bottleneck first.
- No nested row loops in hot solver code: LuaJIT unrolls short inner loops into the outer trace until "too many spill slots" and blacklists the loop (a bimodal 7 vs 67 ms step). `loopunroll=8` hid it but slowed everything else; the fix was one flat task list.
- `loopunroll` in `goluwa/jit/options.lua` `SetOptimized` is 40 (was 15). A sweep on the centrifuge scene gave 15: 43 ms, 40: 26, 60: 29-33, 120: 27, 200: 42 (traces too big). Measure steady state only, short runs are dominated by compile time. Re-sweep if the physics code changes a lot.

## Lua heap

- `objects.CheckRemovedObjects` drains `objects.remove_these` on the next Update: a census in the same frame as `Remove()` shows everything removed as leaked. Wait ~10 frames and `collectgarbage` a few times. The live heap after mounting gmod is ~350 MB and the default GC pause swings it 450-1300 MB, compare after full GCs.
- `assets.GetModel(path)` loads the model into `assets.cache` forever, only use it for procedural `.lua` models; `model_loader.model_loads:Forget(path)` drops one. `Texture.New{path = ...}` pins the decoded texture in `texture_cache` by config key: give previews a unique `cache_key` and `Remove()` them, never remove a texture whose `image` is `Texture.GetFallback().image`. `test/harnesses/ab_browser/census.lua` does a heap census by shape.

## What cost what

Findings from the Esther / Quarry / gm_construct / Beach optimization passes (2026-09/10).

- DDGI is the GPU bottleneck on most scenes. The wins were: tracing visibility rays only for probes with blend weight >= 0.02 (plus a contribution-share rule, see render3d-lighting.md), resolving at half resolution with a depth/normal weighted upsample (`ddgi.GetScreenSampleGLSL`), retracing settled disabled probes about once in 8 frames, dispatching ddgi_shade with probes on x so a warp traces the same ray from neighbouring probes, and `Opaque|CullBackFacing` ray flags for the visibility queries. ddgi_shade cost was dominated by random L2 misses in the triangle fetch and by the 8 visibility ray queries per sample.
- Lights: skip screen space shadows for lights under 0.002 of white, do not shade lights under 0.0002 at all, trace dim lights in reflection hit shading with a probability and weight 1/p. The world light grid (`light_grid.lua`) removed the per-light loop overhead (126 lights that reach nothing cost the same as 0 lights); DDGI samples 2 lights per hit instead of tracing all of them. BSP lights have huge ranges on purpose and are used as-is, so range culling culls nothing there; only the first 256 (`MAX_LIGHTS`) reach the shaders.
- Light loop order (2026-10-17, synthetic rooms from `test/benchmarks/lights_stress.lua`, 256 point lights, range 100 m so every 2 m cell lists all 256): the grid build is 0.05 ms and not the cost, the `lighting` pass is (0.45 ms with no lights, 2.0 ms at range 12 m, 8.4 ms at 100 m). The per light work in `surface_lighting.lua` now rejects early in this order: brightness, lights behind the surface (`dot(s.N, L) <= 0` unless a feature's `lit_from_behind` expression says it still adds something, transmission and clearcoat do), then the coarse occlusion map fetch (exits before the point shadow map and the screen march), and the direction normalize only happens in the branches that read it. 8.4 to 7.3 ms at range 100 m (15.9 to 14.0 ms frame), 2.0 to 1.9 ms at 12 m, run to run noise on the `lighting` pass is about 5 to 15 percent (one process gave 6.0 ms for the same code) so compare inside one process. Pruning the grid by contribution is capped by the specular peak term in `brightest` (up to 800x for a mirror smooth surface), a grid cut that keeps it exact is useless and one that drops it changes highlights of far dim lights on smooth surfaces. Upper bound measured with `Range = 0` (the illuminance based `GetEffectiveRange`): `lighting` 6.0 to 3.6 ms, 61 lights per cell instead of 254.
- Froxel fog: skip froxels beyond the farthest view depth per tile (indoor scenes only). A froxel behind a surface is lit at the surface (`froxel_point` clamp) but its density and air must come from the point at the slice depth along the ray, otherwise a leaf at ground height fills the column behind it with ground fog and filtering leaks it into neighbouring sky columns. A bilateral lookup, own-texel history and clamp-validity fallbacks were all tried and unnecessary, do not rebuild them.
- Ambient occlusion: each half-res AO texel stands for the pixel at the top left of its 2x2, keep that pixel's view depth, and blur with a depth/normal weighted 4x4 upsample (no normal weight for foliage); the old full-res 5x5 bilinear blur was both blurry and 3-4x slower.
- Scatter: one workgroup per triangle in `scatter_tiles` (one invocation used to walk thousands of tiles of a big ground triangle).
- gbuffer_multi_draw is vertex-pull bound (non-indexed, dependent index to position load, per-vertex mat4 instance load); fragment cost is small. A depth prepass does not pay (see render3d-pipeline.md).
- Things that did not help: kernel-weight probe skipping in the resolve, cosine cut in the distance integration, a sun shadow ray skip for hits facing away, slower update of offscreen probes (broke "small emitter lights a sealed room" and lagged lights behind the camera), a shorter screen shadow reach (cost is per march), `LIGHT_SAMPLES` 1 (loop cost, not rays), `smooth_blend=false` for the ocean's ambient (changed the underwater look a lot).
- Draw submission: bind the pipeline once and rebind only descriptors per batch; read culling/soup data from FFI arrays, not scattered Lua tables (~300 ns per access on a 13 GB heap); only look at the shadow batch table's records on a `batch_serial` change (and write the ones that differ, it rewrote all of them until 2026-10-19).
- Big-scene CPU: `ddgi.GetEmitters` rebuilt 308k emitters ~11x/s while moving because it was keyed on `soup_version`; it is now keyed on `scene_bvh.emitter_version`. Map load is CPU bound in MDL decode, VMT loads and static_geometry building inside `Update->timers` tasks, with GC ~25%; frames run 0.4-1.8 s while props stream. Profile one load stage at a time.
- Beach (54M triangles, 10.7 GiB VRAM) went from ~20 to ~12.5 ms CPU per frame and became GPU bound.
- gm_construct_m3_401 is the heavy metastruct map (9724 BSP entities, 4020 static props, ~1850 lights); its default camera is at the origin looking at ocean, use the lobby spawn `units.PositionToEngine(Vec3(-10818,-9029.5,9448))`. Some props/materials are not installed anywhere (props_island, soldier_statue, props_swamp, Nature/grass_09, dirtground011_island, tunnel01-ssbump, Material2). `test/harnesses/gmw/` drives a scripted walk/fly over it (`walk.lua` drives the real player rig through the `CreateMove` event after `SetEyePosition`).

- Buffer memory (2026-10-19): `vkAllocateMemory` was 15% of the main thread while loading models (one allocation per mesh buffer, 1005 Crysis cgf: `finish` 4.4 s to 2.1 s). `vulkan/internal/buffer_pool.lua` binds buffers up to 4 MiB to ranges of 64 MiB blocks per memory type and flags (size classes, eight per power of two, ranges reused by the next buffer of the class once the deferred release ran, blocks never given back, mapped once as a whole). The vram view groups them as `small buffers`. `test/harnesses/cgf/decode_bench.lua` is the benchmark (all cgf models of a level on the main thread under the profiler, `r_codec_threads=0` runs the worker part inline).

## Culling off, and the gm_construct_m3_401 pass

*`r_feature_culling`, what the worst case costs, what was in a frame, the scripts in `test/harnesses/m3`*

`r_feature_culling` (pvar group feature, not stored, `gpu_culling.culling_enabled`) turns off visibility culling to get the worst case: every visible-flagged visual of the map is drawn every frame. It switches off, in both gpu cull shaders, the cull distance, frustum, screen size and Hi-Z tests of the main view and the query box, minimum caster extent and occlusion tests of the shadow views, in the cpu fallbacks the frustum and distance tests of `Visual` (`IsAABBVisibleLocal`, `IsWithinCullDistance`, the static tree walk), `render3d.SphereInFrustum` (which decides which point lights update their shadow map and light occlusion map) and `ShadowMap:IsWorldAABBVisible/TooSmall`, and the Hi-Z build. LOD selection is not culling: add `lod_level 0` for the most detailed worst case. `Visual.Library.noculling` still exists and means something else, it takes the cpu draw path.

`test/benchmarks/gm_construct_m3_frames.lua` runs culled, unculled, unculled at lod 0 and culled again at the lobby spawn. On this machine (RTX 4090, 1080p, lobby spawn, unculled, avg frame / GPU / allocation) the pass took the frame from 22 ms (cpu bound, 21 ms of recording) / 14.8 ms / 65 MB/s to 11.3-11.6 ms (GPU bound, culled the same) / 10.2 ms / 35-45 MB/s with 6-7 ms of recording. The same scripted fly over the map with culling on (`GMW_MODE=fly`) went from 31 ms (p95 54) to 10.5-11.6 ms (p95 18-20), gm_construct from 7.6 to 7.2 ms (p50 8.3 to 6.8).

What was in the frame, unculled (the order is the order of the findings):

- The gbuffer does not care about culling on this map: `gbuffer_multi_draw` draws 4515 entries in 4 indirect calls for 0.3 ms of GPU time, culled or not (742 entries culled). The frame is lighting, GI, translucents and fog, and cpu work for what is not gpu driven (translucent, glass tint and the 300 or so fallback entries).
- GC and `GetPBRFactorUploadKey`: the key was worked out per draw with a string concat per feature param (`"Get" .. param.name`), 15% of all GC samples and 29% of cpu time in GC. Keys of a material only depend on its properties, so they are cached per `property_version`. Properties declared with `versioned = true` (Material does, `objects.lua`) stamp their object with a new `property_version` when they change and put it in a ring log (`objects.version_log`), `Material:Touch()` is for code that changes a vector or a color in place (material proxies, only when they changed something).
- `BatchTable` rewrote 2 x 256 records of the gbuffer batches every frame as a safety net (2.2 ms). It now writes a record when its material was stamped (found from the log, not by scanning), the moving part of an animated batch when the wind changed (every update until 2026-10-19), 4 records as a safety net, and copies only the records a frame's buffer is behind on into a buffer that stays mapped. Records are written by one generated function with constant field names and plain properties are read as fields, 7.5 to 3.3 us per record (a cdata field read by a variable name is slow).
- `GraphicsPipeline:Bind` (every dynamic state setter, 24% self time) ran for every glass tint, gbuffer fallback and overlay draw. They use `UploadConstantsBound` now, and pipelines whose uniform buffers all follow the current material (`block.memo_key`, `model_pipeline.GetMaterialMemoKey`) reuse the uniform offsets of a material for the rest of the frame. `CommandBuffer:BindDescriptorSets` compares dynamic offsets by content now, so offset tables can be reused. `ShouldPushConstants` and the persistent uniform compare allocate nothing and use `memcmp` (`bindings/memory.lua`).
- Screen space shadows were 4 ms of the 6.4 ms lighting pass, all of it for point and spot lights. They were marched before the point shadow map and the light occlusion map were looked up, and before knowing the light reaches the pixel at all (most BSP lights reach through walls), and the march result was thrown away for lights that a shadow map decides alone. The march is last now and only runs when the shadowed light is above the threshold, and fully shadowed lights are skipped before the BRDF and the 25 tap glass tint lookup. Lighting 6.4 to 2.0 ms.
- Glass tint redrew 4 maps every frame, 11 us per glass entry. A map is drawn again only when its light space matrix, the glass (entry, material version, world matrix compared with memcmp) or the framebuffer changed (`glass_tint.IsSlotCurrent`, the last image layout stays valid). The per frame collection of translucent and glass entries keeps what it works out per component until the entries, the material override or a material change (`get_items` in visual.lua), and `GetPreviousWorldMatrix` keeps two matrices instead of copying one per frame.
- Removed: `scene_bvh` diffed every light position every frame for a counter nothing read.

What is left, unculled lobby: GPU is the bound (the cpu waits ~5 ms per frame in `swapchain.GetNextImage`, `block_time.lua`). ddgi (shade 2.4, trace 0.8, distance 0.3, others 0.5 ms) is 35% of the GPU frame, the direct light loop 1.9 ms (115 lights reach the lobby cell by sphere, the light occlusion map kills most of them per pixel, disabling it makes lighting 3x slower; a visibility aware light grid would help), translucent_accumulate 1.2 ms of which 0.9 is that same loop per glass fragment, fog 0.9, shadows 0.5, reflections 0.4, ao 0.4. In the culled fly the cpu is the bound (translucent draws 2 passes x ~340 draws x 3.9 us, collection 0.5 ms, gbuffer 1.2-3 ms, glass tint while moving, shadow update 1 ms), a gpu driven translucent pass would remove most of it. About 30 materials animated by Source proxies still rewrite their batch records every frame (3.3 us each, 80 writes per frame in the lobby).

The Lua heap of this map was 2.5 GB after a full collection (`census_run.lua`, a full collection took 1.9 s): a million filesystem path_info tables (the `vfs` translate cache held 50000 paths times every mounted path, 500 MB and a third of a collection, now limited to 2000 paths: heap 2.2 GB, collection 1.4 s, the load is no slower), 645k polygon vertex tables and as many tangent tables that stay on the cpu after the upload, 26k convex hulls of static props, 7M tables in all. A collection cycle starts every 60-100 s at 40-50 MB/s and costs ~100 frames at +10 ms each plus one ~90 ms atomic hitch, the single worst frames of every run (a 90 ms frame inside `light_grid`, `ddgi_trace` or `glare` is the collector). Flying over the map for 9000 frames with culling on (`spikes.lua`, `M3_MOVE`): default settings avg 8.46 ms p95 17.2 p99 21.7 with 355 frames over 18 ms, `collectgarbage("setpause", 400)` avg 7.34 p95 9.8 p99 11.0 and none over 18 ms but 9.5 GB of heap by the end (no cycle ran), `setstepmul 100` p95 13.2 with a 130 ms hitch, pause 300 + stepmul 100 p95 13.7 with a 328 ms hitch. The engine does not set a pause, 400 is a memory for hitches trade the user can make with one line. Fewer allocations make cycles rarer, dropping the cpu copy of uploaded vertices would make them cheaper.

Scripts (`test/harnesses/m3/README.md` lists them): `measure.lua` for frame time and per pass numbers, `sweep.lua` for pvar variants in one process, `time_fn.lua`, `block_time.lua` and `spikes.lua` for where a frame goes, `prof.lua` and `ptree.lua` for profiles with `PT_UNDER` and `PT_CALLERS` filters, `alloc.lua` for allocations, `verify_caches.lua` to check the caches against a from-scratch computation, `ab_shot.lua` for screenshots. Pitfalls met on the way: `pkill -f "luajit glw"` in a shell command kills that shell, a `pgrep -f` in a waiting loop matches the loop itself, an alloc probe that wraps with a closure measures its own closures (wrap with `local a, b = f(...)`), the profiler pins samples on the wrong line now and then (a 28% hotspot in `scene_lights.lua` did not reproduce and timing said 0.2 ms), and a change of shared GLSL costs ~25 s of driver compile on the next run.

## The pbr stress scene

*`test/benchmarks/pbr_stress.lua`, 2026-10-15, RTX 4090, 1080p, 5 s measured per phase, `PBR_PHASES=name,name` picks phases, `PBR_MEASURE=5`*

Every phase puts the camera in front of a plane (or a field of spheres, panes, sheets) high above the default scene so that the whole screen runs one shading path: matte, glossy dielectric and metal with a roughness ramp, clearcoat + sheen + secondary specular, smooth and rough metal reflecting a lit wall (the reflection rays hit geometry), glass panes, glass spheres, transmission sheets around a light, the empty sky, clouds, the ground fog at the horizon. `frame_benchmark` phases take a `view()` for this. `PBR_SHOTS=<tag>` saves one picture per phase to `tmp/ab/<tag>_<n>.png` instead (exposure locked at EV 15) for A/B runs.
- Every opaque path is cheap: all of them are 4.5 to 4.9 ms of GPU frame at 1080p and the same 4.4 ms without any material (DDGI 2 ms of it: shade 0.7, distance 0.65, resolve 0.4, irradiance 0.3), lighting itself 0.3 ms (0.5 with the three layers), ambient occlusion 0.2. The reflections trace of a rough metal that reflects geometry is 0.7 ms, the sky 3.5 ms in all, clouds +1.9 (`clouds_trace`), the horizon fog +0.6 (`volumetric_froxel_scatter`).
- **Glass is the expensive one: `translucent_accumulate`, 8.7 ms for three full screen panes and 11.7 ms for a field of 105 spheres.** What it was made of (a temporary `TR_MODE` splice into the shader, one part off at a time, panes / spheres): the refraction lookup (the march of `screen_refraction_trace` and the cone rays) 3.4 / 6.9 ms, the probes' light 2.0 / 3.2 ms, the ray traced reflection 0.3 / 3.9 ms, the four cone rays of rough glass 0.4 / 3.8 ms; 5 ms were left with all four off.
- **Fixed (panes 8.7 to 6.1 ms, spheres 11.7 to 8.3 ms, median of alternating runs):** a surface that transmits everything (`refraction.amount >= 1`) has no diffuse, so the light of the probes only reaches its reflection: where that is traced (perceptual roughness under 0.1) the probes are not read at all, and where it is not the opaque scene's light behind it and the sky stand in for the 8 probes with a visibility test per pixel and layer. A refracted ray that finds nothing still reads the full probe light, worked out only then (`get_exit_environment`, the values it needs are kept in globals): with the cheap light there it was a visibly different crescent on the rim of every sphere. The blend of probe and sky reflection is skipped when the reflection is traced alone. `screen_refraction_project` multiplied `projection * view * v` as a matrix product per call (21 per ray), now `projection * (view * v)`. Pictures against the old shader: the same as two runs of the old one (PSNR 34 dB on the sphere field, whose noise floor is that low; 48 dB on the panes).
- Tried and not kept: fewer cone rays at low roughness (2 under 0.15, 3 under 0.3 against 4) saves a part of the 3.8 ms and shows as grain on the rough spheres.
- Tried and not kept: `ddgi_distance` (0.63 ms in every phase, twice the irradiance pass) evaluates `pow(cosine, 50)` for each ray and texel; skipping the rays under the best cosine times 0.79 (a first loop finds the best, the weights of the others would be under 2^-17 of it) made it slower, 0.97 ms (4 alternating runs, the pictures were the same): the second pass over the rays costs more ALU than the pow's transcendentals, which were not the cost. What is: the 256 texels of a probe each walk every ray out of shared memory.
- Tried and not kept: `screen_refraction_trace` reading the depth of four steps before looking at any (to wait once for four fetches and not four times, the same result): panes 7.4 and 4.3 ms with the old march, 5.9 and 5.3 with the new, spheres 8.0 and 9.7 against 10.3 and 10.2, 4 runs each on a day when the same shader moved by 70 percent between runs. No gain that can be told from that.
- Run to run, the same shader differs by 10 to 20 percent (panes 8.4 to 10.6 ms, spheres 10.9 to 18.9 ms in 4 runs of 2 builds), so decide with alternating runs of both builds (`tmp`-style `ab_perf.sh`: head, new, head, new), not one run each. A script's `#!/bin/zsh` does not exist on this machine, use `#!/usr/bin/env bash`.

## Shader and pipeline caches, and the slow first start

*what is cached where, what the logs mean, how to start cold*

Three caches sit between a shader's GLSL and a running pipeline:

1. `storage/cache/shaders/<crc32>_<length>.spv`, the engine's own (`goluwa/render/vulkan/internal/shader_module.lua`). A file is a header, the SPIR-V and then the GLSL it was compiled from; a hit is used only when that GLSL equals the shader's exactly, so a crc32 collision or a stale or truncated file is detected, logged as `[shader] compiled ... because the cache is off: <reason>` and rebuilt. A plain miss logs `[shader] compiled <stage> shader ...` and a hit logs nothing. shaderc takes milliseconds per shader, so this cache is not what makes a cold start slow. The old format (a bare crc32 file name, SPIR-V only, no check) is deleted on first use.
2. `storage/cache/vulkan_pipeline_cache.bin`, the Vulkan pipeline cache, saved a couple of seconds after the last pipeline was made (a `--one-frame` run exits before that).
3. **The NVIDIA driver's own cache** in the home directory: `~/.cache/nvidia/GLCache` (about 1 GB here) and `~/.nv/ComputeCache`. This is what makes the first start slow: a cold start took about 117 s on this machine (about 115 shaders), a warm one 2.8 s. A shader change makes the driver recompile every pipeline that uses it, so any edit of shared GLSL (gbuffer layout, lighting, surface features) costs a slow start the first time. `[pipeline] the driver compiled a <kind> pipeline in N ms` is logged for any pipeline that took 50 ms or more to create, and nothing for the fast ones.

**Where the cold start goes (2026-10-13, `gi_reflections.lua`, 117 s):** shaderc is not the cost, its libraries (the Nix one and the release `.so`) compile the biggest shader in ~30 ms. The driver spends 107 s on 17 graphics pipelines, serially on the main thread: two lighting fragment shaders (132 KB and 183 KB of GLSL) take 45 s and 31 s, eight 65 KB ones ~3.5 s each, all compute pipelines together ~5 s. Tried in a worktree with a fresh driver cache: stubbing every ray query site (glass, reflection hit, DDGI visibility) saves ~30 s (117 to 88 s), `[[dont_unroll]]` on every loop is slower (133 s), shaderc optimization level 1 or 2 saves 3-12 s but grows the SPIR-V 5-10x and spends seconds in spirv-opt. The time is in the sheer size of the lighting shaders, not one feature; graphics pipelines are now created on `thread_pool` workers and waited for at their first bind (`GraphicsPipeline:Wait`), which brings the same cold start to ~55 s; the driver does not scale across threads (12 big pipelines at once take 60-90 s each), so splitting the lighting shader is the remaining lever. Stripping the functions `main` never reaches (14% of the GLSL) cut the driver's total cpu time by only 12% and the wall time not at all.

Start cold with `rm -rf ~/.cache/nvidia/GLCache ~/.nv/ComputeCache storage/cache/shaders storage/cache/vulkan_pipeline_cache.bin`, they all regenerate. If something renders wrong only on one machine's cache state, clear the driver cache first: it is the one cache the engine can't check.

## Startup time

*`goluwa/startup.lua`, the STARTUP tab of PERF, what the load of Esther and Quarry costs and what was done, 2026-10-17*

**Timers.** `goluwa/startup.lua` is imported first in `main.lua` and records two things. `startup.Begin(name)` / `startup.End(name)` are wall clock spans (nested spans are found by containment afterwards, they may interleave across task yields). `local t = startup.Start() ... startup.Add(name, t)` adds to a total for work that happens many times; a name `group: item` is grouped in the tab by the part before the colon. `Add` is a no-op once the scene is ready, so the timers cost nothing after startup. Spans exist for the engine boot (`main.lua`, `render.Initialize` and its parts), the Source load (`bsp.lua`, `map_scene.lua`, `source_engine.lua`) and the Cry load (`cry_engine.lua`, `level.lua`); totals for the render passes, `render.Draw`, task steps (`task: <name or extension>`), pak inflation, texture upload, pipelines, shader compiles, the bvh first build, the batch table, decals and billboard bakes. Name a task (`task:SetName`) or it shows up as `task: unknown`.

**Ready** is decided by `goluwa/render3d/startup_ready.lua`: the bvh has been built, nothing is loading or spawning and the bvh version has not changed for 1.5 s. The time reported is when it stopped changing (the 1.5 s is not counted) and the totals are the snapshot taken then. It only sees the bvh, so GI and exposure convergence, vegetation LOD and anything later is not part of it. `GOLUWA_STARTUP_REPORT=1` prints the report at that point. The STARTUP tab (`addons/debug/.../render_2d/startup_stats.lua`, `StatTable` with `Timeline = true`, mouse wheel scrolls) draws the spans as a timeline and the totals as bars over the time they were active; the totals overlap each other and the spans (a frame contains its render passes).

**Measuring.** `tmp`-style scripts: run `map esther` or `map IA/Quarry` from a `lua` command, exit when `startup.IsReady()`, print `startup.GetReport()`. Run to run noise is 0.3-0.5 s, compare 2-4 runs. A shader change costs the driver recompile on the next run, run twice. The profiler pins C and FFI time on the wrong lines here as well (it put 33% on `batch_table.lua`, the timer says 0.4 s), time a suspect before working on it. Wrapping every `Update` listener with a timer (`event.active.Update[i].callback`) finds the big ones fast, `timers` (tasks) is most of a load, and `window_update` (render.Draw) is on `Render` now, not `Update`.

**Where it went (RTX 4090, warm caches, before):** Esther 7.2 s: boot 1.1 s (vulkan instance 0.25, render.Initialize 0.45, render3d.Initialize 0.33, autorun 0.15), bsp decode 0.5 s (worker), bsp brushes 0.44, translate 0.36, spawn 0.33, then 4 s of streaming with the `static world build` task 1.8 s (decal projection 1.0), mdl decode 0.8, bvh first build 0.65. Quarry 13.5 s: boot 1.1, level load 0.8 (extract visual objects 0.45), the scene spawn task 3 s and cgf decode 3 s (1.2 of it pak inflation on the main thread, 0.9 materials), terrain tiles 3 s, billboard bakes 1 s, decals 1 s in one frame, bvh first build 0.8 s. The main thread is busy for the whole load, so only less work or more threads help; throttling the frames while loading (tried at 0.1-0.5 s) did nothing.

**What was done (Esther 7.2 to 6.1 s, Quarry 13.5 to 10.1 s):**
- GC pause: a load allocates millions of tables and the collector took about 15% of the time. `r_loading_gc_pause` (default 1000, `startup_ready.lua`) is set on `SceneLoad` and put back when the scene is ready: -0.7 s Esther, -1.0 s Quarry for 0.7-0.9 GB more heap at ready.
- Pak entries are inflated on the worker pool: `vfs.Prefetch(path, callback)` (zip context only, `CONTEXT:Prefetch`) inflates on a worker and stashes the string on the entry, the next `Open` takes it. `codec.DecodeFileAsync` (textures) and `model_loader` (before the decode task starts) call it. Inflation on the main thread went from 1.3 s to 0.2 s on Quarry (the deflate is pure Lua, ~100 MB/s, 133 MB of paks are read). A file under `thread_pool.inline_threshold` still inflates inline.
- Terrain: the scene stays loading until the first tiles are built and they were built 2 per frame while frames cost 100 ms each. `LoadBuildsPerFrame` (16) applies while the terrain holds the scene load: Quarry's terrain was done 1 s earlier.
- Decal projection onto displacements (`decal_geometry.project_displacements`): scalar normals, no per quad tables, no queue entry tables, the output polygons of triangles that lie wholly outside the decal rectangle are not made: 1.0 to 0.6 s on Esther, identical fragments (20945 on Esther, checksummed). Pruning the triangles that cannot reach the decal looked like a 4x win but changes the output: the unwrap starts new seeds in the pruned places and the planar projection of surfaces above the decal (steep terrain) overlaps the rectangle, so the connectivity of the whole displacement surface is part of the result.
- `billboard.BAKE_BUDGET` lets several billboards bake in a frame (was one) and the pipeline cache (178 MB) is only written again when its size changed (`GetPipelineCacheDataSize`, it was rewritten every run, 0.17 s on the main thread).

**Left, in order of size (as of the first pass, the cgf decode has since moved to workers, see "Threaded decoders"):** `mtl_material.apply_cry_material_node` (1.4 s for 700 textures, the Material and Texture objects; `resource.Download` runs the decode request synchronously) and the rest of the cgf `Finish` on the main thread; frames while loading cost 100-250 ms against 12 ms steady (gbuffer batches that change every frame, `batch_table` full rewrite 0.2-0.6 s in all); the first bvh build is one 0.7-0.9 s frame (`scan` over every visual) and waits for the decals and bakes (they change the scene); Esther's `static world build`; a 1 s frame when the decals project (`SetDecalFragments`/`RefreshBatches`). Worker threads are not the cost of a slow decode job (a 175 KB dds took 0.7 s because the main thread was in a long frame when it finished).

**Threaded decoders (2026-10-17):** a model decoder whose parsing is plain functions of bytes runs on the worker pool through `model_loader.AddThreadedDecoder(id, {Gather, job, Finish})`: `Gather(path, full_path)` (main thread, vfs reads, workers have no mounts) returns the input of the job and its size, `job` is the worker's source, it gets the input and returns a table and a blob, `Finish(path, full_path, input, meta, blob, mesh_callback, physics_callback, skeleton_callback)` (main thread) makes the materials and meshes. Meshes cross as bytes: the worker adds packed `vertex_math.VertexType` vertices (uvs, normals and tangents built, `Polygon3D:PackVertices`) and indices to a `codecs/internal/blob` builder with `packed_mesh.PackPolygon`, the main thread copies them out with `packed_mesh.Unpack` / `ToPolygon` (`UploadVertexArray` with `keep_packed`), no lua table per vertex. A polygon made this way has an empty `Vertices` until `GetVertices()`, anything that reads the tables of a visual's polygon must unpack first (physics, raycast and now `decal_receivers` do). mdl and cgf use it, a new format needs those three functions.
- cgf: `cgf.Decoder` (`Gather` reads the file and its `_lodN` siblings, `PackModel` is the job, `Finish` makes the `mtl` materials). The physics geometry is not made at load, `Finish` hands `physics_callback` a table that builds `children` (`cgf.ExtractPhysics`, extraction with `skip_visuals`) when a rigid body reads it. The diffuse tile and offset of the material change the uvs the tangents come from, the worker builds the tangents from the plain uvs and `Finish` rebuilds them (`vertex_math.BuildTangents` on the packed arrays) for the models whose material tiles. Quarry: the cgf task went from 2.3 to 1.7 s of main thread, the spawn from 2.3 to 0.5 s (it ran the first slice of every decode), 444 rigid bodies get the same 655 colliders, the picture is within the run to run noise (PSNR 42.3 dB against a second old run at 41.8). Esther's mdl was already like this, only the shape moved (same pictures, same time).
- A spike before it (141 models, 753 entries, 437k vertices): the worker output was byte identical to the main thread's `Polygon3D:Upload` packing, a cold worker takes 52 ms to import `cgf.lua` and the first job on a cold pool 85 ms, the whole batch took 0.55 s on 7 workers. `os.clock()` in a worker is process cpu time, not the thread's.
- The terrain tiles waited `BVHDelay` (1.5 s, one tile per frame, there so that flying fast does not build tiles that are gone) before entering the scene bvh, which held the first bvh build and "ready" for 1-2 s on Quarry: while the terrain holds the scene load they enter at once. Quarry 10.1 to about 9.5 s together with the cgf change.
- Not threadable: the materials (`apply_cry_material_node`, ~0.8 s, Material and Texture objects), the mesh callback, entity creation (0.5 s), `UploadVertexArray`, frames (`render.Draw`, 2.9 s) and terrain tile baking. Frame throttling while loading was tried again after the terrain changes (0.25-0.5 s between frames while loading): -0.3 s, inside the noise of 0.6 s, not kept. Left that could move: the first bvh build (0.76 s: `get_shape` child sah per shape 0.33, `write_block` 0.19, `get_piece` 0.07), texture dispatch (~1.1 ms of main thread per texture, a worker that reads and decodes the pak entry itself would save ~0.2 s).

## Flying over the island (2026-10-18, `test/harnesses/terrain/island_fly.lua`)

`island_fly 300` (or `island.Fly(kmh, radius, height)`) flies the island example around the mountain at 300 km/h, following the ground. The harness prints frame times per 2 s, `ALLOC=1` stops the collector and prints MB/s and ms/frame per event listener, terrain, scene bvh and vulkan call, the memory allocations by label, the slowest frames with what was slow in them, and `PROF=1` writes a profile. Before: p50 28 ms, p95 80, 160 MB/s of Lua heap, 24 `vkAllocateMemory` per frame, 400 ms hitches. After: p50 18, p95 30 in steady state, ~85 MB/s. What it was:
- `Mesh.NewDeduped` built a Lua string of all vertex and index bytes (twice, with the concat) as its cache key: 1 MB of garbage per terrain tile. Meshes nothing else shares take `mode` `"owned"` (the cdata is kept instead of copied, no dedupe) and cpu-only ones `"host"` (no vertex or index buffer, so no `vkAllocateMemory`): `Polygon3D:UploadVertexArray(..., mode)`. Terrain tiles are owned, scatter bvh proxies host.
- A terrain tile in the scene bvh cost ~10 ms of cpu (SAH, bake, soup growth with a `WaitIdle`). The bvh now gets a rays only, host only copy at a coarser stride (`BVHStride` 4, `BVHNearStride` 2 for level 0, `Terrain:CreateBVHEntity`), 8448 to ~2300 or ~640 triangles, the soup stayed at a third of its size.
- Scatter proxies were the biggest bvh cost: 250k triangles/s of SAH while flying (13 ms per proxy, 24k triangles). The range they are built within shrinks with the camera speed (`range / (1 + speed / 25)`) and a unit waits 180 frames before its proxy is rebuilt.
- `Device:FlushDeferredReleases` has a 2 ms budget when not forced (vkFreeMemory is 0.1-0.4 ms each, a collection queues thousands). The releases cost 7 ms/s in all, they are not the GC hitch. The hitch (up to 600 ms, 130 ms with the collector stopped) is the collector itself: ~1.4 GB live heap, mostly cdata.
- Terrain tile bake and mesh (2026-10-18, after reading the Limcore `Terrain` project, a heightmap clipmap displaced by tessellation, see `docs/terrain-streaming.md`): `ShaderSource` bakes the height function once per chunk into a nearest sampled `r32_sfloat` field (detail texels plus a one texel apron) and the normal, splat, splat2 and color passes read it (`terrain_bake_field`, exact at the field's texels, bilinear between) instead of evaluating `terrain_height` 5 more times per texel: 368k evaluations per island tile became 71k, gpu per tile in a batch of 100 0.90 to 0.61 ms on the island (0.54 to 0.52 on a 15 octave noise, there the fixed cost of the passes is what is left). `tiles.BuildPolygon` copies the vertices of a template per (cells, spacing) and every tile of a shape shares one `IndexBuffer` (`Mesh.New` takes an `IndexBuffer` as `indices`): the index pool kept a 50k index copy per tile, drawn once and copied by a lua loop. 0.46 to 0.28 ms per tile, and the aabb comes from the chunk's heights instead of a loop over the vertices (`UploadVertexArray(..., aabb)`). Measure the bakes with a warm texture pool: `bake_cost.lua` calls `Source:Finish`, which empties it, so its "record" column includes allocating the textures (`test/harnesses/terrain/bake_pool.lua` polls `in_flight` instead).
- Not done: SAH build speed (binning is 3 passes per level), growing the soup copies instead of re-baking, dropping the cpu copy of tile vertices after upload.

With the see through mask 0x02 (glass is `IsSeeThrough`, mask 2) it is -2.7 ms (8%), the same picture, kept (`goluwa/render3d/glass_light.lua`). `r_glass_light_distance` (how far it looks) 30 / 100 changed nothing after that, the ray is cheap once only glass is left, what is left is the number of rays and the any hit calls for them.
- `reflection_ray_query` off: -11.5 ms (reflections_trace gone, `translucent_accumulate` 7.5 to 3.6, so the traced reflection and refraction inside translucent surfaces cost 4 ms, 3.6 ms is their shading), `reflection_resolution quarter`: -3.6 ms (`reflections_trace` 6.4 to 2.9, 45% of the time for 25% of the pixels).
- `ddgi_max_ray_distance` 30 (from 4000): -5.8 ms (to 26.3 against 32.1 with the mask change): `reflections_trace` -2.2, `translucent_accumulate` -1, `ddgi_shade` -1.4. Not the probe rays' length (`ddgi_trace` is unchanged): it is the length of the glass ray in the shade pass for misses, and it changes what the probes hold and so what the reflection hits find (a hit outside the probes does 4 extra visibility rays, `scene_reflection.lua`). Changes the look of the cave (dark far field), not free.
- DDGI: `ddgi_visibility_rays` none -1.2 ms, relocated only -2.5, `ddgi_emitters` off -1.8, the probes frozen (`ddgi_update_interval_*` huge, nothing updates) -9.7 ms: the passes skip when no cascade updates.
- The dispatch of the probe passes is every probe of every cascade (`dispatched` 17.7M rays, 22M threads for ddgi_shade), a cascade that does not update returns at once. Cost against the cascades dispatched (z of the trace, y of the shade, `DBG_Z` experiment): 1 cascade 1.2 + 2.3 ms, 2 cascades 1.7 + 3.3, 8 cascades 2.8 + 4.8. That experiment also dropped the updating cascades above z, so it said nothing about launching and returning threads: compacting the dispatch to the cascades that update was done on 2026-10-19 and changed nothing (see "Runtime pass on Esther and Quarry").

Sacrifices that look worth it, in the order of what they save: reflections at quarter resolution (-3.6 ms, softer mirrors), the translucent surfaces without traced reflections when they are rough (the 4 ms above, ask `traced_weight` to stop at a lower roughness), `ddgi_max_ray_distance` around 100 with a check of the look (-2 to -6 ms), `ddgi_visibility_rays relocated` (-2.5 ms, light leaks at thin walls to be checked).

New pvars (all build time, the shaders are made with them): `r_rt_hit_textures`, `r_rt_hit_texels`, `r_rt_hit_sun`, `r_rt_hit_lights`, `r_rt_hit_shadow_rays`, `r_rt_hit_probes`, `r_rt_hit_any_hit` (ddgi.lua), `r_rt_reflection_distance` (scene_reflection.lua), `r_glass_light_distance` (glass_light.lua).

## VRAM (2026-10-20, `test/harnesses/perf/vram_dump.lua`)

*Where the memory of the alpine terrain, Esther and Quarry goes at 1080p, what was reduced, what is left*

`SCENE=alpine|esther|quarry luajit glw --3d --hdr --background --validate lua "./test/harnesses/perf/vram_dump.lua"` prints the `vram_dump` rows once the scene has settled, then every main pipeline with `on`/`off` and its draw count (a pipeline that never drew and still holds a framebuffer is a waste), the tracked total and the process total from `nvidia-smi` (the driver's own context, pipelines and descriptors are the ~800 MiB difference to the tracked allocations). `vram_agg.py log [n]` groups a log by label (framebuffers by pass). Process total before and after: alpine 5700 to about 4500 MiB, Esther 4080 to 3375, Quarry 4695 to 4047.

What alpine held (tracked 4916 MiB, 1080p) and what happened to it:

- **TLAS rows (TLAS 363 MiB + scratch 138)**: four slots built for 364620 instances while 56700 were live. `scatter_rt` reserves a range of rows for the instances the gpu writes and replaces it when the scatter rooms adapt (the first reservation is the estimate, 259k rows, the settled one 57k); the new range went past the end because the old one was freed after four frames, the terrain tiles allocated after the first range kept the row count (`tlas_table.count`) at its peak, and slots only ever grew. Now `Table:FreeRange(base, n, true)` frees at once for a caller that waited for the device (the scatter rebuild does), free ranges are kept sorted, merged and a free range at the end lowers `count`, rows are given out from the lowest free one, and `instances.Build` copies the runs of used rows (`Table:GetSpans`) into a compact buffer when a quarter of the table is free (`accel.CompactInstances`, a TLAS has one instance geometry so holes cannot be skipped any other way). Slots follow the count down as well as up (`get_free_tlas_slot`). 363 to 85 MiB and a TLAS build of 57k instead of 364k.
- **DDGI state atlases (337 MiB)**: `ddgi_irradiance` and `ddgi_distance` kept a state texel (frames behind, the probe's mean brightness and its change filter) per atlas texel, but every texel of a probe computes the same, so it is one texel per probe now (`probe state` textures, 576x240, owned by the pipeline, written by the first thread after a barrier). 337 MiB to 2 MiB in every scene. The picture is the same within the noise between two runs (esther cave GI, 33-35 dB between runs of old and new, 35 dB between two runs of the old).
- **BLAS pools (512 MiB)**: 256 MiB chunks of which the second held 22 MiB, 64 MiB chunks now (320 MiB for 166 MiB live, the rest is size class holes: a BLAS is built at its full size, compacted into a new range and the full size range waits on its class's free list for the next uncompacted build).
- **Staging uploads (`scene_upload`, 115 MiB)**: sized for twice the biggest burst (the first upload of the tables) and never given back. `store.TrimUploads` retires a buffer over 8 MiB that has not been a quarter full for 600 frames.
- **Framebuffers of passes that are off (172 MiB at 1080p, four times that at 4K)**: ssaa, edge_aa (3), fxaa, ambient_occlusion_debug, gbuffer_inspect, lighting_albedo and the two ddgi debug views allocated theirs at startup. `lazy_framebuffers = true` in a pass config creates them when `GetFramebuffer` or the first `Draw` asks (`EasyPipeline.framebuffers` is nil until then, consumers that test it see "not there"). The two ddgi debug passes also gained an `is_enabled`, they dispatched (barriers, descriptor updates) every frame with the view off.

What is left, in the order of size (alpine, MiB): small buffers 640 of which 163 are uniform rings (162 rings of at least 3 x 256 KiB, peak use 1 MiB in all, 125 never uploaded: the variants of the gbuffer and translucent pipelines (`gbuffer_instanced`, `_anim`, `_height_map`) make a 3 MiB ring per persistent keyed block at startup; a ring cannot be made lazily without a safe point, its buffer is in the descriptor sets of the pipeline when it is made and a set that a recorded command buffer bound cannot be written), textures 488 (the 8192 and 4096 sun shadow maps are 160), ddgi 843 (`ddgi_ray_hits` 337 and the ray radiance 169 are sized for all ten cascades x 13824 probes x 160 rays although only the cascades that update this frame are traced: capping the cascades per frame would let them be a fraction), BLAS 320, scatter instances and baked 256 (fixed 2^21 rows of 64 bytes, not grown on demand), froxels 172, gbuffer and post framebuffers ~1 GiB at 1080p. `ddgi_ray_hits` asks for `host_visible` + `device_local` (the 256 MiB BAR window on a machine without resizable BAR) only because a test maps it.
