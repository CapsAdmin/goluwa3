# Performance measurement and optimization

Lessons from past profiling sessions. Timings in here are rough snapshots; re-measure before relying on them. Use `luajit glw bench` (below) rather than ad hoc scripts when a benchmark exists for the scene.

## Measuring correctly

- Vulkan validation is only on with `--validate` (and in tests). Never benchmark with it, it roughly triples CPU frame time. Always pass `--background`.
- The JIT profiler (`PROF`) only samples Lua CPU time. Time blocked in `vkWaitForFences` does not show up, so "slow frame but the profile looks idle" means a GPU sync. Time `render.SubmitAndWait` and swapchain acquire with `system.GetTime()`. It also pins C/FFI time on the trace's anchor line (a map-load profile blamed one line for 67% that was really 0.6 s), so confirm a hotspot with direct timing before optimizing. Never start `PROF` twice in one run. See debugging-and-profiling.md for how to start it.
- Acquire/frame-fence wait > 0 means GPU bound. About 0 with a bimodal frame-time histogram means a mid-frame CPU-GPU drain.
- `render.BeginFrame` is not just the fence wait: render3d records everything inside it (`target:BeginFrame` fires `PreRenderPass`). To measure the GPU wait, wrap `Wait` on `getmetatable(render.target.in_flight_fences[1]).__index` and GetNextImage/Present on the swapchain; patching the imported Fence template does nothing to live instances.
- `goluwa/render/gpu_timing.lua` records GPU timestamps per EasyPipeline pass plus `gpu_frame`; per-frame values are in the `last_ms` upvalue of `GetRawMilliseconds` (use `debug.getupvalue`). Shadow maps record into their own command buffers and are not in these scopes. The first `render.SubmitAndWait` of a frame blocks until the GPU finishes earlier frames, so its duration is about the GPU frame time (terrain bakes "looking slow" were really this).
- Use `system.GetTime()` for timers, never `os.clock()` (CPU time over all threads).
- Process-to-process variance is large (the ray query passes ocean/reflections/ddgi_shade come in a fast and a slow state for identical code, 5-12 ms for ddgi_shade) and about half the runs on a big scene land in a "heavy" state (more translucent draws). Compare modes inside one process (the first mode runs slower, put a throwaway `base` first), or take medians of several processes, and check draws per frame to tell which state a run is in. Before BVHSceneReady the numbers are junk (rt_build and soup_expand are huge).
- A stray engine run in the background doubles GPU numbers: check `pgrep -af "[l]uajit glw"` before measuring.
- Env vars set to "" are truthy in Lua.

## Benchmarks

`luajit glw bench` lists `test/benchmarks/*.lua`; `luajit glw bench <name part|all>` runs the ones whose first line is `-- glw: <flags>` (e.g. `--3d`, `--cli`, `--2d --physics`), one process each, and prints a pass/fail summary. A benchmark must end the process itself (`--cli` scripts need `os.exit(0)`).

- `goluwa/render3d/frame_benchmark.lua`: `frame_benchmark.Run{name, load, view, fov, phases, warmup, lead_in, measure, done}` waits for BVHSceneReady, nothing loading and 3 s of stable bvh version, then per phase (static, spin deg/s, move m/s out and back) prints avg/p50/p95/p99/max, allocation MB/s, gpu_frame, shadows and the top gpu scopes. Phases may have `enter(phase)` and `ready()`. New scene benchmarks should use it.
- Every benchmark ends with `benchmark_results` (`goluwa/benchmark_results.lua`): numbers with a noise value go to `storage/logs/bench/<name>/latest.json`, `glw bench <name> --baseline` also saves `baseline.json`, and each run prints `[COMPARE]` lines against the baseline (else the previous run) for numbers that moved by more than twice the combined noise (min 2%). `--no-compare` skips it. The noise floors are `RUN_TO_RUN_NOISE` in frame_benchmark.lua (frame 4%, p95 8%, gpu 5%, one gpu pass 12%): identical code in two processes really differs that much.
- State fingerprint: each phase records draw calls per frame (needs `render.stats = true`). A different draws/frame than the baseline prints "scene in a different state, timings not comparable".
- Micro benchmarks: `benchmark.Run(name, func, {time, warmup, max_time})`, `benchmark.Compare(name, {{name, func}, ...})` (interleaved, paired ratio), `benchmark.Finish(name)`. Test: test/tests/benchmark.lua.
- Existing: gm_construct_frames, gm_construct_shadows, gm_construct_animation, gm_construct_m3_frames (the heavy map, phases with `r_feature_culling` on and off, see below), lights_stress (synthetic rooms), crysis_beach, physics_stress, physics_map_stack, physics_synthetic_map. gm_construct_frames shows a ~42 ms frame at +3.3 s in its first phase (probably the pipeline cache save, unchecked).

## Screenshot A/B

`test/harnesses/go/run.lua` is the protocol: time-driven things (water) must be frozen with `system.SetElapsedTime(1000 + frame/60)` from a priority-1000 Update listener, restarted per mode so screenshots line up; lock exposure with `ExposureLock` on the View (EV from `r_exposure_info`); compare with ImageMagick `compare -metric PSNR`. The noise floor is about 43 dB between identical runs in one process and 38-39 dB across processes; below ~35 dB look at an amplified diff (`magick a b -compose difference -composite -evaluate Multiply 8`).

- Temporary shader experiments: add an int mode to the pass uniform block set from a global and branch on it, bisect, then remove it before finishing. Early-exit shader variants measured across separate runs were unreliable (the first run after a shader edit gave wrong numbers).
- Do not rewrite a file with `open(p,'w').write(open(p).read())` in a python edit script, it truncates first.
- Banding in smooth gradients (mirror reflections of sky) can be a viewer artifact: crop at full resolution (`magick in.png -crop WxH+X+Y`) before chasing it. The png encoder round-trips exactly and the blit dithers, don't re-audit them. Hard-edged geometric patterns are real.

## LuaJIT

- Fewer live locals, no alias locals (`local x = phys.obj`), direct field access in hot code. Judge by the abort count (`jit.attach` logger, `-jv`), not one timing: a single run can be a lucky or unlucky JIT state, run-to-run variance is +-15-20%, and you need 6+ alternating runs to see anything under 15%.
- "NYI: register coalescing too complex" only aborts side traces. At a side exit ALL locals active in scope (params and inlined caller frames too) are snapshot values, even dead ones. Free fixes: wrap temporaries in `do ... end`, `param = nil` for dead params right after the last use, tail calls (`return f(...)`), keep long-lived scalars in a plain scratch table (not Vec3, which is float32), split one fused loop in two, hoist loop-invariant calls out of nested loops, guarantee fields are numbers so `or 0` branches go away. Hoisting scalars into locals made it worse. Cutting coalescing aborts ~96% in the physics solver did not make the step faster, so check it is the actual bottleneck first.
- No nested row loops in hot solver code: LuaJIT unrolls short inner loops into the outer trace until "too many spill slots" and blacklists the loop (a bimodal 7 vs 67 ms step). `loopunroll=8` hid it but slowed everything else; the fix was one flat task list.
- `loopunroll` in `goluwa/jit/options.lua` `SetOptimized` is 40 (was 15). A sweep on the centrifuge scene gave 15: 43 ms, 40: 26, 60: 29-33, 120: 27, 200: 42 (traces too big). Measure steady state only, short runs are dominated by compile time. Re-sweep if the physics code changes a lot.

## Lua heap

- `objects.CheckRemovedObjects` drains `objects.remove_these` on the next Update: a census in the same frame as `Remove()` shows everything removed as leaked. Wait ~10 frames and `collectgarbage` a few times. The live heap after mounting gmod is ~350 MB and the default GC pause swings it 450-1300 MB, compare after full GCs.
- `assets.GetModel(path)` loads the model into `assets.cache` forever, only use it for procedural `.lua` models; `model_loader.model_loads:Forget(path)` drops one. `Texture.New{path = ...}` pins the decoded texture in `texture_cache` by config key: give previews a unique `cache_key` and `Remove()` them, never remove a texture whose `image` is `Texture.GetFallback().image`. `test/harnesses/ab_browser/census.lua` does a heap census by shape.

## What cost what

Findings from the Esther / Quarry / gm_construct / Beach optimization passes (2026-09/10).

- DDGI is the GPU bottleneck on most scenes. The wins were: tracing visibility rays only for probes with blend weight >= 0.02 (plus a contribution-share rule, see render3d-lighting.md), resolving at half resolution with a depth/normal weighted upsample (`ddgi.GetScreenSampleGLSL`), retracing settled disabled probes about once in 8 frames, dispatching ddgi_shade with probes on x so a warp traces the same ray from neighbouring probes, and `Opaque|CullBackFacing` ray flags for the visibility queries. ddgi_shade cost was dominated by random L2 misses in the triangle fetch and by the 8 visibility ray queries per sample.
- Lights: skip screen space shadows for lights under 0.002 of white, do not shade lights under 0.0002 at all, trace dim lights in reflection hit shading with a probability and weight 1/p. The world light grid (`light_grid.lua`) removed the per-light loop overhead (126 lights that reach nothing cost the same as 0 lights); DDGI samples 2 lights per hit instead of tracing all of them. BSP lights have huge ranges on purpose and are used as-is, so range culling culls nothing there; only the first 256 (`MAX_LIGHTS`) reach the shaders.
- Froxel fog: skip froxels beyond the farthest view depth per tile (indoor scenes only). A froxel behind a surface is lit at the surface (`froxel_point` clamp) but its density and air must come from the point at the slice depth along the ray, otherwise a leaf at ground height fills the column behind it with ground fog and filtering leaks it into neighbouring sky columns. A bilateral lookup, own-texel history and clamp-validity fallbacks were all tried and unnecessary, do not rebuild them.
- Ambient occlusion: each half-res AO texel stands for the pixel at the top left of its 2x2, keep that pixel's view depth, and blur with a depth/normal weighted 4x4 upsample (no normal weight for foliage); the old full-res 5x5 bilinear blur was both blurry and 3-4x slower.
- Grass: one workgroup per triangle in `grass_scatter_tiles` (one invocation used to walk thousands of tiles of a big ground triangle).
- gbuffer_multi_draw is vertex-pull bound (non-indexed, dependent index to position load, per-vertex mat4 instance load); fragment cost is small. A depth prepass does not pay (see render3d-pipeline.md).
- Things that did not help: kernel-weight probe skipping in the resolve, cosine cut in the distance integration, a sun shadow ray skip for hits facing away, slower update of offscreen probes (broke "small emitter lights a sealed room" and lagged lights behind the camera), a shorter screen shadow reach (cost is per march), `LIGHT_SAMPLES` 1 (loop cost, not rays), `smooth_blend=false` for the ocean's ambient (changed the underwater look a lot).
- Draw submission: bind the pipeline once and rebind only descriptors per batch; read culling/soup data from FFI arrays, not scattered Lua tables (~300 ns per access on a 13 GB heap); only rewrite the shadow batch table on a `batch_serial` change.
- Big-scene CPU: `ddgi.GetEmitters` rebuilt 308k emitters ~11x/s while moving because it was keyed on `soup_version`; it is now keyed on `scene_bvh.emitter_version`. Map load is CPU bound in MDL decode, VMT loads and static_geometry building inside `Update->timers` tasks, with GC ~25%; frames run 0.4-1.8 s while props stream. Profile one load stage at a time.
- Beach (54M triangles, 10.7 GiB VRAM) went from ~20 to ~12.5 ms CPU per frame and became GPU bound.
- gm_construct_m3_401 is the heavy metastruct map (9724 BSP entities, 4020 static props, ~1850 lights); its default camera is at the origin looking at ocean, use the lobby spawn `units.PositionToEngine(Vec3(-10818,-9029.5,9448))`. Some props/materials are not installed anywhere (props_island, soldier_statue, props_swamp, Nature/grass_09, dirtground011_island, tunnel01-ssbump, Material2). `test/harnesses/gmw/` drives a scripted walk/fly over it (`walk.lua` drives the real player rig through the `CreateMove` event after `SetEyePosition`).

## Culling off, and the gm_construct_m3_401 pass

*`r_feature_culling`, what the worst case costs, what was in a frame, the scripts in `test/harnesses/m3`*

`r_feature_culling` (pvar group feature, not stored, `gpu_culling.culling_enabled`) turns off visibility culling to get the worst case: every visible-flagged visual of the map is drawn every frame. It switches off, in both gpu cull shaders, the cull distance, frustum, screen size and Hi-Z tests of the main view and the query box, minimum caster extent and occlusion tests of the shadow views, in the cpu fallbacks the frustum and distance tests of `Visual` (`IsAABBVisibleLocal`, `IsWithinCullDistance`, the static tree walk), `render3d.SphereInFrustum` (which decides which point lights update their shadow map and light occlusion map) and `ShadowMap:IsWorldAABBVisible/TooSmall`, and the Hi-Z build. LOD selection is not culling: add `lod_level 0` for the most detailed worst case. `Visual.Library.noculling` still exists and means something else, it takes the cpu draw path.

`test/benchmarks/gm_construct_m3_frames.lua` runs culled, unculled, unculled at lod 0 and culled again at the lobby spawn. On this machine (RTX 4090, 1080p, lobby spawn, unculled, avg frame / GPU / allocation) the pass took the frame from 22 ms (cpu bound, 21 ms of recording) / 14.8 ms / 65 MB/s to 11.3-11.6 ms (GPU bound, culled the same) / 10.2 ms / 35-45 MB/s with 6-7 ms of recording. The same scripted fly over the map with culling on (`GMW_MODE=fly`) went from 31 ms (p95 54) to 10.5-11.6 ms (p95 18-20), gm_construct from 7.6 to 7.2 ms (p50 8.3 to 6.8).

What was in the frame, unculled (the order is the order of the findings):

- The gbuffer does not care about culling on this map: `gbuffer_multi_draw` draws 4515 entries in 4 indirect calls for 0.3 ms of GPU time, culled or not (742 entries culled). The frame is lighting, GI, translucents and fog, and cpu work for what is not gpu driven (translucent, glass tint and the 300 or so fallback entries).
- GC and `GetPBRFactorUploadKey`: the key was worked out per draw with a string concat per feature param (`"Get" .. param.name`), 15% of all GC samples and 29% of cpu time in GC. Keys of a material only depend on its properties, so they are cached per `property_version`. Properties declared with `versioned = true` (Material does, `objects.lua`) stamp their object with a new `property_version` when they change and put it in a ring log (`objects.version_log`), `Material:Touch()` is for code that changes a vector or a color in place (material proxies, only when they changed something).
- `BatchTable` rewrote 2 x 256 records of the gbuffer batches every frame as a safety net (2.2 ms). It now writes a record when its material was stamped (found from the log, not by scanning), the moving part of an animated batch every update, 4 records as a safety net, and copies only the records a frame's buffer is behind on into a buffer that stays mapped. Records are written by one generated function with constant field names and plain properties are read as fields, 7.5 to 3.3 us per record (a cdata field read by a variable name is slow).
- `GraphicsPipeline:Bind` (every dynamic state setter, 24% self time) ran for every glass tint, gbuffer fallback and overlay draw. They use `UploadConstantsBound` now, and pipelines whose uniform buffers all follow the current material (`block.memo_key`, `model_pipeline.GetMaterialMemoKey`) reuse the uniform offsets of a material for the rest of the frame. `CommandBuffer:BindDescriptorSets` compares dynamic offsets by content now, so offset tables can be reused. `ShouldPushConstants` and the persistent uniform compare allocate nothing and use `memcmp` (`bindings/memory.lua`).
- Screen space shadows were 4 ms of the 6.4 ms lighting pass, all of it for point and spot lights. They were marched before the point shadow map and the light occlusion map were looked up, and before knowing the light reaches the pixel at all (most BSP lights reach through walls), and the march result was thrown away for lights that a shadow map decides alone. The march is last now and only runs when the shadowed light is above the threshold, and fully shadowed lights are skipped before the BRDF and the 25 tap glass tint lookup. Lighting 6.4 to 2.0 ms.
- Glass tint redrew 4 maps every frame, 11 us per glass entry. A map is drawn again only when its light space matrix, the glass (entry, material version, world matrix compared with memcmp) or the framebuffer changed (`glass_tint.IsSlotCurrent`, the last image layout stays valid). The per frame collection of translucent and glass entries keeps what it works out per component until the entries, the material override or a material change (`get_items` in visual.lua), and `GetPreviousWorldMatrix` keeps two matrices instead of copying one per frame.
- Removed: `scene_bvh` diffed every light position every frame for a counter nothing read.

What is left, unculled lobby: GPU is the bound (the cpu waits ~5 ms per frame in `swapchain.GetNextImage`, `block_time.lua`). ddgi (shade 2.4, trace 0.8, distance 0.3, others 0.5 ms) is 35% of the GPU frame, the direct light loop 1.9 ms (115 lights reach the lobby cell by sphere, the light occlusion map kills most of them per pixel, disabling it makes lighting 3x slower; a visibility aware light grid would help), translucent_accumulate 1.2 ms of which 0.9 is that same loop per glass fragment, fog 0.9, shadows 0.5, reflections 0.4, ao 0.4. In the culled fly the cpu is the bound (translucent draws 2 passes x ~340 draws x 3.9 us, collection 0.5 ms, gbuffer 1.2-3 ms, glass tint while moving, shadow update 1 ms), a gpu driven translucent pass would remove most of it. About 30 materials animated by Source proxies still rewrite their batch records every frame (3.3 us each, 80 writes per frame in the lobby).

The Lua heap of this map was 2.5 GB after a full collection (`census_run.lua`, a full collection took 1.9 s): a million filesystem path_info tables (the `vfs` translate cache held 50000 paths times every mounted path, 500 MB and a third of a collection, now limited to 2000 paths: heap 2.2 GB, collection 1.4 s, the load is no slower), 645k polygon vertex tables and as many tangent tables that stay on the cpu after the upload, 26k convex hulls of static props, 7M tables in all. A collection cycle starts every 60-100 s at 40-50 MB/s and costs ~100 frames at +10 ms each plus one ~90 ms atomic hitch, the single worst frames of every run (a 90 ms frame inside `light_grid`, `ddgi_trace` or `glare` is the collector). Flying over the map for 9000 frames with culling on (`spikes.lua`, `M3_MOVE`): default settings avg 8.46 ms p95 17.2 p99 21.7 with 355 frames over 18 ms, `collectgarbage("setpause", 400)` avg 7.34 p95 9.8 p99 11.0 and none over 18 ms but 9.5 GB of heap by the end (no cycle ran), `setstepmul 100` p95 13.2 with a 130 ms hitch, pause 300 + stepmul 100 p95 13.7 with a 328 ms hitch. The engine does not set a pause, 400 is a memory for hitches trade the user can make with one line. Fewer allocations make cycles rarer, dropping the cpu copy of uploaded vertices would make them cheaper.

Scripts (`test/harnesses/m3/README.md` lists them): `measure.lua` for frame time and per pass numbers, `sweep.lua` for pvar variants in one process, `time_fn.lua`, `block_time.lua` and `spikes.lua` for where a frame goes, `prof.lua` and `ptree.lua` for profiles with `PT_UNDER` and `PT_CALLERS` filters, `alloc.lua` for allocations, `verify_caches.lua` to check the caches against a from-scratch computation, `ab_shot.lua` for screenshots. Pitfalls met on the way: `pkill -f "luajit glw"` in a shell command kills that shell, a `pgrep -f` in a waiting loop matches the loop itself, an alloc probe that wraps with a closure measures its own closures (wrap with `local a, b = f(...)`), the profiler pins samples on the wrong line now and then (a 28% hotspot in `scene_lights.lua` did not reproduce and timing said 0.2 ms), and a change of shared GLSL costs ~25 s of driver compile on the next run.

## Shader and pipeline caches, and the slow first start

*what is cached where, what the logs mean, how to start cold*

Three caches sit between a shader's GLSL and a running pipeline:

1. `storage/cache/shaders/<crc32>_<length>.spv`, the engine's own (`goluwa/render/vulkan/internal/shader_module.lua`). A file is a header, the SPIR-V and then the GLSL it was compiled from; a hit is used only when that GLSL equals the shader's exactly, so a crc32 collision or a stale or truncated file is detected, logged as `[shader] compiled ... because the cache is off: <reason>` and rebuilt. A plain miss logs `[shader] compiled <stage> shader ...` and a hit logs nothing. shaderc takes milliseconds per shader, so this cache is not what makes a cold start slow. The old format (a bare crc32 file name, SPIR-V only, no check) is deleted on first use.
2. `storage/cache/vulkan_pipeline_cache.bin`, the Vulkan pipeline cache, saved a couple of seconds after the last pipeline was made (a `--one-frame` run exits before that).
3. **The NVIDIA driver's own cache** in the home directory: `~/.cache/nvidia/GLCache` (about 1 GB here) and `~/.nv/ComputeCache`. This is what makes the first start slow: a cold start took about 117 s on this machine (about 115 shaders), a warm one 2.8 s. A shader change makes the driver recompile every pipeline that uses it, so any edit of shared GLSL (gbuffer layout, lighting, surface features) costs a slow start the first time. `[pipeline] the driver compiled a <kind> pipeline in N ms` is logged for any pipeline that took 50 ms or more to create, and nothing for the fast ones.

**Where the cold start goes (2026-10-13, `gi_reflections.lua`, 117 s):** shaderc is not the cost, its libraries (the Nix one and the release `.so`) compile the biggest shader in ~30 ms. The driver spends 107 s on 17 graphics pipelines, serially on the main thread: two lighting fragment shaders (132 KB and 183 KB of GLSL) take 45 s and 31 s, eight 65 KB ones ~3.5 s each, all compute pipelines together ~5 s. Tried in a worktree with a fresh driver cache: stubbing every ray query site (glass, reflection hit, DDGI visibility) saves ~30 s (117 to 88 s), `[[dont_unroll]]` on every loop is slower (133 s), shaderc optimization level 1 or 2 saves 3-12 s but grows the SPIR-V 5-10x and spends seconds in spirv-opt. The time is in the sheer size of the lighting shaders, not one feature; the untried levers are creating the pipelines on several threads (the two giants would overlap, wall time near the 45 s of the slowest) and splitting the lighting shader.

Start cold with `rm -rf ~/.cache/nvidia/GLCache ~/.nv/ComputeCache storage/cache/shaders storage/cache/vulkan_pipeline_cache.bin`, they all regenerate. If something renders wrong only on one machine's cache state, clear the driver cache first: it is the one cache the engine can't check.
