# Crysis levels

Crysis content is loaded by the `addons/crysis_loader` addon (`lua/crysis_loader/`: `level.lua`, `scene.lua`, `terrain.lua`, `water.lua`, `mtl_material.lua`, `units.lua`) with models from `goluwa/codecs`. Load levels with the `map` command (`map IA/Quarry`; prefix `cry:` if a name exists in several loaders). Where behavior must match CryEngine, read the shipped CryFX shader sources in `Game/Shaders.pak` (`Shaders/HWScripts/CryFX/*.cfx|cfi`, readable with python zipfile) before guessing; every earlier guess about encodings in this area was wrong until the shaders were read.

## Games

`crysis_loader/game.lua` knows Crysis, Crysis Wars and Crysis Warhead (`GAMES`: paks to mount, patch paks first because the VFS takes the first mount that has a file). Only one game's content is mounted at a time; loading a level mounts the game that owns its directory. `map IA/Quarry` picks the first installed game that has it (Crysis); use `map cry:wars:IA/Quarry` (`crysis:`, `wars:`, `warhead:`) to choose. Wars levels are the Crysis format with `.cry` editor data and need `ZPatch1.pak` for their props. Warhead's retail `level.pak` entries use zip method 6, which is raw deflate behind a keyless block cipher (key `crc32 ^ 0xCAFEBABE`, CRC-32 table feedback, 64 byte blocks permuted by a table; `crysis_loader/cry_pak.lua`, reached through the `ZipDecrypt` event, read from `CrySystem.dll`), so the zip codec reads them. Levels without `.cry` editor data (Warhead's, and Crysis's `Armada`) are "compiled" levels: `level.Load` then reads objects from `level.pak/mission_mission0.xml` (`<Objects>`: decals, entities, lights, `Archetype="Library.name"` props, resolved through `libraries.archetype_ids`) and brushes from `level.pak/brush.lst` (`crysis_loader/brush_list.lua`: a material name table (64 bytes, truncated, completed from `resourcelist.txt` only when the prefix is unambiguous), a model table with bounds, then 76 byte instances with a row-major 3x4 matrix). Brushes whose material is `collision_proxy_*` are invisible solids and are skipped, and `HIDDEN_MODELS` in `level.lua` drops models that break lighting (Warhead's `zero_g_sphere_half.cgf` dome shadows the whole level for GI). Compiled terrain (`crysis_loader/compiled_terrain.lua`) reads `terrain/heightmap.dat`: a 32 byte header, a 1024 slot vegetation group table (332 byte records), a model name table and a material name table (260 byte records, each led by a u32 count), then a depth first quadtree of 64 m sector nodes (version 5; AABB, f32 offset, f32 range, a sample count of 3, 5, 9, 17 or 33 per side and that many u16 heights, `height = offset + u16 * range`). Within a sector the slow index runs along x, and the editor heightmap is indexed `x * size + y`, which the rebuilt array follows (verified against the editor heightmap of a campaign level: exact at the stored samples, off by up to some meters between the coarse samples of steep 5x5 sectors, because the file only stores those). The low 4 bits of every height sample are the 0-based surface type index of that sample (order of `leveldata.xml` SurfaceTypes, 15 means none; verified against the editor layer bitmap of a campaign level, 99% identical), so the loader masks them out of the height (and centers it) and builds `terrain.surface_indices` (1 based, same layout as the heights) from them; sectors with a coarse grid use the nearest stored sample. The surface id bytes at the end of each node only list which types a sector uses. Vegetation (`crysis_loader/compiled_vegetation.lua`) is the 1024 slot group table (`[u32][name 256]` then the same parameters the editor vegetation map has: bending, size, size variation, density, elevation and slope limits, view distance ratio, flag bits for align to terrain, use terrain color, cast and receive shadow) plus the instances, which sit in an octree after the quadtree: 62 byte records (a bounding box, a flags word with bit `0x800` for vegetation, the position inside that box, scale, the group byte at +56 and the angle byte at +58). The octree node chunks are not walked: instances are found by scanning for that signature (checked on a campaign level against its editor instance array: all of them found, a few dozen extra). Brightness, category, sprites and random rotation are not stored, so category comes from the model folder and sprites are on except for rocks and grass. Their sun, fog and ocean come from the mission xml (`Lighting` can be under `Environment`); `ParseMissionEnvironment` is shared with editor levels. Warhead stores the terrain colour as plain RGB (its `tex2DTerrain` is a plain `tex2D`, read from `Shaders.pak`), where Crysis and Wars store chromaticity plus brightness (`plain_terrain_color` in `game.lua`). Warhead also has a `TerrainIce.cfx` shader that is not modelled. Textures and materials fall back to the merged mounted tree because a model in `Warhead_Objects.pak` can reference a material that lives in `Objects.pak`.

## Materials and textures

- `_ddn.dds` normal maps are ATI2 (3Dc), which stores Y in the first half of each block and X in the second, the reverse of BC5. `dds.lua` swaps the halves for ATI2, after which Cry normals follow the engine's TBN convention with no extra flips. If normals look wrong, correlate normal XY with the diffuse brightness gradient before adding flips.
- `mtl_material.lua` converts Cry MTLs to roughness/metallic at load time like `vmt_material.lua` does for Source. Cry shininess is a phong lobe and specular color times the gloss map is its strength: roughness comes from the lobe (blended to 1 for weak specular), a gloss mask (diffuse alpha or the Specular texture) becomes `RoughnessMin/Max`. The Metal shader does not mean metal: it still lights the diffuse fully and adds specular and reflection, and Crysis uses it for painted and rusty sheet metal (diffuse 0.3 to 0.5, specular 0.1 to 0.3); making it metallic turns those dark. Metallic is `smoothstep(0.4, 0.7, specular)` for the Metal shader and `metal` surface types, raised by `smoothstep(0.3, 0.8, FresnelBias)` (reflectance at normal incidence; Crysis's chrome preset has 0.9 with a specular of 0.125). The Metal shader's sharpness is `Glossiness` (`CookTorranceTex` in `Metal.cfx`, default 0.75), so its roughness is `1 - Glossiness`. A spec map scales the metallic softly (0 to 0.5, dark rust and dirt turn rough dielectric); the old narrow window speckled. A zero Cry specular color only meant no Phong highlight, so every material keeps the dielectric F0 of 0.04 (specular 1). The terrain layers are the exception at specular 0: the cover colors are very dark (a grass floor decodes to about 0.02 linear, Crysis brightens it only through gamma space lighting and exposure), and at that albedo 4% of the sky outshines the diffuse and greys the terrain out. Not handled: spec-map-alpha power, colored specular tints, Illum/Metal environment maps.
- Terrain color (`level.ParseCoverData` of `level.pak/terrain/cover.ctc`, a quadtree of DXT5 sectors): layer 0 is chromaticity (R, G) plus brightness (B), decoded as in CryEngine's `tex2DTerrain`; alpha is baked sun shadow; layer 1 is the terrain normal map. The detail texture is added in gamma space (adding in linear leaves saturated specks near black); that is `TerrainLayerAdditiveDetail`. CryEngine draws the detail layers only up to `e_detail_materials_view_dist_z` (128 m at the shipped specs) for Z projected passes and `_xy` (2048 m) for X and Y projected ones (a surface type whose material has `x`, `y` and `z` sub materials, the cliffs, gets all three passes, so steep faces keep their detail far away; the loader gives those layers `fade_distance_xy` and the shader weighs the two fades by the triplanar up and side weights), fading the layer out with `sqrt(1 - (d / dist)^4)` (`Terrain.cfx`); past that only the cover color is drawn. The loader gives the layers that `fade_distance`. Every layer is its own pass over the cover color with `sqrt(weight)` as alpha (the weights are per vertex, 0 or 1, so the square root spreads each layer about a cell into its neighbours), a later pass covering the earlier ones; the loader sets `layer_blend = "passes"`, which composites the layers that way in ascending surface type order (the order is assumed, not read from the engine). With a plain weighted blend the 2 m cells average into flat ground.
- UseTerrainColor grass blends its albedo toward the terrain color by `blendWithTerrainAmount` (`GroundColorTexture`, `terrain.ApplyVegetationMaterialState`), as `Vegetation.cfx` does for grass at every distance. Other UseTerrainColor vegetation is not blended: CryEngine fades it toward the terrain color only with distance (`0.5 + fRendQuality * 0.5`, "take terrain only at distance"), a trick to hide far trees in the terrain, and the engine renders assets the same near and far. It is not applied in GI/ray hit shading.

## Lights

`Light`, `SimpleLight` and `SimpleIndirectLight` entities (`level.ExtractLight`) become `light_point`, or `light_spot` when a projector texture is set (`crysis_loader/scene.lua`). Inactive ones (`bActive=0`, toggled by scripts in the original) are skipped. Many multiplayer maps have none (Mesa, Beach, Shore): there emissive materials are the only lamps. A Cry light's multiplier is its strength at the source, fading to nothing at its radius, so the lumens come from both: a multiplier M is M times `CRY_LIGHT_LUX_PER_UNIT` (100 lux, an interior scale, not the sun's) of illuminance at half the Cry radius, which is `4 pi (r/2)^2 M lux` lumens; the colour's luminance is folded into the lumens because the engine's light normalizes its colour. The Cry radius is also the light's `Range` and sets the source radius. Indirect lights get a larger source radius and no shadow. `bCastShadow` adds a `shadow_map_point` (far plane = the Cry radius) to point lights; spots get none yet. Light occlusion maps are never touched by the importer, they stay on by default; `fIndirectMutiplier` and the other RAM fields are not used. The calibration is by eye, not measured against CryEngine.

## Sun, fog, water

- Sun and fog live in `level.editor_xml` under Missions > Mission[Name=Current]: TimeOfDay (time, "Volumetric fog: Global density") and Lighting (`SunRotation` is latitude, Longitude). The sun uses CryEngine's CTimeOfDay formula; `Lighting.SunVector` is stale, ignore it. `level.lua` computes `sun_direction` and `fog_density`; `scene.lua` hands them to the `atmosphere_controller` (`GroundFogVisibility = -ln(0.02) / (fog_density * 0.0025)`), bypassing the weather latitude/date system. The level code never reads the time of day's ambient or sun color; the scene is lit by the engine's own sky. What CryEngine really does with that density (read from `Bin32/CryRenderD3D9.dll`, the function at VMA `0x3802d860` that fills `PB_VolumetricFogParams`, with `Shaders/HWScripts/CryFX/VolumetricFog.cfi` as the consumer; find it again by searching for the float constant log2(e) and its x87 `fldl2e` neighbour): extinction per metre at the viewer is `global density * 0.01 * exp(-16 / (atmosphere height + offset) * (viewer z - water level))` (water level 0 when the level has no ocean), and transmittance is `exp(-extinction * distance * (1 - exp(-t)) / t)` with `t` the same scale times the height difference, so it is a plain exponential height fog that dies out over the `Volumetric fog: Atmosphere height` variable (Quarry: density 0.2, height 2257 m, so 2e-3 per metre at the water level and an e-fold of 141 m). The loader now follows it: `scene.lua` sets the `atmosphere_controller`'s `GroundFogScaleHeight` to `atmosphere height / 16`, `GroundFogStartHeight` to the water level, `GroundFogEndHeight` to the water level plus 8 scale heights (CryEngine fades over the whole atmosphere height, but a taller shell only costs integration steps) and the ground fog visibility to `-ln(0.02) / (0.005 * density)` at the start height. That is half of CryEngine's extinction: with the full value, a Crysis screenshot of Quarry against the same view (exposure matched on the brick) showed the nearby hillsides veiled grey where Crysis keeps them green and detailed. Half still keeps the haze on the far mountains. Earlier the loader used a tuned `0.0025` and a fixed 280 m e-fold, which was 2 to 4 times thinner than CryEngine near the ground (Quarry at 158 m: 6.5e-4 against 2.8e-4 per metre). The level's `Fog color` and multiplier are still not used. When fog looks too dense, compare brightness and colour of the in-scatter before the extinction.
- Environment mapping is physical only. The sun comes from the time of day and `Lighting` (checked on Warhead's Frost: elevation crosses 0 at the level's `DawnTime`/`DuskTime`, 06:00 and 18:00, and peaks at the `Longitude` value; the `SunVector` attribute is stale). Fog follows the renderer's `PB_VolumetricFogParams` function in both `CryRenderD3D9.dll` builds: extinction `density * 0.01`, scale height `(atmosphere height + density offset) / 16`, anchored at the water level, with `WaterLevel` -1000000 meaning no ocean and an anchor of 0 (an anchor of -1e6 puts the fog a million metres underground). Warhead's extra density factor is `LDRGlobalDensMult`, which only applies in LDR rendering and is ignored. `EnvState.WindVector` (m/s) becomes the climate wind. Not mapped on purpose: sun and sky colour multipliers, the fog colour, the sky model's Mie/Rayleigh/anisotropy knobs and the skybox material (artistic; the engine's sky and exposure are physical).
- Ocean settings are Mission > Environment > Ocean/OceanAnimation; `WaterLevel` is mean sea level. CryEngine's ocean waves travel against the vector of `OceanAnimation.WindDirection` (radians): on island the angle is 3 and the level wind (`EnvState.WindVector`) is +x, so the loader negates the vector; the engine's `WindDirection` is where the waves go. The ocean follows the level wind (`EnvState.WindVector`, the climate wind) at runtime, with `WindOffset` set so the loaded wave size matches `WavesSize`; `Directionality` is 0.5. `WaterVolume` is a polygon (min-area rectangle), `River` a Bezier spline cut into boxes of at most 16 m. Fog color for water volumes and rivers comes through `media.MediumFromFog`; the ocean uses `media.MediumFromColor` (`cry_water.GetOceanMedium`): grey extinction of `FogDensity` per metre (CryEngine's fog density is already per metre: on island 0.08 gives the underwater visibility of the reference shots), scattering in the hue of `FogColor` (taken as linear, its 2.2 decode makes the water too blue) with green lifted by `OCEAN_HUE_BALANCE` (Crysis adds a cyan tint in post and on the terrain, which the reference shots carry), and a single scattering albedo of `max(FogColor) * FogColorMultiplier * 24.5` (0.85 on island, about 0.26 on Stranded, whose multiplier is 0.015 and whose water is darker in the game). Per channel extinction from the fog colour, or an absorption of pure water with the fog colour as albedo, turned the body purple or saturated blue. Match exposure on bright sand in the same shot (`ev` in the saved view) before judging the water colour; island's aerial reference matches at ev 15.7. At grazing angles the colour is mostly the reflection, not the medium.
- Cry's water shaders (CommonCausticsPass.cfi, Water.cfx, WaterOcean.cfx) use non physical caustics and normal-map waves; the engine's ocean does its own physically based version (see [render3d-lighting.md](render3d-lighting.md)).

## Ice

Warhead's ice shaders (`TerrainIce.cfx`, `Ice.cfx`, `IceOutdoor.cfx`, `IceIndoor.cfx`, read from `Shaders.pak`) map to the engine's `medium` feature (the `ice` preset, see [render3d-pipeline.md](render3d-pipeline.md)). Only the shader name is used: the `Absorption` param and `Diffuse` colour are ignored, the colours come from the medium preset. Ice meshes get a fixed absorption, white colour, porosity from the albedo, roughness 0.14 and specular 0.5, and loading one sets the scene level `assumed_thickness`; the terrain layer (`Materials/Terrain/frozen/ice2`, the `ice` surface type) puts the medium density in `cry_medium_density`, which `terrain.lua` gives the layer as `medium`. The air bubbles, depth map and refraction of `Ice.cfx` are not modelled. Frost's floes use the plain `Illum` shader, so only the `ice` terrain layer (about a quarter of the map, the frozen sea) and a few dozen special meshes are affected.

## Vegetation

- Leaf back lighting (`Vegetation.cfx`, `LeafShadingBack` in `shadeLib.cfi`, read from `Shaders.pak`): CryEngine adds `BackDiffuse * BackDiffuseMultiplier * opacity map * sun` to the front lighting, both multiplied by the diffuse map, with `Diffuse` multiplying only the front. So the transmittance over reflectance is `BackDiffuse * BackDiffuseMultiplier / Diffuse` (luminances) times the opacity map, which the loader sets as `DiffuseTransmission` with `BackDiffuse` as the tint and the opacity map as `TransmissionTexture`. `BackShadowBias` (back light kept in shadow) stands in for light through other leaves and is not used; the path tracer carries that light.
- Vertex colors (CGF stream 3, RGBA): R leaf edge flutter, G branch phase, B branch stiffness (1 rigid, bend = 1 - B), A ambient occlusion. A cgf without a color stream gets r 0, g 0, b 1, a 1 (held still), because zeros read as flexible everywhere. `Polygon3D.BendHeight` is the whole cgf's max height shared by all submeshes so trunk and leaves bend together.
- Vegetation animation (`deformation.BuildGlsl`) is based on CE2's `_DetailBending`. Detail bending applies only with the Vegetation GenMask DETAIL_BENDING plus LEAVES or GRASS; main bending applies to every object whose level vegetation group has `Bending != 0`, and rotates vertices about the origin keeping length (which keeps palm trunks from stretching). The CPU side follows Lumberyard: the bend vector is wind times 0.25 softly clamped, and the detail speed is 0.3 of its length; passing the raw wind as the detail speed makes leaves buzz because the wave input past 0.5 gets faster, not wider. Deliberate differences from CE2: the engine smooths the triangle wave, centers the flutter wave and pushes along the wind part of the normal, and pushes branches downwind. Tune `BEND_PER_HEIGHT` for sway strength before touching the shader. See [foliage.md](foliage.md) for the shared wind rules.
- Painted vegetation (`vegetationinstancesarray.editor_data`: 19 byte records of f32 x, y, z, f32 scale, u8 prototype id, u8 brightness, u8 angle) is drawn by scatter as placed instances, one `scatter_placements` entity per prototype (see [scatter.md](scatter.md)), never one entity per instance. "Fit to Terrain" (GenMask 0x4000) is scatter `Conform`; scatter is off on cry terrain (layers get `scatter = 0`). Only LOD 0 is drawn plus a billboard (`BillboardRadii`).

## Collision

- Collision comes from the cgf physics chunk of slot 0 (`physics_data_chunk_ids[1]`, decoded by `codecs/cry_physics.lua`); slots 1 and 2 are no-collide and obstruct geometry and are not solid. Models with no slot 0 (bushes, grass, hill trees) have no collision in Cry either.
- Brushes and GeomEntities are static bodies; entities and EntityArchetypes (physics and class come from `Libs/EntityArchetypes`) are static or dynamic from their `Physics` properties.
- Painted vegetation is drawn by scatter, but prototypes whose cgf has physics (`cgf.HasPhysics`: palm and jungle trunks, rocks) also get one static body per instance under `Vegetation Physics`.

## Performance of big levels

Beach has ~30k visuals and flying streams terrain, so a visual is added, removed or hidden nearly every frame. Rules that keep it workable:

- Scene updates must be incremental; terrain chunk bakes are batched into one command buffer with one fence (never a `SubmitAndWait` per chunk); removing an object scans `Instances`/`Children` from the back, because streamed objects are recent.
- `system.GetTimeNS()` returns `uint64`; dividing it by `1e9` gives whole seconds. `tonumber` first. A budgeted thinker that never exhausts its budget runs every task fully every frame.
- Large `BatchTable` growth must keep its records; queue model-load callbacks through `utility.CreateLoadCache(cache, budget)` so hundreds of instances do not build their primitives in one slice.
- Measure with `glw bench crysis_beach` (`test/benchmarks/crysis_beach.lua`). Wait ~30 s after the load "settles" before judging vegetation, and capture twice before calling a difference a regression. Print frames over 150 ms to find load stalls. See [performance.md](performance.md) for measurement pitfalls.

## Quarry test camera

Objects sit around (1414, 178, -1158); the default camera at the origin is far away. Overview: `--pos 1380,215,-1080 --ang -20,-10,0 --fov 70`; ground level by a warehouse: `--pos 1395,170,-1105 --ang -5,-20,0 --fov 70`. `--settle 15` is enough for vegetation to show.

- Players in Crysis levels are scaled to a 1.8 m person (`sv_cry_player_scale`, default `1.8 / 1.37`, times `sv_player_scale`): the levels' doors and props are built for that, the Source hull is 1.37 m, and no content is scaled. The loader does not convert units (a Cry unit is a meter).
- The world is curved (see [render3d-lighting.md](render3d-lighting.md), Planet): terrain and ocean fall away from the origin by `planet.GetDrop`, but Cry levels are authored flat (up to 1.4 m at the far corner of a 4 km map). Every Cry world position goes through `units.PositionToEngine`, which lowers it by the drop; `units.ToEngine` is for directions and model local data only. A new placement path that uses `ToEngine` for a position floats above the terrain by `d^2 / 2R`.
- Cry heightmap sample `i` sits at `i * HeightmapUnitSize` (the last sample is one unit short of the world size); the sampler and the rendered terrain use that convention, and painted vegetation matches the terrain within a centimeter with it. A `(width - 1) / world_size` scale is off by up to half a meter on a steep 4 km map.
