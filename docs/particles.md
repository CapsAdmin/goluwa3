# Particles

GPU particle pools simulated by one compute pass and drawn through the translucent passes. Rain and snow are low level systems; `particle_emitter_gpu` and `particle_emitter_cpu` are the editor facing components.

Start from `goluwa/render3d/particles.lua` (the system; the `Register{...}` fields are documented at its top), `passes/particles.lua`, `precipitation.lua` (rain/snow physics and rates), `particle_emitter.lua` (shared emitter properties), `particle_emitter_gpu.lua`, `particle_emitter_cpu.lua`, `medium_lighting.lua`.

## How it fits together

- A system is a pool of `max_count` `Particle`s (80 bytes) in one device local buffer, created when it first has something to show. Its behavior is glsl bodies (`spawn`, `update`, optional `visibility`, `collide`, `should_spawn`, `shade`) and its own uniform block. Systems are matched by name; a module that reloads takes over its slot and pool.
- `particles_simulate` is one dispatch over the largest active pool (x particle, y system). A dead slot spawns, otherwise it ages, updates, collides, gets visibility, and gets its light. The pass is in `default_passes` before `translucent`.
- Drawing is the `particles` entry of `translucent_extras.lua`: vertex pulling from the pools by device address; a particle is a capsule along its velocity, never thinner than about a pixel and a half (fainter by the same amount).
- Light is computed per particle every `RELIGHT_INTERVAL` frames and stored, so the draw passes only read it: the primary sun through the same chain the froxel fog uses (atmosphere, fog layer, shadow maps, cloud shadow, Henyey-Greenstein phase), local lights (`medium_lighting.GetLocalLightsGLSL`), and DDGI probes or the sky environment for ambient. In surfel mode particles on screen read the fog's GI grid (`froxels.gi`, the 8 nearest cells, skipping -1) and blend their light over relights against its noise; elsewhere they use the surfel lookup. `medium_lighting.lua` is what fog and particles share; use it for any new medium.
- Per-slot random numbers come from the generation counter (`p.user.x`) so respawns differ.

## Precipitation

Rain and snow fill a box of `BOX_SIZE` (20 m) around the camera, wrapped on every side, so density is constant and teleports cost nothing. The drawn count is capped and each particle stands for `coverage_scale` real ones. Wind is read every frame; size is read at spawn. Both collide with the `shelter_map`; a box wrap is not a fall (the update resets `particle_previous` so the step is not tested). `r_feature_precipitation` turns both off.

A system with `after_aa = true` is drawn after TAA in the effect layer (see vfx.md, Effects after TAA), which removes TAA ghosting of fast thin streaks.

## Collision

A system sets `collision = "shelter_map" | "scene_depth" | "rays"` (read each frame) plus a `collide` body; after the update the step from `particle_previous` to the new position is tested. Helpers in `particles.GetCollisionGLSL`: `particle_stick`, `particle_bounce`, or `p.life = 0.0` to die.

- `shelter_map`: the depth map from above along the precipitation. One read per end of the step; only sees tops of things.
- `scene_depth`: the view's depth and normals. Cheap; only sees what is on screen.
- `rays`: a short ray query per particle against the scene store (`hit.GetTraceGLSL`, solid mask). Needs ray tracing; no alpha; keep counts to tens of thousands.

The pass binds all resources whatever the mode, so a system can switch at runtime.

## Emitter components

Plain `GetSet` properties (storable, prefab friendly): rate, bursts, loop/duration, shape, speed, lifetime, gravity, drag, size, `OnHit`. `particle_emitter.Step` decides how many particles to spawn per frame (the same for both types). The two types follow each other where they can, and the editor shows only what each supports.

- `particle_emitter_gpu`: thousands of lit/emissive blended capsules; all gpu emitters share one system (`emitters`) with a ring-allocated range per emitter (`POOL_SIZE`, `MAX_EMITTERS`). All collision modes.
- `particle_emitter_cpu`: hundreds of solid meshes simulated in Lua over ffi arrays and queued into the gbuffer instancing path each frame (lit like models, with fog/AO/TAA). Collision is `none` or `rays` via the scene raycast, at most `RAY_BUDGET` per frame.

A `particle_emitter_cpu` whose `Material` is transparent (refractive, translucent, additive) is drawn by single draws in the translucent passes instead of the gbuffer instances: it extends the translucent depth range and requests the refraction source in `PreDraw3DTranslucent`, and thickness is `RefractionThickness` or 0.3 x the particle size. Meshes tumble around a per particle axis (`Spin` is the rate); `shard` is a faceted bipyramid. `Sparkle` (gpu) twinkles each particle's alpha. `Fizzle` (gpu, m/s^2) pushes each particle in a fast changing noise direction once `FizzleStart` (fraction of its life) has passed, so a burst that has slowed down scatters before it dies. `Flow` (gpu, m/s^2) adds the curl of a value noise field (`FlowScale` is its spatial frequency, features are 1/`FlowScale` m, the emitter `Seed` offsets it) to every particle's velocity, so a burst drifts in swirls; it is static in time. Damage types can list `Debris` (material, `Trail` for projectiles, `Emitter` for impacts; `Mesh` per emitter) and the impact effect bursts it. `SwayAmount`/`SwayRate` push cpu particles sideways with a per particle phase and `RockAngle` rocks a mesh back and forth instead of tumbling (feathers).

`emitter:BurstAt(count, position, direction)` queues a burst with its own origin (one is consumed per frame, the emitter does not move), so a shared emitter can serve many bursts a frame; `Burst(count)` spawns at the emitter's transform. A gpu emitter past `MAX_EMITTERS` simply gets no range and draws nothing, it does not error.

Properties marked `range` in the lists of `particle_emitter.lua` (`Lifetime`, `Speed`, `Drag`, `GravityScale`, `Spin`) take a number or a `{min, max}` table (`particle_emitter.GetRange`, `ScaleRange`, `AddRange`): each particle draws its own value inside the range. A range is opt in per property because it costs a min and a max in the gpu emitter block; to make another property randomizable give its list entry the `range` flag and its validator `range_value`, read it with `GetRange` in both backends (the gpu shader hashes a per particle random from the particle index, its generation and the emitter seed, `emitter_random_a` and `emitter_random_b`; the cpu particle record keeps its random values) and give the field `Range = true` in `effects_schema.lua` so the editor offers `Random` in the row's context menu. Properties without the flag are a single number.

A band property (`Size`, `Color`, `Emissive`, flagged `band` or `color_band`) is a value over the particle's life: a constant, a range (a number pair, or two colors), or a curve `{Keys = {{time, value, mode}, ...}, MaxKeys = {...}}` with times from 0 to 1 in order, a number (or an `{r, g, b, a}` / `Color`) per key and an optional `"smooth"` or `"step"` for the segment that starts at the key (default linear). `MaxKeys` makes the curve a band: every particle draws one random and sits that far between the `Keys` curve and the `MaxKeys` curve, so a particle that is big stays big. `particle_emitter.BakeScalar` and `BakeColor` write a value into a low and a high table of `CURVE_SAMPLES` samples (`math/curve.lua` finds the segment); the gpu emitter bakes every live emitter each frame into a host visible buffer reached by device address (`curves` in the emitter block, one record per slot, three frames in flight) and the shaders read it with `emitter_curve_size`, `emitter_curve_color` and `emitter_curve_emissive`; the cpu emitter bakes `Size` into its runtime and samples it with `SampleBaked`. Shader hooks get `emitter_size_at(e, index, p, f)` and `emitter_color_at(e, index, p, f)`, the value at a fraction `f` of the life (the particle's own random included). Color inputs set the rgb of a whole curve (`set`), only its first key (`set_first`) or only its last (`set_last`), keeping each key's alpha.

`Swirl` (m/s², signed) accelerates particles tangentially around the emitter's axis, so they spiral outward; `MinSpeed` (m/s) makes a particle that is slower than that age five times as fast (sparks that land and fade, after the first 0.1 s); `FlipRandom` (0 to 1) mirrors that share of the sprites horizontally; `Orientation = "ground"` lays the sprites flat on the world's horizontal plane instead of facing the camera (splashes, rings); `AlphaFromColor` takes the sprite's alpha from its brightest color channel instead of its alpha channel, for additive textures that are color on black. The three last ones are bits in the particle record's `spare` word (`2` mirrored, `4` ground, `8` alpha from color; bit `1` is the stuck flag of `OnHit = "stick"`), read by the draw shaders.

They run different code: a shape or force change that belongs in both has to be made in `particle_emitter_gpu.lua` (glsl) and `particle_emitter_cpu.lua`.

- `RatePerMeter` (gpu) spawns that many particles per metre the emitter moved since the last frame, spread along the segment between the two positions (with their sub frame age and offset, so fast sweeps leave no gaps), and points the emitter axis opposite to its motion so `Spread` is a cone behind it; `Rate` still adds on top.

## Shaders

A gpu emitter has a `Shader` (a name, default `glow`) and `ShaderParams` (a table of values by param name). `goluwa/render3d/particle_shaders.lua` is the registry: `Register(name, {Params = {{Name, Type, Default, Min, Max, Group, Description}}, Sprite = "ParamName", Source = "glsl"})`. Param types are `float`, `int`, `bool`, `vec3`, `color` and `texture`; the numeric ones are packed in declaration order into 16 floats per emitter (`e.params`), textures are looked up by name (vfx procedural textures, then asset paths).

- `Source` is one glsl string with up to four functions, compiled into the shared `emitters` system after the common code, not instead of it: `void spawn(emitters_t e, uint index, uint generation, inout Particle p)`, `void update(emitters_t e, uint index, float dt, float t, inout Particle p)` (before drag and integration), `float visibility(emitters_t e, uint index, float t, Particle p)` (a number multiplied into alpha) and `void shade(emitters_t e, uint index, float t, inout Particle p)` (after the common shading, `p.radiance`). Leave out the ones you do not need: the compiler finds the definitions by name (comments are ignored, a source that defines none of them is an error), gives each its own name per shader and dispatches by `e.shader`, and a hook nobody defines does nothing (`visibility` counts as 1). Every param is a preprocessor name for its slot in `e.params`, defined around the source and undefined after it, so a function that reads a param needs `e` in scope (helpers take an `emitters_t e` argument) and a local variable cannot reuse a param name. `glow` has no source and adds nothing.
- `Sprite` names the texture param: those particles are drawn as camera facing textured quads (`p.sprite` = rotation, texture slot + 1, a free float `z` (the frame for flipbooks, see below), `p.sprite.w` scales the size curve) instead of capsules. The param value is a flipbook name (`vfx.RegisterFlipbook`), a vfx texture or an asset texture, looked up in that order. Up to `MAX_SPRITE_TEXTURES` textures are in use at once.
- A flipbook sprite plays its frames: the emitter's `FlipbookFps` advances one frame per `1 / fps` seconds and wraps, `0` plays the frames once over the particle's life, and `FlipbookRandomStart` (with a nonzero fps) starts each particle on a random frame. The common update writes the frame to `p.sprite.z` before the `Update` hook, so a hook may override it; the draw reads the atlas grid per texture slot (`sprite_grids`). A plain texture leaves `z` alone. `Spin` (degrees per second, a number or a range) turns every sprite, added to `p.sprite.x` before the `Update` hook. The `sprite` shader (`Sprite` param only) draws any texture or flipbook with no hooks. `Stretch` above 0 draws the sprite as a streak along its screen space velocity instead: its length is the width plus that speed times `Stretch` seconds (the record marks it with a negative `p.sprite.y` and keeps `Stretch` in `p.sprite.x`, so rotation and spin do not apply). The `puff` shader is a sprite with `Grow` (how early the size curve is followed), `ColorCurve` (how early the color curve is followed), `FadeIn` and `FadeStart` params: the flipbook smoke and fire look of the grenade explosion. `Flatten` (0 to 1) squashes the emission direction onto the plane perpendicular to the emitter axis (with a wide `Spread` it makes a ring).
- The generated glsl is compiled once when the passes are built. After registering or changing a shader call `particles.Recompile()`: it rebuilds only the `particles_simulate` pipeline, and throws the compiler error if the glsl is wrong (the old pipeline keeps running); `particle_shaders.ParseError(message)` turns it into `shader line N: message` (N counts the lines of `Source`). The shader that is registered at that point is what the next compile uses, so undo a bad one before recompiling again.
- The game side is `addons/game/lua/particle_shader_library.lua` (data files in `lua/particle_shaders/`, `Update` validates, recompiles only when the glsl or the param layout changed and restores the previous version on failure) and the effects editor category `particle shaders`.

## Pitfalls

- A block layout table must nest sub-layouts (`light_occlusion.GetBlockLayout()` as an element); `unpack(...)` in the middle only yields one field.
- A pass that reads a storage buffer from the vertex stage by address needs the barriers by hand: compute to vertex after the dispatch, vertex to compute before it (see `particles_simulate`'s `on_draw`).
- Systems that depend on ray queries must work with `GOLUWA_NO_RAY_TRACING=1` (the particle test passes with it).
