# Terrain

`goluwa/terrain/` builds terrain as streamed tiles of real triangles from a height `Source` (`source.lua`, `shader_source.lua`: a glsl field baked once per tile, with normals, splat weights and color derived from it). `terrain.lua` is the tile manager, `tiles.lua` builds tile meshes and materials, `height_physics.lua`/`physics.lua` give colliders. `local_stuff/terrain/` holds the C++/Vulkan Limcore Terrain project used as a reference (a heightmap clipmap displaced by tessellation) and a goluwa port of its scene (`limcore_scene.lua`).

## Terrain from maps

`heightmap_source.lua` is a terrain source made from data: `size` (meters), `origin` (the world x, z the map is measured from), `uv` (a 2x2 matrix, how a world x, z minus the origin maps to the maps), `outside` (the height beyond the map: `"zero"`, `"clamp"` to the edge height or a constant number, colors and layers always clamp to the edge), `max_height`, `height` (`{width, height, samples}` r16 samples), `color` (a Texture), `indices` (a layer id per cell, optional) and `layers` (detail layers by id: albedo, normal, height textures and `height_scale`, `scale`, `detail`, `additive_detail`, `specular`, `scatter`, `roughness`). `HeightmapSource.SampleHeight(data, x, z)` is the same height on the cpu (the static world's `TerrainHeight` for roads and decals). The `terrain` component owns such data: `SetData(data)` builds the tiles once the color map is ready, `Path` loads the data from a file. `heightmap_file.lua` saves and loads the data as a directory (`terrain.lua` with a `version` that `Load` checks, `origin`, `uv`, `outside`, `height.r16`, `indices.r8`, `color.dds` bc7, the layer textures, a generated layer height texture as bc4) so a terrain does not need the source it was made from. `crysis_loader/terrain.lua` only translates a Crysis level into that data (`Translate`) and adds the component to the level's entity (`SpawnTerrain`); put the component on the entity of the static world, an extra child entity under it costs a third of the frame rate. The terrain manager itself has no extent: tiles stream around the camera forever and a finite map is a source whose answer outside its data is the `outside` policy. Pitfalls: `static_world.Find` starts at the parent, an entity's own static world is `entity.static_world`; the color map must be ready before the first tile bakes from it.

## Editable terrain

A `terrain` component with an empty `Path` owns its data as properties: `Size`, `Resolution`, `MinHeight`/`MaxHeight` (`min_height` is the height of a zero sample), `Layer1..4` (names registered with `terrain.RegisterLayer(name, definition)`; the game addon registers its `textures/terrain/` layers), `Layer1..4Scatter`, `ScatterSet` (a name, see `ScatterSet.AddFactory`) and the maps `Heights` (r16) and `LayerMap` (r8, a layer id per sample) as hidden binary strings, so the scene file carries the terrain and undo, clone and load work on it like any property. Without maps it is flat at 0. It is a square centered on the world origin in world space whatever its entity's transform (the tiles' root undoes it). Property changes rebuild at the end of the frame. `IsEditable()` is true for such data; scene export's `terrain` option only writes the other kind.

- Edits change `data.height.samples`/`data.indices.samples` and call `UpdateRegion(box)`: the maps are uploaded again and `Terrain:Invalidate(box)` bakes the tiles and colliders over the box again under a new `Generation` (part of the chunk key), swapping each in place when its chunk is ready; a tile still waiting for a chunk the source had already started (or that was in and becoming the tile, which can yield) is built again once it arrives. `CommitMaps()` writes the samples back to the properties.
- With no more than four layer ids a layer id is always the same material slot, so a scatter prototype's `layers` weights mean the same layer in every chunk.
- The editor's brush mode is `addons/editor/lua/terrain_editor.lua`: selecting an entity with a terrain (or `scatter_placements`) opens a tool window (raise, lower, smooth, flatten, paint a layer; radius, strength), one stroke is one undo entry, the gizmo hides while a tool is active and left drag paints instead of turning the camera.

## Tile streaming

- `Terrain` has `Levels` (LOD rings) and `GridSize` (chunks per side of a level; the finer level fills the middle half, so the ring is `GridSize / 4` chunks thick; it must be at least 4, because the two levels snap differently). Reach is `GridSize * 64 * 2^(Levels-2)` m across; layout changes cost tiles, triangles, memory and load time but not gpu frame time.
- A tile is kept until its replacements are built (`IsTileReplaced`), then the replacements are shown and the old tile is removed once the culling that is drawn was dispatched after they were shown (`AreReplacementsDrawn`, `gpu_culling.GetDrawnCullFrame`, so `draw.Draw` must call `MarkMainViewDrawn`). A fixed delay is both too short (holes) and too long (z-fighting overlap). When a replacement has a scatter set it also waits for its vegetation to be baked (see [scatter.md](scatter.md)).
- Removed tiles' chunk textures are released `ReleaseFrames` later (`PendingReleases`, at most `ReleasesPerFrame` a frame): the bindless array swaps a released texture for the fallback and reuses its index, so releasing early shows another chunk's texture. Bake textures are pooled by size and format (`RecycleTexture`).
- Build order is `goluwa/render3d/view_priority.lua` (shared with scatter): tiles with nothing drawn under them come before tiles that only refine; inside that, the nearer of the camera now and where it will be in 0.5 s to the tile's box, times `1 + OutsidePenalty * (how far outside the view)`. It must be a multiplier, not an offset, or tiles under a moving camera starve. The build queue is worked every frame (`BuildsPerFrame`) and re-prioritised each update; replacements of one retiring tile share their best member's priority so they appear together.
- Ray traced presence is throttled: `InSceneBVH` per visual, `BVHLevels` (finest levels in the scene), `BVHDelay` (a tile enters only after being wanted that long, since fast flight makes tiles that are gone before they are used) and `BVHPerFrame`. Flying fast and jumping make hundreds of tiles due at once; any per-frame work over all of them must be budgeted.
- A shader source writes a visual tile's vertices on the gpu (`request.gpu_mesh`, `tiles.RecordGpuMesh`): in its bake batch, after the heights are copied out for readback, a compute pass reads them from that buffer and writes the tile template's layout (grid, skirts, shell base copy) into a device only vertex buffer the chunk owns (`ShaderSource:ReleaseChunk` frees it), so a tile keeps no cpu vertex copy. The cpu still gets the heights (physics, bounds) and builds the coarser ray traced copies (`BVHStride`) itself. Tiles only use the buffer once the cpu saw the batch's fence, so the batch ends with a barrier that only makes the writes available instead of one that makes later work wait.
- A tile's splat, color and normal textures are at least as fine as its mesh (`Samples - 1`) on every level: a high camera looks straight down at far rings, which are not foreshortened there.
- Per-frame scans over all tiles must use cached tile bounds and per-level grids (`GatherOverlappingDesired`), not recompute levels or compare every retiring tile with every desired one.
- Debug: the `terrain_tiles` command (`Terrain:GetDebugReport()`) lists counts and tiles that should be drawn but are hidden; the TERRAIN tab of the PERF window (`terrain_stats`). `addons/examples/lua/examples/render3d/terrain_debug.lua` is a bare rolling terrain with a hue per level; oblique views only (top-down from high looks grey).

## Planet curvature

Sources work in local height (meters above the planet's datum, what `HeightGLSL`, the map samples and `HeightmapSource.SampleLocalHeight` return); the baked heights, the tile meshes, height colliders (`HeightPhysics`) and `HeightmapSource.SampleHeight` (world `TerrainHeight` for roads, decals, foliage, the editor) are world y, the local height minus `planet.GetDrop(x, z)` (see render3d-lighting.md, Planet). Splat and color bakes get the local height back. Build priorities use each tile's drop range.

## Earth (`addons/earth`)

`lua/earth/earth.lua` streams the real Earth as terrain: `earth.Start{lat, lon, Layers, Terrain, Clouds, Buildings, Water, Land, Roads, RecenterDistance}` (the example is `addons/examples/lua/examples/render3d/earth_real.lua`, `EARTH_LAT`/`EARTH_LON`). Without lat and lon it starts at the weather's location (`weather.GetLocation`, set by the game addon), and the weather's location follows the origin (start and `Recenter`), so the sun and sky are those over the origin.

- Frame: the world origin stands on the anchor latitude and longitude, +x is east, -z is north, and a world x, z is the point of the sphere straight below the tangent plane (`planet.GetDrop`, `geo.WorldToLatLon`). The planet is a sphere of `planet.RADIUS`; lat/lon are used as if spherical. Heights are above sea level (EGM2008, as the data comes), so they meet the ocean at 0.
- `source.lua` (`EarthSource`) is a shader source whose bakes get per chunk textures (`request.textures` in `ShaderSource`): a 9 x 9 map from world x, z to web mercator pixels computed in doubles on the cpu (float32 cannot hold a global mercator pixel at deep zooms), a height mosaic and an imagery mosaic copied from the decoded tiles at one zoom per chunk. A chunk waits for its tiles; tiles that cannot come (failed, or deeper than the data goes there) make it use the next coarser zoom. Terrain marks a request it no longer wants `request.cancelled`, so a source that waits can drop it.
- `tile_set.lua` downloads (per host request limits, retries, a disk cache under `storage/cache/earth/`), decodes on the thread pool and keeps decoded tiles in an LRU. Heights are Mapterhorn's terrarium webp tiles read out of its pmtiles archives with range requests (`mapterhorn.lua`: the coverage list says which regional archive has lidar zooms; `pmtiles_archive.lua` reads an archive, its header and directories cached on disk, every read pinned to the ETag of the first). Mapterhorn has no tiles over open sea and reads exactly 0 on the sea near coasts: those texels take the AWS terrarium bathymetry (`fill_sea`), clamped to 0 near coasts. Imagery is a chain (`imagery_sources.lua`, BeamNG.Earth's list of keyless national and state orthophoto services, 10 cm to 1 m, each with its bounding box) ending in EOX Sentinel-2 cloudless 2016 (10 m): a chunk takes the first source whose box holds it at a zoom it serves (tile caches from zoom 10, WMS exports from 14, as a WMS renders every tile it is asked for), the next where a tile is missing or blank (a service outside its country answers one colour, mostly white, or black edges), so the change between sources lies along borders and between near and far rings, not colour matched yet. All of them get a tone curve that lifts the darks and holds back the brights, since the photos carry the capture sun's shading. A source can be dehazed as it is decoded (`dehaze` on its `TileSet`: the dark channel prior with a fixed haze colour, so tiles agree at their edges); the Sentinel-2 mosaic is, as its haze and thin cloud read as a pale teal over green land. Attribution is drawn on the HUD, with the regional services baked from in the last minute.
- The photo is the albedo; layers only add grain (`detail` > 0 divides the layer by its average), so wrong splat weights change texture, not color. Outside lidar the heights are a surface model (forests and towns stand up) at 20 to 40 m; the bake adds noise below the data's native spacing (`native_zoom`), stronger on slopes.
- `earth.Recenter(lat, lon)` moves the origin: the old terrain stops streaming (`Terrain:Freeze`) and is drawn moved by the rigid transform between the two frames (`geo.Relate`) until the new terrain has loaded hidden; the active view moves too and `EarthRecenter` lets other systems follow. Heights stand along the old frame's y, so tall ground of the old terrain is off by height times distance over radius (14 m at 3.5 km and 25 km) until it is replaced.
- `Clouds = true` (`cloud_cover.lua`): low, mid and high cloud layers whose cover comes from Open-Meteo (a weather model's percent cover per height band, hourly from yesterday to tomorrow) on a 1.5 degree lat/lon grid around the origin, interpolated to the weather time and drawn into the clouds' coverage map. Open-Meteo counts each location as a call (about 600 a minute free), so the grid is a few hundred points fetched in batches that retry, cached for three hours. The grid is sampled with a cubic b-spline: bilinear shows the cells from orbit.
- `Buildings = true` (`buildings.lua`): Overture's building footprints (OpenStreetMap, Microsoft and Google machine learned footprints) from its zoom 14 vector tiles (`goluwa/codecs/mvt.lua`) within 3 km of the camera, extruded to `height`, else floors times 3.2 m, else a guess by class. A tile's mesh is built on the thread pool (`building_mesh.lua`; tens of ms for a dense city tile) from a grid of ground heights the main thread samples over it; a tile waits until the ground under it is loaded. Heights are often missing outside well mapped places (one Vietnamese town tile: 67 of 12501 buildings have one, central Oslo: 16% height, 72% floors). Outside lidar the terrain is a surface model that already has the buildings as lumps. Colours are vertex colours (materials with `VertexTint`): a wall takes a mapped `facade_color` (muted toward grey, they are named colours) or one of a weighted palette picked by a hash of the building's id, so a building looks the same from every tile; a roof takes a mapped `roof_color`, else its mean colour in the photo (`EarthSource:RequestPhoto` through the imagery chain, only where a source is about 2 m a pixel or sharper: pixels 1 m inside the outline and out of shadow, at least 6), else a palette pick. Walls carry a facade texture baked once (`FACADE` in `buildings.lua`, through `layer_texture`): a window bay per uv unit, white so the vertex colour is the plaster's; a wall's uv has a whole number of bays across and a floor per unit up from the ground (`building_mesh.BAY_WIDTH`, `FLOOR_HEIGHT`).
- `Water = true` (`water_bodies.lua`, `water_grid.lua`): Overture's water polygons (base theme, zoom 13; lakes, ponds, reservoirs, rivers, streams, canals; not pools, fountains, basins, ditches, drains or intermittent water, nor the sea, which is the ocean) within 5 km of the camera. A tile is turned on the thread pool into grids over it (1024 texels and a margin): the signed distance to the shore (exact to the outlines next to them, chamfer further out) and the level of the nearest water, from height data the main thread composes (`EarthSource:RequestHeights`). A lake's level is the median ground inside it away from the banks, below the ground along its shore, and the lake is dropped when its ground varies more than 1.5 m (the height data has flattened real lakes) or is near sea level; a river gets a level per block of 64 texels from the low ground of its block and the blocks around, so it steps down its course. The terrain is carved in the bake from a per chunk water mosaic of those grids (`EarthSource` texture3, `earth_carve`): down under the water along a bank slope to a few meters, never below the sea, and the ground within 25 m of the shore raised half a meter over the level, which is what lets a box reach over the bank. Finished tiles `Terrain:Invalidate` their area so chunks baked without them bake again. The nearest water is filled with open `water_volume` boxes of one level each (at most `water.MAX_VOLUMES`, which the water pass loops over per pixel), grown greedily from the deepest texels over water of their level and over ground the carved terrain keeps above it; farther water is the carved bed in the photo's colours. Flat land near the level (deltas, paddies) keeps the boxes close to the water, so there they are many and small.
- `tile_grids.lua` streams grids made from Overture tiles around the camera on the thread pool (`overture_tiles.lua` fetches and caches the tiles of each Overture theme once for everything that reads them); a chunk's bake gets a mosaic of a grid's texels, waits for the tiles under it that are on their way, and tiles that come later invalidate the chunks baked without them.
- `Land = true` (`earth.LandCover`, `land_grid.lua`): what the ground is within 6 km of the camera, from the zoom 13 base tiles: ESA WorldCover's land cover everywhere (about 50 m polygon edges at that zoom), OpenStreetMap's land use and land drawn over it where they say what the ground is (residential and protected areas do not), as a grid of classes (`EarthSource` texture4). The class picks the layers (`Layers` has eight: grass, forest floor, rock and crop first, as those are the four a `ScatterSet` (`Terrain.ScatterSet`) can grow on, so meadows, woods, scree and fields grow apart; then sand, snow, dirt and gravel; crop is the crop layer or dirt by how green the photo is, urban gravel or grass, bare dirt or sand, a water bed dirt) and scales the relief finer than the height data (flat fields and towns, rough rock); steep ground is rock whatever the class, and only unclassed ground falls back to guessing from the photo's colour. Class edges are sampled through a little noise, so the polygons' straight edges do not show.
- `Roads = true` (`earth.Roads`, `road_grid.lua`): Overture's transportation segments within 3 km (zoom 14; roads, paths and main railways, not sidewalks, crossings, steps, bridges, tunnels or other levels) as a grid of the distance to the nearest road's edge and its class (`EarthSource` texture5). Overture has no widths, so a class gives one, and a shoulder over which the ground beside blends to the road's. The bake drops the relief finer than the height data on a road, paints the class's colour over the photo by how much of a texel the road covers (so far, coarse texels fade it), and gives paved roads no layer and unpaved ones dirt. The distance is interpolated between texels, which keeps edges sharp at 2 m texels, as the nearest of several roads' distances is continuous. Mesh road decals (`decal_projection.Road`) sample the CPU height per vertex, which neither scales to a city's roads nor matches heights baked on the gpu.
- `Objects = {Trees}` (`objects.lua`, `object_features.lua`, `bridge_features.lua`, `prop_models.lua`): what stands at a point or runs along a line within 2.5 km, from the zoom 13 base tiles' infrastructure and land layers, and the bridges of the zoom 14 transportation tiles within 3 km (the raised parts the road grid leaves out: a deck from one end's ground to the other's, lifted in an arch to clear the ground between by `CLEARANCE`, railings, piers). Points (power towers and poles, street lamps, traffic signals, bus stops, masts, mapped trees, and trees every 8 m along tree rows) are placed scatter instances (`scatter.AddPlacements`, `scatter.WritePlacement`) of one set made at start, a mapped tree one of `Trees` by its position; power lines, fences, walls, hedges and bridges are a vertex coloured mesh per tile (`tint_mesh.lua`, which buildings use too; a visual's primitives go on child entities). All are made on the thread pool from the height data under the tile (`EarthSource:RequestHeights`), without the terrain's finer relief; a feature in a tile's buffer belongs to the tile it starts in. The models of `prop_models.lua` are tapered boxes standing in for real ones.
- `png.DecodeBuffer` writes rows bottom up; jpg and webp decode top down.

## Height functions of a shader source

`terrain_bake_step()` is the sample spacing of the texture being baked, which differs between the mesh heights and the finer field, normal, splat and color bakes of the same tile; anything that changes the height itself with level (octave dropping aside) must use `terrain_tile_step()` (the mesh spacing of the tile, the same in every bake of it), or the mesh and its splat and normals disagree. A pattern finer than a few mesh samples aliases, so a procedural pattern should coarsen with `terrain_tile_step()` (a checkerboard can double its cell size per ring so it stays readable from far above).

## Layers

The weight texture of a tile (`SplatSize` texels, baked by the source's `terrain_splat`) says where a layer is allowed; a texel covers more ground on coarser tiles, so slopes taken from it differ between levels. Per layer values (`tiles.CreateMaterial`, `layer.<key>`, vec4 per four layers) decide the rest at the pixel:

- `slope_min`, `slope_max`, `slope_blend`: steepness from the detail normal; put slope rules here rather than in the splat. Scatter applies the same rules (`goluwa/render3d/terrain_layer_rules.lua` is the glsl both include), so what grows on a layer is where the layer shows.
- `height_blend`: scales the weight by the layer's height texture so transitions follow the grain.
- `height_scale` (with a `height` texture, `layer_texture.BakeHeight`): parallax relief as a fraction of the layer scale. The march is one ray in world space along the surface normal with the triplanar height sampled at each step, ground at the real surface and rocks rising from it; marching each projection along its own axis made rocks lean and swim with the view. On the finest `ShellLevels` (2) levels the tiles get a height shell instead (`TerrainShell`, the largest `height_scale * scale`): the tile is lifted along its normals by it and gets a base copy, the chunk heights become a float texture (`TerrainHeightTexture`), and the shared shell march (render3d-pipeline.md) measures each sample's height above the ground along the local terrain normal and samples the splat weighted relief at its foot point on the ground, so rocks grow out of slopes and break the outline. The layer textures are then sampled at that foot point (sampling at the hit puts half a dome's texture in the wrong place), and the shading normal is the slope of the displaced relief there, not the layer normal maps, whose baked strength does not match the relief. It costs several ms of gbuffer time when near tiles fill the view. The shell measures height above the tile's own triangles (the cell's triangle plane, same diagonal as the mesh), not a bilinear sample, or on steep curved cells the ray starts above the shell and discards, leaving holes (the base copy is not drawn with the eye outside). The chunk's height texture has one border sample all round (`chunk.border_heights`, `chunk.heights` is the inside), and a march stays valid up to that border past the tile edge, so neighbouring tiles overlap and a ray leaving one tile is resolved by the other instead of falling into a seam. The splat weights are sampled at every step (caching them along the ray was tried and dropped). The slope at the hit is a forward difference against the hit's own relief (its height minus its clearance), two extra relief evaluations; a central difference takes four, and those evaluations were most of the shell's cost.
- `far_scale`/`far_distance`, `far_scale_b`/`far_distance_b`: extra texture scales the layer fades to with distance, against visible repeats.
- `fade_distance`: fade to the layer's average color (the smallest mip, so the layer's textures need mips: `mip_map_levels = "auto"`; `detail_strength` has the same need). An additive detail layer fades out to the base color instead, as CryEngine's layer pass does. The curve is CryEngine's `1 - sqrt(1 - (d / fade_distance)^4)`, so most of the detail stays until near the distance.
- `anti_tiling`: samples a rotated and shifted copy and mixes by noise; costs a second fetch.
- `TriplanarSharpness` on the source: exponent of the triplanar weights.
- `cover_slope`, `cover_start`, `cover_range`, `cover_power`, `cover_blend`: a covering layer (snow) laid over the others, covering ground flatter than a slope that grows with height. With `cover_depth` (metres) it has real depth in the height shell: under cover the relief is `max(rock relief, cover_depth + its own height * height_scale * scale)`, so it fills hollows and rocks taller than it poke through.

## What the Limcore reference does that tiles do not

Limcore bakes a height function into nested heightmap cascades re-baked incrementally around the camera, and displaces instanced planes in the vertex/tessellation stage. Tiles here are real triangles because the ray traced scene, height colliders and scatter (one job per triangle) read them; a displaced mesh would need each of those to read the height texture. Ported from it: bake the height function once and derive the rest from it, level aware octave dropping (`pn_fbm_lod` in `goluwa/terrain/noise.lua`), and sharing one index buffer between tiles of a shape.

## Verifying

`test/tests/render3d/terrain.lua` and `terrain_streaming.lua`. For streaming changes fly a terrain scene fast with periodic teleports and look at frame times of the terrain stages and at per-frame coverage (count drawn tiles covering points ahead of the camera: 0 is a hole, 2+ an overlap). Long frames after a jump usually come from many tiles becoming due at once.
